# ADR 0005: 파이프라인 실행 트레이스 — DynamoDB 기반 단계별 추적

Date: 2026-04-23
Updated: 2026-07-21

## Status

Accepted (2026-07-21)

## Context

RCA 파이프라인은 여러 단계와 최대 3회의 검증 루프로 구성된다. 세션 수준 상태만
저장하면 대시보드는 "현재 어떤 단계인지"와 최종 보고서만 보여줄 수 있고, 그 사이에
무슨 일이 있었는지는 사라진다.

구체적으로 확인할 수 없는 것들이다.

1. 각 단계의 소요 시간, 입출력 요약, 오류 원인
2. 가설 트리 구조(부모-자식 관계, 분기 과정) — 분석 과정을 재현할 수 없다
3. 검증 루프 반복 횟수와 각 루프의 결과

## Decision Drivers

- 가설 설명·판단 근거 같은 도메인 데이터를 트레이스에 담을 수 있어야 한다.
- 진행 중인 분석의 상태를 실시간 조회·갱신할 수 있어야 한다.
- 한 RCA의 전체 실행 기록을 단일 조회로 읽을 수 있어야 한다. 대시보드가 매 페이지 로드마다 여러 저장소를 오가면 안 된다.
- 트레이스 기록 실패가 분석 파이프라인을 중단시켜서는 안 되고, 트레이스가 무기한 축적되어서도 안 된다.
- 두 엔진의 트레이스가 섞이지 않아야 한다. 같은 알람을 두 엔진이 분석하기 때문이다.

## Decision

기존 DynamoDB 단일 테이블에 `SPAN#` 및 `HYPO#` SK 접두사로 트레이스 데이터를 저장한다. 분산 트레이스의 span 개념을 차용하여 파이프라인의 각 단계를 추적하고, 가설 트리 노드를 별도 아이템으로 영속화한다.

### 아이템 스키마

기존 `PK="RCA#{rca_id}", SK="SESSION"` 아이템과 동일 파티션에 두 가지 새 아이템 유형을 추가한다:

1. **Span 아이템** (`SK="{engine}#SPAN#{span_id}"`): 파이프라인 각 단계의 시작/종료, 소요 시간, 입출력 요약, 에러, 메타데이터를 기록한다. parent_span_id로 중첩 구조(검증 루프 → 하위 단계)를 표현한다. SK 접두사에 엔진명(`strands` 또는 `cc-headless`)을 포함하여 엔진별 트레이스를 분리한다.
2. **Hypothesis 아이템** (`SK="{engine}#HYPO#{hypothesis_id}"`): 가설 트리 노드의 설명, 카테고리, 상태, 신뢰도, 증거 요약, 판단 근거를 기록한다. parent_id와 depth로 트리 구조를 표현한다.

### 쓰기 전략

엔진별로 쓰기 방식이 다르다:

**코드로 오케스트레이션하는 엔진**은 각 파이프라인 단계의 시작·종료 시점에 스팬을
직접 기록한다. 단계 경계가 코드에 있으므로 계측 지점도 코드에 둘 수 있다.

**CC Headless**는 산출물 파일을 트레이스 소스로 사용한다. 모델이 트레이스 기록 도구를
직접 호출하게 하면 "분석에 불필요한 도구"로 판단해 건너뛰므로, 트레이스 완결성이 모델
판단에 의존하게 된다. 대신 모델은 이미 계약상 저장해야 하는 산출물만 저장하고, wrapper가
산출물 생성을 감지해 스팬으로 변환한다. 트레이스 기록의 권위를 모델에서 서버로 옮기는
결정이다.

산출물은 실행 토큰별 격리 디렉터리에 원자적으로 저장되고, wrapper가 현재 실행의
디렉터리만 폴링한다. 실행 종료 후 디렉터리를 정리해 다른 세션이 이전 산출물을
트레이스로 오인하지 못하게 한다.

각 산출물은 대응하는 파이프라인 단계 스팬이 되고, 가설 목록과 검증 결과는 가설 항목의
생성·상태 갱신으로 이어진다.

공통 규칙:

- **트레이스 쓰기 실패는 분석을 차단하지 않는다.** 기록 후 진행하는 fire-and-forget이며, 트레이스는 관측 편의이고 분석 결과가 계약이다.
- 가설 노드는 일괄 쓰기로 저장한다.
- 입출력 요약은 500자로 제한하고 전체 데이터는 증거 저장소에 남긴다. 항목 크기 제한이 있고, 트레이스는 "무슨 일이 있었나"를 보여주는 용도이므로 원본을 중복 보관하지 않는다.
- 산출물 파싱에 실패한 스팬은 실패 상태와 원인을 함께 기록한다. 누락시키면 그 단계가 실행되지 않은 것과 구별되지 않는다.

### 읽기 전략

한 RCA의 세션·스팬·가설 전체를 **단일 파티션 조회**로 읽는다. 세션 목록 조회는 기존
방식을 유지하고 트레이스 항목은 필터로 제외한다. 별도 인덱스를 추가하지 않는다.

### 대시보드 연동

RCA 식별자로 트레이스를 조회하는 엔드포인트를 제공하고, 스팬 타임라인과 가설 트리를
시각화한다.

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 표준 분산 트레이싱(OpenTelemetry + 관리형 트레이스 서비스) | 트레이싱 생태계 도구를 그대로 쓸 수 있고 계측 방식이 표준적이다. | 가설 설명·판단 근거 같은 도메인 데이터를 span 속성으로 담기에 부적합하고, 보존 기간이 짧으며 커스텀 질의가 제한적이라 대시보드가 필요한 조회를 만들 수 없다. |
| 트레이스 전용 별도 테이블 | 세션 조회와 트레이스 조회가 격리되어 서로 영향이 없다. | 관리 지점이 늘고, 한 RCA의 세션+트레이스를 읽으려면 두 번 조회해야 한다. 같은 파티션 키를 공유할 수 있는데 테이블을 나눌 이유가 없다. |
| 오브젝트 스토리지에 실행 로그 JSON 저장 | 저장 비용이 가장 낮고 크기 제한이 없다. | 진행 중 상태를 갱신할 수 없고 질의가 불편해 실시간 대시보드가 성립하지 않는다. |
| 기존 세션 테이블의 같은 파티션에 항목 유형 추가 | 한 번의 조회로 세션·스팬·가설 전체를 읽고 인프라 변경이 없다. | 세션 목록 조회 시 트레이스 항목도 읽혀 필터링이 필요하고, 항목 수가 늘어 테이블 비용이 증가한다. |

## Consequences

### Positive

- 파이프라인 실행 과정을 분산 트레이스처럼 시각화할 수 있다
- 가설 트리 구조와 판단 과정(증거 요약, 판단 근거, 신뢰도 변화)을 대시보드에서 확인할 수 있다
- 기존 테이블 재사용으로 인프라 변경이 없다 (CDK 스택 수정 불필요)
- **90일** 후 자동 정리되어 트레이스가 무기한 축적되지 않는다 (가설 트리 상태와 같은 주기 — [ADR infra/0002](0002-evidence-storage.md))

### Negative

- 파이프라인 단계마다 상태 저장소 쓰기가 추가된다 (코드 계측 엔진은 단계당 시작·종료 2회, 산출물 기반 엔진은 산출물당 1회)
- 가설 노드 저장·갱신 쓰기가 가설 수에 비례해 추가된다
- 세션 목록 조회 시 트레이스 항목도 읽히고 필터로 제외된다
- 산출물 폴링 주기만큼 트레이스 반영이 지연된다

### Risks

- 저장소 쓰로틀링 시 트레이스 데이터가 유실될 수 있다. fire-and-forget이므로 분석 파이프라인은 영향받지 않는다
- 항목 수 증가로 테이블 비용이 소폭 증가한다
- 세션 수가 크게 늘면 목록 조회 성능이 저하될 수 있다. 인덱스 추가로 대응한다
- 산출물 기반 엔진에서 모델이 산출물을 저장하지 않으면 그 단계의 트레이스가 누락된다. 다만 필수 산출물이 없으면 완료 게이트가 세션을 완료하지 않으므로 누락이 조용히 넘어가지 않는다([ADR agent/0011](../agent/0011-cc-headless-prompt-driven-rca.md))
- 모델이 형식이 깨진 산출물을 저장하면 해당 스팬이 실패로 기록된다. 저장 시점 형태 검증이 이 경우를 작성 주체에게 되돌려준다
