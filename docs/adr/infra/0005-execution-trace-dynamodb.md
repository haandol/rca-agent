# ADR 0005: 파이프라인 실행 트레이스 — DynamoDB 기반 단계별 추적

Date: 2026-04-23
Updated: 2026-09-15

## Status

Proposed

## Context

RCA 파이프라인은 여러 단계와 최대 3회의 검증 루프로 구성된다. 세션 수준 상태만
저장하면 대시보드는 "현재 어떤 단계인지"와 최종 보고서만 보여줄 수 있고, 그 사이에
무슨 일이 있었는지는 사라진다.

구체적으로 확인할 수 없는 것들이다.

1. 각 단계의 소요 시간, 입출력 요약, 오류 원인
2. 가설 트리 구조(부모-자식 관계, 분기 과정) — 분석 과정을 재현할 수 없다
3. 검증 루프 반복 횟수와 각 루프의 결과

플레이북 실행과 회고가 분석과 별도 생명주기로 추가되면서 추적 대상이 늘었다. 실행은
같은 리포트에 대해 여러 번 시도될 수 있고, 각 시도는 절차 단위로 진행된다
([ADR agent/0017](../agent/0017-playbook-execution-agent.md)). 회고는 실행마다 한 번
수행된다([ADR agent/0018](../agent/0018-playbook-retrospective.md)).

## Decision Drivers

- 가설 설명·판단 근거 같은 도메인 데이터를 트레이스에 담을 수 있어야 한다.
- 진행 중인 분석의 상태를 실시간 조회·갱신할 수 있어야 한다.
- 한 RCA의 전체 실행 기록을 단일 조회로 읽을 수 있어야 한다. 대시보드가 매 페이지 로드마다 여러 저장소를 오가면 안 된다.
- 트레이스 기록 실패가 분석 파이프라인을 중단시켜서는 안 되고, 트레이스가 무기한 축적되어서도 안 된다.
- 세션을 소유한 엔진과 그 엔진이 만든 트레이스를 식별할 수 있어야 한다.
- 같은 리포트에 대한 여러 실행 시도가 서로 섞이지 않아야 한다.

## Decision

기존 DynamoDB 단일 테이블에 `SPAN#` 및 `HYPO#` SK 접두사로 트레이스 데이터를 저장한다. 분산 트레이스의 span 개념을 차용하여 파이프라인의 각 단계를 추적하고, 가설 트리 노드를 별도 아이템으로 영속화한다.

### 아이템 스키마

엔진 중립 세션 아이템(`PK="RCA#{rca_id}", SK="ANALYSIS#SESSION"`)과 동일 파티션에 다음 아이템 유형을 추가한다:

1. **Span 아이템** (`SK="{engine}#SPAN#{span_id}"`): 파이프라인 각 단계의 시작/종료, 소요 시간, 입출력 요약, 에러, 메타데이터를 기록한다. parent_span_id로 중첩 구조(검증 루프 → 하위 단계)를 표현한다. 신규 SK 접두사에는 활성 엔진명(`strands` 또는 `headless-codex`)을 포함하여 엔진별 트레이스를 분리한다.
2. **Hypothesis 아이템** (`SK="{engine}#HYPO#{hypothesis_id}"`): 가설 트리 노드의 설명, 카테고리, 상태, 신뢰도, 증거 요약, 판단 근거를 기록한다. parent_id와 depth로 트리 구조를 표현한다.
3. **Execution 아이템** (`SK="EXEC#{execution_id}"`): 한 번의 플레이북 실행 시도의 상태, 시작·종료 시각, 대상 분석 원본(완료 리포트 또는 조기 승인 파트), 수행한 절차 수, 차단·실패 건수, 해결 판정을 기록한다. 실행 단위로 항목이 갈라지므로 같은 분석에 대한 재실행이 서로 덮어쓰지 않는다.
4. **Playbook 개정본 아이템** (`SK="{engine}#PLAYBOOK_REVISION"`): 회고가 갱신한 플레이북의 현재 내용과 검증 상태, 그리고 어느 실행이 갱신했는지를 기록한다. 실행 항목과 달리 **실행마다 갈라지지 않고 덮어쓴다** — 갱신은 같은 플레이북 식별자를 유지하므로([ADR agent/0018](../agent/0018-playbook-retrospective.md)) 개정본도 하나만 존재해야 하고, 새 식별자로 분기하면 같은 장애 유형의 지식이 흩어진다. 덮어쓰기 때문에 갱신 전 내용은 이 항목이 아니라 증거 저장소의 사본이 보유한다.
5. **Playbook 개정 준비 아이템**
   (`SK="{engine}#PLAYBOOK_REVISION_STAGE#{execution_id}"`): 벡터 게시 전에 실행별
   개정 내용을 `PENDING`으로 내구성 있게 저장한다. 벡터의 publication token과 정식
   개정본의 실행 식별자가 일치해야만 검색에서 `VERIFIED`를 노출한다. 정식 개정본
   확정은 이 준비 아이템의 소유 실행과 상태를 조건으로 검증하며, 확정 트랜잭션에서
   준비 아이템을 삭제한다.
6. **활성 실행 아이템** (`SK="EXEC_ACTIVE"`): 같은 RCA에 아직 끝나지 않은 승인이
   있는지를 나타내는 단일 예약이다. 대시보드는 Execution 아이템의
   `PENDING_APPROVAL` 생성과 이 아이템 생성을 한 트랜잭션으로 수행한다. 종료 시에는
   자신이 소유한 실행 식별자와 일치할 때만 삭제한다.
7. **분석 파트 권위 아이템**: 정상화·근본원인 분석·운영 개선 파트별로 상태, 시도,
   현재 원본 개정, 원본의 S3 위치와 내용 지문, 제한된 요약, 시작·종료 시각과
   실패·건너뜀 이유를 기록한다. 조기 실행의 승인 준비 여부와 철회 여부도 서버가
   관리한다. 전체 산출물은 이 아이템이 아니라 불변 S3 원본에 보존한다.

**실행 항목의 SK에는 엔진명을 넣지 않는다.** 실행 경로는 엔진과 무관하게 하나이므로
([ADR infra/0008](0008-playbook-execution-stack.md)) 엔진으로 분리할 대상이 아니다. 어느
엔진의 분석을 실행했는지는 항목의 대상 분석 원본 참조가 보유한다. 반면 **개정본은
엔진별로 분리한다** — 서로 다른 알람에서 선택된 엔진들이 같은 플레이북 식별자를 보강할
수 있으므로, 한 엔진의 회고 결과가 다른 엔진의 절차를 덮어써서는 안 된다.

완료 분석의 승인 화면은 **승인 직전까지** 개정본을 분석 산출물보다 우선한다.
조기 승인은 현재 정상화 파트의 정확한 원본 개정과 서버가 검증한 승인 근거를 사용한다.
승인한 뒤의 실행
근거는 최신 조회 결과가 아니라 승인 시점에 저장한 immutable 플레이북 스냅샷이다.
승인 이후 개정본이 바뀌어도 이미 승인된 실행의 근거는 바뀌지 않는다.

실행 하위 단계(절차별 시도)는 스팬 아이템으로 기록하고 실행 식별자를 부모로 참조한다. 회고도 실행 식별자를 부모로 하는 스팬으로 기록한다. 실행 증거 원본과 갱신 전 플레이북 사본은 트레이스가 아니라 증거 저장소가 보유하며([ADR infra/0002](0002-evidence-storage.md)), 트레이스는 요약과 참조만 담는다 — 항목 크기 제한이 있고 트레이스의 용도는 "무슨 일이 있었나"를 보여주는 것이다.

### 쓰기 전략

#### 세 분석 파트의 상태와 조기 승인 예약

정상화·근본원인 분석·운영 개선은 각각 **대기·실행 중·완료·실패·건너뜀** 상태를
가진다. 전체 분석 상태, 근본원인 확정 여부, 실행 상태를 파트 상태로 대신하지 않는다.
실제로 시작한 파트만 실행 중으로 전이하며, 원본 저장과 권위 참조 확정 후 완료로
기록한다. 실패한 파트에는 실패 이유를, 시작하지 않고 건너뛴 파트에는 건너뜀 이유를
남긴다. 재시도는 기존 실행 제한 안에서 별도 시도로 식별하고 이전 결과를 보존한다.
현재 소유권이나 원본 개정이 바뀐 뒤 도착한 쓰기는 현재 결과를 덮어쓸 수 없다.

파트 완료와 승인 준비 상태 `READY`는 별개다. 정상화 파트가 완료돼도 검증된
런북이 없으면 조기 승인은 불가능하다. 근본원인 미확정 자체는 검증된 조기 롤백을
막지 않지만, 서버가 입력 호환성과 정상 대상 등 승인 선행 조건을 검증해야 한다.
검증에 사용할 장애 당시 관측은 런북을 `READY`로 공개하기 전에 불변 원본으로
고정한다([ADR infra/0002](0002-evidence-storage.md)). 모델의 완료·호환 주장이
권위 상태를 대신하지 않는다.

조기 승인 요청은 화면에서 확인한 원본 개정·위치·내용 지문을 사용한다. 서버는
승인 스냅샷에 해당 원본 개정, 검증 근거, 대상, 명령과 순서 및 성공 기준을 고정한다.
승인 스냅샷을 저장한 뒤 **현재 원본 개정 일치, 파트 완료, `READY`, 미철회**와
기존 소유권 조건을 확인하는 조건부 결정 안에서 `EXEC`의 `PENDING_APPROVAL`과
`EXEC_ACTIVE` 예약을 함께 확정한다. 큐 전달은 예약 확정 뒤에 수행한다.
조회 이후 원본이 바뀌거나 준비가 철회되면 이전 화면의 요청은 거부한다.
스냅샷 저장만 성공하고 예약에 실패한 경우 실행을 시작하지 않는다.

이 조건은 승인 직전 조회만으로 대체할 수 없다. 원본 교체·철회와 승인 예약이
경합해도 하나의 유효한 현재 원본에 대해서만 예약돼야 한다. 승인 이후에는 기존
불변 스냅샷과 실행 취소·소유권 검증 계약을 유지하며, 새 원본으로 승인 내용을
바꾸지 않는다.

분석 파트의 상태와 승인 권위는 관측용 스팬의 비차단 쓰기 대상이 아니다. 저장
실패를 성공으로 표시하거나 누락된 권위를 스팬·최신 리포트에서 추정하지 않는다.
원본은 **60일**, 경량 파트 상태는 **90일**의 기존 보존 주기를 따른다.
조기 승인 가능이나 실행 성공만으로 미완료 분석을 공개 라이브러리에 승격하지 않는다.

#### 비교·제안과 현재 지식의 상태

새 사고의 비교 결과와 변경 제안은 해당 RCA와 연결해 조회한다. 비교 기록은 후보별
유사도와 선정·제외 이유, 선택한 플레이북의 기준 개정본, 기존 내용, 현재 사고 증거,
제안 내용과 항목별 변경 전후·이유를 고정한 원본을 참조한다. 현재 플레이북이
바뀌어도 당시 비교는 그대로 읽으며 재비교는 별도 기록으로 남긴다.

비교 결과는 변경 제안, 변경 불필요, 유사 후보 없음, 적용 가능한 후보 없음,
검색·비교 실패를 구분한다. 제안은 검토 대기에서 사용자 반영으로 반영됨,
사용자 기각으로 기각됨이 되며 처리 근거와 결과 개정본을 기록한다.
제안 처리와 런북 실행 승인은 별개의 상태와 행동이다.

사용자가 반영하면 서버는 **제안에 고정된 플레이북 식별자·기준 개정본의 식별과 전체
내용이 현재 권위 개정본과 정확히 일치할 때만** 현재 지식을 갱신한다.
기준에 개정본이 없었다면 여전히 개정본이 없고 그 완료 원본의 식별과 내용이 같아야 한다.
비교와 현재 개정본 교체, 제안의 반영됨 및 결과 기록은 하나의 원자적 조건부 결정이다.
CAS(compare-and-swap, 기준값이 같을 때만 교체)는 조회 이후의 동시 변경도 거부한다.
사고별 복사본만 확인하거나 플레이북 식별자만 비교해 공유 지식의 현재 기준 확인을
대신할 수 없다.

자동 회고나 다른 제안 반영으로 기준이 바뀌면 기존 제안은 반영하지 않으며
최신 내용으로 다시 비교하게 한다. 비교 원본을 최신 값으로 바꿔 기존 제안을 통과시키지
않는다. 같은 제안의 반복 요청은 이미 기록된 결과를 돌려주고 개정본과 이력을
중복 생성하지 않는다. 반영·기각과 게시 상태는 유실 가능한 관측 트레이스가 아니라
갱신의 권위 기록이다.

사용자 반영으로 원본 저장과 현재 개정본을 확정하면 검색 게시를 대기로 기록한다.
검색 인덱스의 게시 대상과 현재 권위 개정본이 같을 때만 게시 완료로 전이한다.
검색 실패는 반영 결과를 되돌리지 않고 동일 개정본의 게시를 재시도한다.
늦은 이전 게시가 현재 개정본을 덮어쓰거나 새 개정본의 게시 완료로 기록될 수 없다.
제안의 반영됨과 검색 게시 완료는 분리해 조회한다.

해결된 실행의 자동 회고와 기존 엔진별 회고 개정본·준비본 계약은 유지한다.
사용자 반영이 다른 엔진이나 다른 사고의 런북을 덮어쓰지 않으며 과거 보고서,
승인 스냅샷과 실행 증거도 보존한다. 원본과 상태의 보존 주기는
[ADR infra/0002](0002-evidence-storage.md)를 따른다.

#### 파이프라인 트레이스

엔진별로 쓰기 방식이 다르다:

**코드로 오케스트레이션하는 엔진**은 각 파이프라인 단계의 시작·종료 시점에 스팬을
직접 기록한다. 단계 경계가 코드에 있으므로 계측 지점도 코드에 둘 수 있다.

**Headless Codex**는 산출물 파일을 트레이스 소스로 사용한다. 모델이 트레이스 기록 도구를
직접 호출하게 하면 "분석에 불필요한 도구"로 판단해 건너뛰므로, 트레이스 완결성이 모델
판단에 의존하게 된다. 대신 모델은 이미 계약상 저장해야 하는 산출물만 저장하고, wrapper가
산출물 생성을 감지해 스팬으로 변환한다. 트레이스 기록의 권위를 모델에서 서버로 옮기는
결정이다.

산출물은 실행 토큰별 격리 디렉터리에 원자적으로 저장되고, wrapper가 현재 실행의
디렉터리만 폴링한다. 실행 종료 후 디렉터리를 정리해 다른 세션이 이전 산출물을
트레이스로 오인하지 못하게 한다.

각 산출물은 대응하는 파이프라인 단계 스팬이 되고, 가설 목록과 검증 결과는 가설 항목의
생성·상태 갱신으로 이어진다.

공통 규칙:

- **관측 트레이스 쓰기 실패는 분석을 차단하지 않는다.** 기록 후 진행하는 fire-and-forget이며, 트레이스는 관측 편의이고 분석 결과가 계약이다. 파트 원본 확정·승인 준비·철회·예약 같은 권위 기록에는 이 비차단 규칙을 적용하지 않는다.
- 가설 노드는 일괄 쓰기로 저장한다.
- 입출력 요약은 500자로 제한하고 전체 데이터는 증거 저장소에 남긴다. 항목 크기 제한이 있고, 트레이스는 "무슨 일이 있었나"를 보여주는 용도이므로 원본을 중복 보관하지 않는다.
- 산출물 파싱에 실패한 스팬은 실패 상태와 원인을 함께 기록한다. 누락시키면 그 단계가 실행되지 않은 것과 구별되지 않는다.

### 읽기 전략

한 RCA의 세션·스팬·가설 전체를 **단일 파티션 조회**로 읽는다.

분석 파트의 경량 상태와 승인 준비 여부도 같은 RCA 파티션에서 읽으며 전체 분석
상태와 구분해 반환한다. 파트 상세는 권위 아이템이 가리키는 S3 원본을 범위·개정·내용
지문 검증 후 읽는다. 원본이 없거나 만료됐으면 이유를 표시하고 과거 내용을 최신
리포트나 현재 관측으로 재구성하지 않는다. 파트 아이템에는 세션 목록 전용 인덱스
키를 기록하지 않는다.

세션 목록은 **엔진별 시간 역순 인덱스**로 읽는다. 파티션 키는 세션을 소유한 엔진이고
정렬 키는 세션 생성 시각이며, 인덱스는 목록 한 행을 그리는 데 필요한 속성만 투영한다.

**인덱스 키는 세션 아이템만 갖는 전용 속성이어야 한다.** 이미 존재하는 `engine`과
`created_at`을 그대로 키로 쓰면 가설·실행 아이템도 두 속성을 갖고 있어 인덱스에 함께
들어온다. 실측에서 세션 91개를 읽으려면 인덱스에 641개 항목이 실려 **7배**가 되고, 한
페이지를 요청해도 대부분이 가설 항목이라 세션은 몇 건만 나온다 — 페이징이 성립하지
않는다. 따라서 세션을 기록할 때만 쓰는 별도 키 속성을 두고, 그 속성의 존재 자체가 "이
아이템은 세션이다"를 뜻하게 한다. **인덱스 키를 갖지 않는 아이템은 인덱스에 들어오지
않는다**는 DynamoDB의 sparse index 성질이 필터 없는 세션 전용 조회를 만든다.

**목록 조회는 전체 테이블 순회여서는 안 된다.** 순회는 트레이스 항목까지 모두 읽고
필터로 버리므로 비용과 지연이 세션 수가 아니라 **트레이스 총량**에 비례하고, 정렬을
보장하지 않아 "최신 N건"을 저장소가 잘라줄 수 없다. 최신 구간만 필요한 화면이 전체를
읽는 구조는 기록이 쌓이는 만큼 확실히 악화된다.

**목록은 활성 엔진을 각각 조회하고 레거시 파티션을 함께 합친다.** 엔진이 파티션
키이므로 한 번의 조회로는 한 엔진만 읽힌다. 활성 엔진 `strands`,
`headless-codex`와 읽기 호환 대상 `codex-headless`, `cc-headless`의 결과를 생성
시각으로 병합해 한 페이지를 만든다. 신규 쓰기는 두 레거시 식별자를 사용하지 않는다.
엔진을 인덱스 파티션
키로 두는 대신 상수 하나로 묶으면 모든 세션이 단일 파티션에 몰려 쓰기가 그 파티션에
집중된다.

**인덱스 도입 전에 기록된 세션은 키 속성이 없어 인덱스에 없다.** 인덱스만 읽으면 그
세션들이 목록에서 사라지므로, 인덱스 사용은 기존 세션에 키 속성을 채우는 것과 같은
변경으로 다룬다. 채우기는 기존 속성을 덮지 않는 추가 전용 갱신이어야 한다 — 목록 조회가
쓰기 경로의 상태를 바꿔서는 안 된다.

#### 페이지 경계와 전체 집계의 분리

한 페이지를 그리는 데 필요한 정보와 **전체를 세는 정보는 다른 조회로 얻는다.**

목록 한 행은 "이 분석에 아직 사람이 할 일이 남았는지"를 말해야 하고, 그 판정은 같은
파티션의 실행 절차·실행 항목까지 봐야 나온다. 따라서 **행 단위 보강은 그 페이지에 실린
세션에 대해서만 수행한다** — 전체를 보강하면 페이지를 나눈 이유가 사라진다.

반면 **승인을 기다리는 건수와 결과별 건수는 전체 기준이어야 한다.** 페이지에 실린 것만
세면 "승인 대기 10건"이 "3건"으로 줄어들고, 이는 늦은 화면보다 나쁘다 — 사람이 남은 일의
양을 틀리게 안다. 이 집계는 페이지와 무관한 별도 조회로 구하고, 목록 페이지와 같은
응답으로 내려보내지 않는다.

### 대시보드 연동

RCA 식별자로 트레이스를 조회하는 엔드포인트를 제공하고, 스팬 타임라인과 가설 트리를
시각화한다.

세 분석 파트의 상태와 산출물, 조기 실행의 승인 가능 여부를 각각 표시한다.
정상화 파트 완료나 실행 성공을 전체 분석 완료 또는 근본원인 확정으로 표시하지 않는다.
승인 화면은 서버의 현재 원본 개정·준비·철회 상태를 사용하며 스팬 완료만으로
승인 버튼을 활성화하지 않는다.

플레이북 전용 목록은 현재 보존 중인 완료 분석의 공개 가능한 플레이북을 식별자별로
묶고 현재 게시된 지식과 연결된 사고를 제공한다. 장애 유형·증상 요약·태그·갱신 시각과
연결된 특정 런북의 초안·검증됨 상태를 보여주며 유형·태그·검증 상태로 페이지 단위
조회한다. 미완료 분석, 미반영 제안, 회고 준비본을 공개 지식에 섞지 않는다.
검증됨을 다른 사고의 명령에 대한 보증으로 표시하지 않는다.

상세 조회는 게시된 개정본과 고정된 비교 기록, 제안 처리 결과와 게시 대기·완료를
구분해 제공한다. 원문 만료·조회 실패는 사유를 표시하고 비교·반영에 사용하지 않는다.
요약과 같은 페이지의 상세 모달은 [ADR agent/0007](../agent/0007-rca-report-generation.md)의
열람 계약을 따른다.

## Consequences

### Positive

- 파이프라인 실행 과정을 분산 트레이스처럼 시각화할 수 있다
- 가설 트리 구조와 판단 과정(증거 요약, 판단 근거, 신뢰도 변화)을 대시보드에서 확인할 수 있다
- 기존 테이블 재사용으로 인프라 변경이 없다 (CDK 스택 수정 불필요)
- **90일** 후 자동 정리되어 트레이스가 무기한 축적되지 않는다 (가설 트리 상태와 같은 주기 — [ADR infra/0002](0002-evidence-storage.md))
- 분석·실행·회고가 같은 파티션에 있어 한 장애의 전 과정을 단일 조회로 읽는다
- 실행 시도가 항목 단위로 갈라져 재실행 이력이 보존된다
- 회고 게시가 중단돼도 준비본과 정식 개정본이 구분되어 미완료 승격을 검색에서
  검증됨으로 노출하지 않는다
- 기존 `codex-headless`·`cc-headless` 세션을 다시 쓰지 않고도 대시보드와 승인
  경로에서 계속 읽을 수 있다

### Negative

- 파이프라인 단계마다 상태 저장소 쓰기가 추가된다 (코드 계측 엔진은 단계당 시작·종료 2회, 산출물 기반 엔진은 산출물당 1회)
- 가설 노드 저장·갱신 쓰기가 가설 수에 비례해 추가된다
- 세션 목록 조회 시 트레이스 항목도 읽히고 필터로 제외된다
- 산출물 폴링 주기만큼 트레이스 반영이 지연된다
- 실행 절차 수에 비례해 스팬 쓰기가 늘어나고, 재실행마다 항목이 누적된다
- 회고 게시 중에는 실행별 준비 아이템이 하나 추가되며 실패한 준비본은 TTL까지 남을
  수 있다

### Risks

- 저장소 쓰로틀링 시 트레이스 데이터가 유실될 수 있다. fire-and-forget이므로 분석 파이프라인은 영향받지 않는다
- 항목 수 증가로 테이블 비용이 소폭 증가한다
- 세션 수가 크게 늘면 목록 조회 성능이 저하될 수 있다. 인덱스 추가로 대응한다
- 산출물 기반 엔진에서 모델이 산출물을 저장하지 않으면 그 단계의 트레이스가 누락된다. 다만 필수 산출물이 없으면 완료 게이트가 세션을 완료하지 않으므로 누락이 조용히 넘어가지 않는다([ADR agent/0011](../agent/0011-cc-headless-prompt-driven-rca.md))
- 모델이 형식이 깨진 산출물을 저장하면 해당 스팬이 실패로 기록된다. 저장 시점 형태 검증이 이 경우를 작성 주체에게 되돌려준다
- 실행 스팬은 fire-and-forget이므로 유실될 수 있으나, 실행 증거 원본은 증거 저장소에 별도 보존되므로 회고 입력은 트레이스에 의존하지 않는다
