# ADR 0008: 플레이북 실행 인프라 — 사용자 트리거 큐와 실행 권한 분리

Date: 2026-07-30

## Status

Accepted (2026-07-30)

## Context

플레이북 실행은 사용자 승인 뒤에만 시작되고, 대상 리소스를 제한하지 않는 대신
파괴적 액션을 거부하는 방식으로 안전을 확보한다([ADR agent/0017](../agent/0017-playbook-execution-agent.md)).
이 실행 주체를 어디에 두고 어떻게 기동할지 결정해야 한다.

기존 인프라에는 자동 복구용 워커 스택이 있었다. 그 스택은 분석 완료 이벤트를
구독해 자동으로 기동되며, 활성화 여부를 태스크 수로 제어했다. 두 특성 모두 새
결정과 맞지 않는다. 이벤트 구독은 사용자 승인 없이 실행을 시작하는 경로이고,
태스크 수로 기능을 켜고 끄는 것은 승인 게이트가 있는 구조에서 의미가 없다.

또한 분석 엔진은 두 종류를 유지하지만(엔진 비교 목적) 실행 경로는 하나여야 한다.
엔진마다 실행 스택을 두면 안전 정책이 복제되어 갈라진다.

실행 주체는 분석 엔진과 **권한이 반대**다. 분석은 읽기 전용이고 실행은 넓은 쓰기
권한을 가진다. 두 권한을 같은 태스크 역할에 두면 분석 경로의 결함이 쓰기 권한에
닿는다.

## Decision Drivers

- 실행은 사용자 승인 없이 기동되어서는 안 된다.
- 실행 경로는 분석 엔진 종류와 무관하게 하나여야 한다.
- 실행 권한이 분석 태스크 역할에 섞여서는 안 된다.
- 승인 요청이 중복 전달되어도 실행이 중복되어서는 안 된다.
- 실행이 오래 걸려도 플랫폼 시간 제한에 걸려서는 안 된다.
- 실행 요청의 유실이 승인 사실의 유실이 되어서는 안 된다.

## Decision

플레이북 실행을 **전용 스택의 단일 상시 워커**로 운영하고, 사용자 승인은 **전용
큐에 발행되는 실행 요청**으로 전달한다.

### 새 스택 신설, 자동 복구 스택 제거

자동 복구 워커 스택은 제거하고 실행 전용 스택을 새로 만든다. 기존 스택을 재정의해
재사용하는 대안보다 신설을 택한 이유는 두 가지다. 첫째, 진입 경로가 이벤트 구독에서
사용자 요청 큐로 바뀌므로 큐와 구독 구성이 사실상 전부 교체된다. 둘째, 스택 이름과
리소스 이름이 역할을 드러내야 운영자가 어떤 스택이 쓰기 권한을 갖는지 혼동하지
않는다.

교체 과정에서 기존 스택의 리소스는 삭제된다. 자동 복구는 기본 비활성 상태로 운영되어
왔으므로 진행 중인 복구 작업이 유실될 위험은 없다.

### 사용자 승인 전달 — 실행 요청 큐

대시보드가 실행 요청을 전용 큐에 발행하고, 상시 대기하는 워커가 이를 소비한다.
요청마다 태스크를 새로 기동하는 대안 대신 큐를 택한 이유는, 알람 수신 경로가 이미
같은 형태이므로 재전달·멱등성·claim 로직을 그대로 재사용할 수 있기 때문이다
([ADR infra/0006](0006-session-recovery-on-restart.md)). 실행마다 태스크를 띄우면
유휴 비용은 없지만 재시도와 중복 방지를 새로 만들어야 하고, 대시보드에 컴퓨트 기동
권한이 필요해진다.

실행 요청은 안정적인 식별자를 가지며, 중복 전달은 claim으로 걸러진다. 처리 실패한
요청은 재전달되고, 반복 실패는 별도 보관 큐로 이동한다.

### 권한 경계

실행 태스크 역할에만 쓰기 권한을 부여한다. 분석 엔진의 태스크 역할은 읽기 전용을
유지하며 어떤 변경 권한도 갖지 않는다. 두 스택은 태스크 역할을 공유하지 않는다.

실행 권한은 대상 리소스를 제한하지 않되, **파괴적 액션의 차단은 태스크 역할이 아니라
실행 도구가 수행한다.** 역할 정책으로 거부 목록을 표현하려 하면 작업 이름 어휘와
IAM 액션 이름이 일대일로 대응하지 않아 누락이 생기고, 차단 사유를 실행 증거에
기록할 수도 없다. 도구가 판정하면 차단을 증거로 남기고 해당 절차를 수동 조치로
표시할 수 있다.

역할 정책은 명백히 불필요한 범위를 제외하는 데 쓴다 — 실행 대상이 아닌 계정·조직
수준 API와 청구 관련 API는 역할에서 제외한다.

### 네트워크

실행 태스크는 대상 서비스와 AWS 제어 평면에 접근할 수 있어야 한다. 분석 엔진에
부여한 것과 달리 대상 서비스 포트로의 접근을 허용한다.

### 실행 증거 저장

실행 증거는 명령 단위로 누적되므로 세션 상태 저장소가 아니라 오브젝트 저장소를
주 보관소로 사용하고, 조회·목록에 필요한 요약만 상태 저장소에 둔다
([ADR infra/0002](0002-evidence-storage.md)). 증거는 실행이 실패해도 보존된다.

### 실행 시간

실행은 관측 대기를 포함하므로 오래 걸릴 수 있다. 상시 워커이므로 플랫폼 시간 제한은
없으나, 큐 메시지의 가시성 시간과 claim 유효 시간은 최악 실행 시간보다 길게 둔다.
그렇지 않으면 실행 중인 요청이 재전달되어 중복 실행된다.

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 기존 자동 복구 스택을 실행 스택으로 재정의 | 스택 수가 늘지 않고 네트워크·IAM 구성을 재사용한다. | 진입 경로가 전부 교체되므로 재사용되는 것이 이름뿐이다. 스택 이름이 역할을 드러내지 못해 어느 스택이 쓰기 권한을 갖는지 혼동된다. |
| 분석 엔진 태스크가 실행까지 수행 | 컨텍스트 전달이 없고 스택이 늘지 않는다. | 분석 태스크 역할에 넓은 쓰기 권한이 붙어, 읽기 전용 분석의 안전 이점이 사라진다. 엔진이 둘이므로 실행 경로도 둘이 된다. |
| 엔진별 실행 스택 | 엔진별로 실행 특성을 다르게 할 수 있다. | 안전 정책과 멱등성 로직이 복제되어 갈라진다. 엔진 비교는 분석 품질 비교이므로 실행을 나눌 이유가 없다. |
| 실행 전용 스택 + 요청 큐 | 실행 경로가 하나이고 쓰기 권한이 한 역할에 격리된다. 알람 경로의 재전달·멱등성을 재사용한다. | 상시 워커의 유휴 비용이 발생하고 스택이 하나 늘어난다. |

실행 기동 방식에 대한 대안:

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 요청마다 컴퓨트 태스크를 직접 기동 | 유휴 비용이 없다. | 재시도와 중복 방지를 새로 만들어야 하고, 대시보드에 컴퓨트 기동 권한이 필요하다. 기동 실패가 승인 사실의 유실이 된다. |
| 분석 완료 이벤트 구독 후 승인 플래그 확인 | 기존 이벤트 경로를 재사용한다. | 승인 없이도 태스크가 기동되어 승인 게이트가 코드 조건으로만 남는다. 게이트를 인프라 경계로 세우지 못한다. |
| 사용자 요청을 전용 큐로 발행 | 승인이 곧 메시지이므로 게이트가 경로 자체에 있다. 재전달·멱등성을 재사용한다. | 상시 워커의 유휴 비용이 발생한다. |

## Consequences

### Positive

- 승인 없이 실행이 기동될 경로가 인프라에 존재하지 않는다.
- 쓰기 권한이 실행 태스크 역할 하나에 격리되어 분석 경로와 분리된다.
- 실행 경로가 하나이므로 안전 정책을 한 곳에서 유지한다.
- 알람 수신 경로의 재전달·멱등성·claim 구조를 그대로 재사용한다.
- 스택 이름이 역할을 드러내 어느 스택이 쓰기 권한을 갖는지 명확하다.
- 실행 증거가 실패한 실행에서도 보존된다.

### Negative

- 상시 워커의 유휴 비용이 발생한다. 실행은 사용자 승인 시에만 일어나므로 대기
  시간이 대부분이다.
- 스택이 하나 늘어나고, 기존 자동 복구 스택 제거 시 리소스가 삭제된다.
- 대시보드가 큐 발행 권한을 가져야 한다.
- 실행 증거가 오브젝트 저장소와 상태 저장소에 나뉘어 저장되므로 조회 경로가 둘이다.

### Risks

- 실행 태스크 역할의 권한이 넓으므로 도구의 파괴성 판정이 안전의 주 의존점이 된다.
  역할 정책은 계정·조직·청구 범위만 제외하는 보조 경계로 둔다.
- 실행이 예상보다 길어지면 메시지 가시성 시간을 넘겨 재전달될 수 있다. 가시성
  시간과 claim 유효 시간을 최악 실행 시간보다 길게 두고, claim으로 중복 실행을
  차단한다.
- 대시보드의 큐 발행 권한이 노출되면 승인 없이 실행 요청을 만들 수 있다. 대시보드는
  로컬 전용 도구이며 발행 권한은 로컬 자격 증명에 종속된다.
- 자동 복구 스택 제거 시 남아 있던 미처리 메시지가 유실된다. 자동 복구는 기본
  비활성이었으므로 진행 중 작업은 없다.
