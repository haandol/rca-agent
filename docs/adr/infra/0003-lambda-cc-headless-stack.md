# ADR 0003: CC Headless 오케스트레이터 실행 인프라

Date: 2026-04-22
Updated: 2026-07-31

## Status

Accepted (2026-07-30)

## Context

CC Headless는 장시간 RCA와 전문 서브 에이전트 호출을 수행하므로 짧은 서버리스
실행보다 상시 워커가 적합하다.

이 태스크는 **분석만 수행한다.** 복구는 사용자 승인 뒤의 별도 스택이 수행하므로
([ADR infra/0008](0008-playbook-execution-stack.md)) 이 런타임에는 쓰기 도구가 없다.
경계가 역할별 도구 허용 정책이 아니라 태스크 역할의 권한 자체이므로, 한 런타임 안에서
읽기·쓰기 노출 범위를 나눌 필요도 없다.

## Decision Drivers

- 장시간 RCA와 서브 에이전트 실행에 플랫폼 타임아웃이 없어야 한다.
- 알람 전달 실패와 태스크 재시작에도 메시지가 보존되어야 한다.
- 분석 태스크는 어떤 변경 권한도 갖지 않아야 한다.
- 실행별 파일·대화·설정이 다음 알람으로 누출되지 않아야 한다.
- 로컬에서 검증한 하네스가 변형 없이 그대로 실행 단위에 실려야 한다.

## Decision

CC Headless는 전용 SQS를 Long Polling하는 단일 ECS Fargate 서비스로 운영한다.
알람마다 격리된 Claude Code 실행을 만들고 메인 에이전트가 RCA와 Report 서브
에이전트를 조정한다.

태스크에는 AWS 관측·변경 이력·코드 조회용 읽기 도구와 산출물 저장 도구만 제공한다.
**태스크 역할에는 어떤 변경 권한도 부여하지 않는다** — 복구 권한은 실행 스택의
태스크 역할에만 존재하며 두 스택은 역할을 공유하지 않는다.

대상 서비스로의 네트워크 접근도 허용하지 않는다. 분석은 관측 API로만 수행되므로
대상 서비스에 직접 연결할 이유가 없고, 연결 경로가 있으면 프롬프트 우회로 요청을
보낼 여지가 남는다.

산출물 디렉터리와 Claude 작업·홈 디렉터리는 실행마다 새로 만들고 종료 후
정리한다. wrapper는 산출물 생성을 감지하여 세션 트레이스를 기록한다. SQS 메시지는
플레이북을 포함한 필수 리포트가 저장되고 세션이 완료된 뒤에만 확인 처리한다.

### 하네스 동봉 배포

실행 단위 이미지는 엔진 코드와 하네스 자산(워크스페이스 계약, 역할 정의, 스킬,
프롬프트)을 함께 담는다. 하네스를 외부 저장소나 파라미터 스토어에서 런타임에
내려받지 않으므로, 이미지 태그 하나가 코드와 하네스 버전을 동시에 고정한다.
로컬 검증에 쓴 하네스와 배포된 하네스가 같은 커밋에서 나온다.

에이전트 실행에 필요한 런타임(Claude Code CLI, MCP 서버 실행기, 읽기 전용 MCP
서버)도 같은 이미지에 사전 설치하고, 실행 중 외부 패키지 해석에 의존하지 않는다.
프라이빗 서브넷에서 네트워크가 제한되거나 외부 레지스트리가 흔들려도 하네스가
로컬에서 검증된 구성 그대로 기동되어야 하기 때문이다. 같은 이유로 CLI와 외부
MCP 서버 버전은 이미지에서 고정한다.

하네스 자산만 바뀐 변경도 이미지 재빌드와 서비스 재배포를 거친다. 실행 중
자산을 교체하는 경로는 두지 않는다.

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 알람마다 서버리스 함수 실행 | 유휴 비용이 적고 운영 단위가 작다. | 장시간 분석과 다중 서브 에이전트 호출이 플랫폼 시간 제한에 걸릴 수 있다. |
| 분석과 복구를 같은 태스크에서 수행 (이전 결정) | 컨텍스트를 유지하며 복구를 즉시 시작할 수 있다. | 분석 태스크 역할에 쓰기 권한이 붙어, 역할별 도구 허용 정책이 유일한 경계가 된다. 프로세스 격리가 없으므로 도구 자체의 중복 검증이 필요하다. |
| 읽기 전용 단일 Fargate 분석 워커 | 태스크 역할에 변경 권한이 없어 오판이 서비스 변경으로 이어질 경로가 없다. | 복구가 별도 스택이므로 분석 컨텍스트가 리포트를 통해서만 전달된다. |

하네스와 에이전트 런타임을 실행 단위에 어떻게 공급할지에 대한 대안:

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 하네스와 런타임을 실행 시점에 외부에서 설치·조회 | 이미지가 작고 프롬프트를 재배포 없이 교체할 수 있다. | 실행 시점 구성이 로컬 검증 구성과 달라질 수 있고, 제한된 네트워크에서 외부 해석 실패가 곧 RCA 실패가 된다. |
| 하네스는 이미지에 담고 런타임은 실행 시점에 설치 | 런타임 갱신이 쉽다. | 하네스는 고정되지만 도구 계층이 흔들려 재현성이 절반만 성립한다. |
| 하네스와 런타임을 모두 이미지에 사전 설치·고정 | 로컬 검증 구성이 그대로 실행되고 태그 하나로 재현된다. | 이미지가 커지고 프롬프트만 바꿔도 재빌드·재배포가 필요하다. |

## Consequences

### Positive

- 장시간 분석을 하나의 격리 실행에서 완료할 수 있다.
- 태스크 역할에 변경 권한이 없어 분석 경로의 결함이 서비스 변경으로 이어지지 않는다.
- 대상 서비스로의 네트워크 경로가 없어 프롬프트 우회로 요청을 보낼 여지가 없다.
- 쓰기 권한이 실행 스택에만 있으므로 권한 경계가 프로세스와 역할 수준에서 성립한다.
- SQS 재전달과 ECS 자동 재시작을 이용할 수 있다.
- 이미지 태그가 코드와 하네스를 함께 고정하므로 배포 단위가 재현 가능하다.
- 외부 패키지 저장소 장애가 진행 중인 RCA 실행을 깨뜨리지 않는다.

### Negative

- 서브 에이전트와 MCP 서버를 포함한 컨테이너 이미지가 커진다.
- 하네스 자산만 바뀐 변경도 전체 이미지 빌드와 배포 주기를 거친다.
- 분석 컨텍스트가 리포트를 통해서만 실행에 전달되므로, 리포트에 담기지 않은 맥락은
  실행 시점에 재수집되어야 한다.

### Risks

- 도구 허용 정책이 잘못 구성되면 의도하지 않은 도구가 노출될 수 있다. 다만 태스크
  역할에 변경 권한이 없으므로 노출의 상한이 읽기와 산출물 저장에 머문다. 서브
  에이전트 계약 테스트로 도구 집합을 고정한다.
- 리포트 저장 실패 시 분석 결과가 유실될 수 있다. 필수 리포트 계약과 SQS 재처리로
  완화한다.
