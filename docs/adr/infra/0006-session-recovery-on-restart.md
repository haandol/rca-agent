# ADR 0006: SQS 재전달 기반 미완료 RCA 세션 복구

Date: 2026-04-23
Updated: 2026-07-31

## Status

Accepted (2026-07-31)

## Context

Codex Headless 태스크는 배포, 비정상 종료, 수동 중지 중에도 장시간 RCA를 수행할 수
있다. 처리 중인 SQS 메시지를 먼저 삭제하면 태스크 장애 후 분석을 복구할 수 없다.
반대로 재전달 메시지가 기존 진행 세션과 동시에 실행되면 복구 액션과 보고서가
중복될 수 있다.

같은 알람 이벤트는 엔진별로 안정된 세션 식별자를 사용하므로, 재전달 시 새 세션을
만드는 대신 기존 미완료 세션의 실행 소유권을 안전하게 넘겨야 한다.

## Decision Drivers

- 메시지는 전체 오케스트레이션이 성공한 뒤에만 삭제되어야 한다. 실패하거나 중단된 실행은 재전달만으로 처음부터 다시 시작할 수 있어야 한다.
- 이전 실행은 소유권을 잃은 뒤 상태, 보고서, 복구 결과를 확정할 수 없어야 한다.
- 재전달과 별도 중복 이벤트가 동시에 도착해도 한 실행만 세션을 소유해야 한다.
- heartbeat 시각에 의존한 stale 판정은 피해야 한다. 지연된 heartbeat를 장애로 오판하면 정상 실행이 탈취된다.
- 소유권 저장소 장애가 쓰기 작업 허용으로 해석되어서는 안 된다.
- 사람이 시작하는 취소와 삭제도 소유권 규칙 밖에 있어서는 안 된다. 사람의 개입이 fencing을 우회하면 워커 간 fencing만으로는 중복 실행을 막을 수 없다.

## Decision

SQS 메시지는 성공 또는 이미 완료된 중복으로 판정된 경우에만 확인 처리한다.
실패, 예외, 종료 신호로 중단된 경우에는 확인하지 않아 visibility timeout 후
재전달되게 한다.

세션은 알람 이벤트와 엔진에 대해 안정된 키를 유지한다. 각 수신은 SQS 메시지
식별자, 해당 메시지 안에서 단조 증가하는 receive count, 새로운 claim token으로
실행 소유권을 요청한다.

- 세션이 없으면 첫 수신이 소유권을 얻는다.
- 완료, 만료, 취소 상태는 최종 상태로 중복 처리한다.
- 수신됨, 분석 중, 실패 상태는 같은 SQS 메시지 식별자에서 더 큰 receive count를
  가진 재전달만 원자적으로 reclaim할 수 있다.
- 같은 알람 이벤트를 담은 별도 SQS 메시지는 receive count를 비교하지 않으며 현재
  실행의 소유권을 가져갈 수 없다.
- 같은 receive count의 별도 중복이나 조건부 갱신 경합은 실행하지 않는다.
- 모든 상태 전이와 완료 기록은 현재 claim token이 일치할 때만 허용한다.
- 실행 중 소유권이 바뀌면 이전 실행을 취소 대상으로 보고 결과 발행을 중단한다.
- 완료된 세션의 중복만 확인 처리하고, claim 경합이나 소유권 확인 실패는 확인하지
  않아 다시 전달되게 한다.

종료 신호를 받은 실행은 가능하면 실패 상태를 남기되 메시지는 확인하지 않는다.
visibility timeout은 정상 최대 실행 시간보다 길게 유지하여 정상 실행 중 불필요한
reclaim 가능성을 낮춘다.

세션 외부에 영향을 주는 복구, 보고서 저장, 알림 발행은 claim에 종속된 짧은
부작용 lease를 획득한 실행만 시작할 수 있다. 유효한 lease가 있는 동안에는
reclaim을 허용하지 않고, lease가 만료되거나 해제된 뒤에만 더 큰 receive count가
소유권을 넘겨받을 수 있다. 소유권 또는 lease 확인을 읽을 수 없으면 해당 작업은
fail-closed로 중단한다.

시도별 보고서는 claim 단위로 격리하여 이전 실행의 늦은 업로드가 현재 실행의
보고서를 덮어쓰지 못하게 한다. 실행 트레이스 쓰기는 세션 claim 확인과 같은
원자적 경계에서 수행한다. 알림과 멱등 복구처럼 외부 시스템과 원자적으로 묶을 수
없는 작업은 세션 식별자를 멱등성 키로 전달하고, 성공 확정까지 lease를 유지한다.

### 운영자 개입 — 취소와 삭제

사람이 대시보드에서 수행하는 취소와 삭제도 소유권 규칙을 따른다. 두 작업은 워커가
아니라 사람이 시작하지만, 같은 세션을 향한 또 하나의 쓰기 주체이므로 claim 밖에
두면 fencing이 사람 손으로 무력화된다.

**취소는 claim을 회전시킨다.** 상태를 취소로 바꾸는 것만으로는 부족하다. 진행 중인
실행은 자신의 claim token을 계속 들고 있으므로, 상태만 바뀌면 그 실행은 취소 이후에도
가설·트레이스를 계속 기록하고 이미 lease 안에 들어간 부작용을 완료한다. 따라서 취소는
상태 전이와 claim token 무효화를 **하나의 원자적 쓰기**로 수행하고, 그 이후 이전
claim의 모든 상태·산출물·트레이스·최종 발행 쓰기는 실패한다.

취소는 유효한 부작용 lease가 있는 동안에는 시작하지 않는다. 외부 쓰기가 이미 시작된
구간을 중간에서 끊으면 그 작업의 완료 여부를 알 수 없는 상태로 남기 때문이다. lease가
만료되거나 해제된 뒤에 취소가 성립한다.

**삭제는 최종 상태에서만 허용한다.** 활성 claim이나 유효한 lease를 가진 세션의 레코드를
지우면 fencing 기준 자체가 사라진다. 진행 중인 실행은 자기 claim이 사라진 것을 모르고
계속 진행하는 한편, 재전달된 메시지는 세션이 없다고 판단해 처음부터 새로 실행한다. 즉
삭제는 중복 실행을 막는 근거를 제거하는 작업이다. 따라서 세션이 최종 상태이고 유효한
lease가 없을 때만 삭제하고, 그 밖의 경우는 거부해 사람이 먼저 취소하도록 한다.

삭제 후 같은 알람의 메시지가 메시지 보관 기간 안에 재전달되면 세션이 다시 생성된다.
이는 삭제가 알람 이벤트 자체를 취소하지 않기 때문이며, 재생성된 세션은 새 실행으로
처리한다. 삭제를 재생성 금지로 확장하려면 별도의 묘비 레코드가 필요하므로, 현재
결정에서는 재생성을 허용하고 삭제를 "지금 보관된 기록의 제거"로만 정의한다.

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 처리 시작 즉시 메시지 삭제 | 중복 실행 가능성이 낮고 구현이 단순하다. | 태스크 장애 시 복구할 입력이 사라진다. |
| heartbeat와 stale 세션 스캔 | 메시지 재전달 전에 복구를 시작할 수 있다. | 지연된 heartbeat를 장애로 오판할 수 있고 별도 스캐너가 필요하다. |
| SQS 재전달 + 세션 claim | SQS의 전달 상태를 복구 신호로 사용하면서 조건부 소유권으로 중복을 막는다. | 재시도는 visibility timeout만큼 늦어지고 처음부터 분석을 반복한다. |
| 세션 claim + 부작용 lease | 장시간 분석의 reclaim을 유지하면서 외부 쓰기 시작 구간까지 소유권을 확장한다. | lease 만료와 외부 호출 제한 시간을 함께 관리해야 하고 외부 소비자의 멱등성이 필요하다. |

운영자 개입의 처리 방식에 대한 대안:

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 취소는 상태만 변경 | 구현이 단순하고 취소가 즉시 응답한다. | 진행 중인 실행이 claim을 유지하므로 취소 이후에도 가설·트레이스를 기록하고 부작용을 완료한다. 취소가 표시일 뿐 중단이 아니다. |
| 취소가 claim을 회전 | 이후 이전 claim의 모든 쓰기가 저장소 조건에서 실패하므로 취소가 실제 중단이 된다. | 진행 중 실행은 다음 쓰기 시점에야 취소를 인지하므로 즉시 멈추지 않고, 유효한 lease가 있으면 취소가 지연된다. |
| 상태와 무관하게 삭제 허용 | 운영자가 어떤 세션이든 정리할 수 있다. | 활성 claim·lease를 지워 fencing 기준을 없앤다. 진행 중 실행과 재전달이 동시에 진행되어 중복 실행이 된다. |
| 최종 상태 + lease 없음일 때만 삭제 | 삭제가 fencing 기준을 없애지 못한다. | 진행 중 세션은 먼저 취소해야 하므로 정리가 2단계가 되고, 보관 기간 안의 재전달로 세션이 재생성될 수 있다. |
| 삭제 시 묘비 레코드로 재생성 금지 | 삭제가 재전달에 대해서도 최종적이다. | 묘비의 보관 기간을 메시지 보관 기간과 맞춰 관리해야 하고, 삭제가 "기록 제거"를 넘어 알람 무시 정책이 된다. 현재 필요 범위를 넘는다. |

## Consequences

### Positive

- 태스크 장애와 배포 중단 후에도 원본 메시지로 자동 재시도한다.
- claim을 잃은 실행이 늦게 완료되어 결과를 덮어쓰는 것을 차단한다.
- reclaim과 외부 쓰기가 겹치는 구간을 부작용 lease로 차단한다.
- 별도 heartbeat나 세션 스캐너 없이 다중 태스크 경합을 제어한다.
- 취소가 표시가 아니라 실제 중단이 되어, 취소 이후의 늦은 산출물이 기록되지 않는다.
- 삭제가 fencing 기준을 제거하지 못하므로 삭제와 재전달이 겹쳐 중복 실행되지 않는다.

### Negative

- 재처리는 visibility timeout 이후 시작된다.
- 중간 분석 상태를 이어가지 않고 처음부터 재실행한다.
- 동일 세션의 이전 시도 기록 일부는 reclaim 시 최신 시도로 대체된다.
- lease 중 프로세스가 종료되면 만료 전까지 reclaim이 지연된다.
- 같은 알람의 별도 중복 메시지는 현재 메시지가 완료될 때까지 확인 처리되지 않아
  추가 수신과 큐 비용이 발생할 수 있다.
- 진행 중 세션의 삭제는 거부되므로 운영자는 취소 후 삭제라는 2단계를 거친다.
- 유효한 부작용 lease가 있는 동안에는 취소가 거부되어 즉시 중단되지 않는다.
- 취소된 세션의 삭제 후에도 메시지 보관 기간 안의 재전달로 세션이 재생성될 수 있다.

### Risks

- visibility timeout이 최대 실행 시간보다 짧으면 정상 실행 중 reclaim이 발생할 수
  있다. 실행 제한과 큐 timeout을 함께 관리하고 claim token으로 이전 실행의 확정을
  차단한다.
- 알림 발행 후 완료 상태 기록이 실패하면 재시도에서 알림이 중복될 수 있다.
  소비자는 세션 식별자를 멱등성 키로 사용해야 한다.
- 외부 호출이 lease보다 오래 지속되면 fencing이 약해질 수 있다. 외부 호출 제한
  시간보다 긴 lease를 사용하고 만료 전에는 reclaim을 차단한다.
- 취소는 진행 중 실행을 즉시 종료시키지 않고 다음 쓰기 시점에 차단한다. 그 사이의
  읽기 전용 조회는 계속되므로, 취소의 의미는 "이후 확정 금지"이며 "즉시 정지"가
  아니다.
