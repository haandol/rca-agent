# ADR 0002: 증거 저장 — S3 + S3 Vectors + DynamoDB 기반 증거 아카이브

Date: 2026-04-21
Updated: 2026-07-30

## Status

Accepted (2026-07-30)

## Context

RCA 과정에서 수집된 증거(메트릭, 로그, 트레이스, 배포 이력, 코드 diff)와 가설 트리 상태를 체계적으로 저장하고, 향후 유사 장애 분석 시 과거 증거를 유사도 검색으로 빠르게 참조할 수 있어야 한다.

플레이북 실행이 도입되면서 저장해야 하는 증거가 한 종류 늘었다. **실행 증거**는 명령 단위로 누적되며, 어떤 명령이 어떤 인자로 실패하고 무엇으로 교정되었는지를 담는다([ADR agent/0017](../agent/0017-playbook-execution-agent.md)). 이 증거는 회고가 플레이북을 교정하는 유일한 입력이므로 실행이 실패해도 보존되어야 한다.

회고는 갱신 근거를 사람이 대조할 수 있어야 하므로([ADR agent/0018](../agent/0018-playbook-retrospective.md)) **실행 전 플레이북 사본**도 보존해야 한다. 갱신이 원본을 덮어쓰므로 사후에 복원할 수 없다.

## Decision Drivers

- 수집된 증거 원본은 변경 없이 보존되어야 한다. 사후 검증에서 요약이 아닌 원본을 봐야 하는 경우가 있다.
- 과거 경험을 유사도로 검색할 수 있어야 한다([ADR agent/0001](../agent/0001-initial-scoping-and-report-similarity.md)).
- 가설 트리의 상태 변화를 실시간으로 조회할 수 있어야 한다. 대시보드가 진행 중인 분석을 보여주기 때문이다.
- 증거는 무기한 축적되어서는 안 된다. 보존 기간 후 자동 정리되어야 한다.
- 증거 저장 실패가 RCA 분석을 중단시켜서는 안 된다.
- 실행 증거는 실행이 실패해도 보존되어야 한다. 회고의 유일한 입력이기 때문이다.
- 회고의 갱신 근거를 대조할 수 있도록 갱신 전 플레이북이 보존되어야 한다.

## Decision

**S3(원본 저장) + S3 Vectors(벡터 검색) + DynamoDB(상태 관리)** 3계층 저장 전략을 채택한다.

### 저장 구조

```mermaid
flowchart TD
    Evidence["수집된 증거\n(메트릭/로그/트레이스/배포이력/코드diff)"] --> S3["S3\n원본 JSON 저장"]
    Evidence --> Embed["임베딩 모델\n증거 요약 임베딩"]
    Embed --> SV["S3 Vectors\n벡터 검색용 임베딩"]
    HypTree["가설 트리 상태"] --> DDB["DynamoDB\n실시간 상태 관리"]
    S3 --> DDB
    SV --> DDB
```

### 핵심 결정사항

1. **RCA·가설 단위로 분할된 저장 경로**: 증거 원본은 RCA 식별자와 가설 식별자로 구분된 경로에 저장한다. 가설별로 경로가 갈라지므로 특정 가설의 증거만 조회하거나 정리할 수 있고, 가설별 컨텍스트 격리와 저장 구조가 일치한다([ADR agent/0014](../agent/0014-hierarchical-evidence-session-isolation.md)).

2. **벡터 인덱스는 경량 메타데이터만 보유**: 증거 요약을 임베딩해 벡터 인덱스에 저장하되, 인덱스 메타데이터에는 크기 제한이 있어 검색·판별에 필요한 최소 필드만 담는다. 상세는 상태 저장소에서 식별자로 조회한다. 같은 상세를 두 저장소에 중복 저장하면 갱신 시 어긋나므로, 인덱스는 "무엇을 찾을지"만 알고 "무엇인지"는 저장소가 갖는다([ADR agent/0008](../agent/0008-playbook-generation.md)).

3. **가설 트리 상태를 RCA 단위 파티션에 저장**: RCA 식별자로 파티션하고 가설 식별자로 정렬해, 한 RCA의 가설 전체를 단일 조회로 읽는다. 부모 참조와 깊이를 함께 기록해 트리 구조를 복원할 수 있게 한다.

4. **증거 보존 정책**: 증거 원본은 RCA 완료 기준 **60일** 보존 후 자동 삭제한다. 가설 트리 상태는 **90일** 보존한다. 상태를 원본보다 오래 두는 이유는, 원본이 정리된 뒤에도 어떤 가설이 어떤 판정을 받았는지는 조회 가치가 남기 때문이다.

5. **증거 접근 감사**: 증거 저장·조회 행위는 클라우드 감사 로그에 기록된다. 증거에는 운영 로그와 코드가 포함되므로 누가 언제 접근했는지 추적 가능해야 한다.

6. **저장 실패의 비차단 처리**: 벡터 인덱싱이 실패해도 증거 원본 저장은 완료하고 인덱싱만 재시도한다. 검색 가능성은 편의이고 원본 보존은 계약이므로, 둘의 실패 처리를 다르게 둔다.

7. **실행 증거는 원본 계층에, 요약만 상태 계층에**: 실행 증거는 명령 단위로 누적되어 크기가 예측되지 않으므로 오브젝트 저장소를 주 보관소로 쓴다. 상태 저장소에는 목록·조회에 필요한 요약(실행 상태, 시도한 절차 수, 차단·실패 건수)만 둔다. 전체 증거를 상태 저장소에 담으면 항목 크기 한도에 걸리고, 반대로 요약까지 오브젝트 저장소에만 두면 목록 화면이 매 항목마다 오브젝트를 읽어야 한다.

8. **실행 증거는 실행 단위로 append 되고 실패해도 보존한다**: 실행 증거는 실행 식별자로 구분된 경로에 시도 순서대로 누적한다. 같은 리포트를 여러 번 실행할 수 있으므로 경로는 리포트가 아니라 실행 단위로 갈라진다. 실행이 실패·미해결로 끝나도 증거는 지우지 않는다 — 자동 회고의 입력은 아니지만 사람이 원인을 읽는 유일한 자료다.

9. **회고는 갱신 전 플레이북 사본을 함께 보존한다**: 회고가 플레이북을 갱신할 때 갱신 전 내용을 실행 단위로 보존한다. 이 사본이 없으면 갱신 diff의 기준이 사라져 회고 결과의 타당성을 판단할 수 없다([ADR agent/0018](../agent/0018-playbook-retrospective.md)).

10. **실행 증거 보존 정책**: 실행 증거와 갱신 전 플레이북 사본은 증거 원본과 같은 **60일** 보존을 적용한다. 실행 상태 요약은 가설 트리 상태와 같은 **90일** 보존한다. 실행 증거가 정리된 뒤에도 어떤 실행이 어떤 결과로 끝났는지는 조회 가치가 남는다.

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 단일 저장소(관계형 DB)에 모두 저장 | 저장소가 하나라 일관성 관리가 쉽고 조인 질의가 가능하다. | 증거 원본이 수십 KB~MB 규모여서 행 크기와 비용이 급증하고, 유사도 검색을 위한 벡터 인덱스가 없어 과거 경험 검색이 성립하지 않는다. |
| 원본과 상태를 모두 오브젝트 스토리지에 저장 | 저장 비용이 가장 낮다. | 진행 중 분석의 상태를 실시간 조회·갱신할 수 없어 대시보드가 성립하지 않고, 조건부 갱신으로 동시성을 제어할 수 없다. |
| 벡터 인덱스에 상세까지 함께 저장 | 검색 한 번으로 상세를 얻어 조회 홉이 줄어든다. | 메타데이터 크기 제한을 넘고, 같은 상세가 두 저장소에 존재해 갱신 시 어긋난다. |
| 원본·벡터·상태 3계층 분리 | 각 접근 패턴(보존, 검색, 실시간 갱신)에 맞는 저장소를 쓴다. | 저장소가 셋이라 인프라 복잡도와 정합성 관리 부담이 늘어난다. |

## Consequences

### Positive

- 3계층 분리로 원본 보존, 벡터 검색, 실시간 상태 관리를 각각 최적화
- 벡터 인덱싱으로 과거 증거·보고서를 유사도 검색해 현재 RCA에 참조 가능
- RCA·가설 단위 경로로 증거 접근과 선택적 정리가 용이
- 수명주기 정책으로 비용 효율적인 보존 정책 적용
- 실행 증거가 실패한 실행에서도 보존되어 사람이 원인을 읽을 수 있다
- 갱신 전 플레이북 사본이 남아 회고 결과의 타당성을 대조할 수 있다

### Negative

- 3개 저장소 관리로 인프라 복잡도 증가
- 임베딩 비용이 증거 수량에 비례하여 발생
- 상세 조회에 저장소 홉이 하나 더 필요하다 (벡터 검색 → 상태 저장소)
- 상태 저장소 쓰로틀링 시 상태 업데이트 지연 가능
- 실행 증거와 갱신 전 사본이 실행마다 누적되어 저장량이 실행 횟수에 비례한다
- 실행 상세 조회가 상태 계층의 요약과 원본 계층의 증거 두 경로로 나뉜다

### Risks

- 증거 저장 실패가 RCA 흐름을 막을 수 있다. 재시도 후에도 실패하면 "저장 실패"를 메타데이터로만 기록하고 분석을 계속한다.
- 동시 다수 RCA 실행 시 상태 저장소 쓰로틀링이 발생할 수 있다. 온디맨드 용량 모드로 완화한다.
- 원본 보존 60일이 지난 뒤 그 RCA에서 파생된 플레이북 상세를 로드할 수 없어 같은 유형의 플레이북이 새로 생성될 수 있다([ADR agent/0008](../agent/0008-playbook-generation.md)).
- 실행 증거 저장이 실패하면 회고의 입력이 사라진다. 증거 저장 실패는 실행 실패로 처리하지 않되, 회고는 입력 부족으로 실패시켜 잘못된 갱신보다 미갱신을 택한다.
- 실행 증거에 명령과 인자가 담기므로 자격 증명이 인자로 전달되면 증거에 남는다. 증거 접근은 감사 로그에 기록되며, 실행 도구는 인자를 기록할 때 자격 증명으로 보이는 값을 가린다.
