# ADR 0009: 멀티 계정 RCA — 허브·스포크 역할 위임과 계정별 유입 제한

Date: 2026-08-07

## Status

Proposed

## Context

현재 시스템은 배포된 계정 하나만 분석하고 실행할 수 있다. 세 곳이 계정 경계를 못박고
있다.

첫째, **알람 유입이 배포 계정으로 제한된다.** 알람 입력 토픽은 발행 요청이 이 배포의
계정에서 시작되고 이 배포가 만든 알람에서 왔다는 것을 함께 요구한다
([ADR 0001](0001-alarm-ingestion-sns-sqs-fargate.md)). 이 조건은 인증 없는 진입점의
유일한 비용 경계이므로 그냥 넓힐 수 없다.

둘째, **증거 수집 권한이 태스크 역할에 직접 붙어 있다.** 분석 워커의 태스크 역할이
관측 읽기 권한을 보유하므로, 조회 범위가 배포 계정으로 고정된다.

셋째, **실행 권한도 태스크 역할에 직접 붙어 있다.** 실행 태스크 역할이 넓은 쓰기
권한을 보유하며([ADR 0008](0008-playbook-execution-stack.md)) 다른 계정으로 조치를
전달할 경로가 없다.

동시에 도메인 모델에 계정 차원이 없다. 알람 봉투는 ARN에서 리전만 취하고 계정을
버리며, 세션 상태와 실행 요청 어디에도 대상 계정이 없다. 따라서 여러 계정을 다루려면
권한 위임만으로는 부족하고 **대상 좌표가 세션·리포트·실행·플레이북을 관통해야 한다.**

운영 조직은 워크로드를 계정으로 분리하지만 장애 대응 인력과 RCA 지식은 분리하지
않는다. 계정마다 전체 시스템을 배포하면 축적된 플레이북이 계정별로 갈라져, 같은
워크로드의 같은 장애를 계정마다 처음부터 다시 분석한다.

## Decision Drivers

- 여러 계정의 알람을 한 곳에서 분석하고, 분석 결과와 플레이북을 한 곳에 축적해야 한다.
- 알람 유입을 조직 밖으로 열지 않으면서 조직 안의 여러 계정에 열어야 한다.
- 한 계정의 알람 폭주가 다른 계정의 알람 대응을 굶기거나 모델 비용을 무제한으로
  소모해서는 안 된다.
- 대상 계정을 조회하거나 변경하는 권한이 워커의 태스크 역할에 상주해서는 안 된다.
- 분석의 읽기 전용 성질과 실행의 쓰기 권한이 계정 경계를 넘어서도 갈라져 있어야 한다.
- 사람이 승인한 실행이 승인하지 않은 계정에서 일어나서는 안 된다.
- 대상 계정에 배포해야 하는 것이 적어야 한다. 스포크 배포가 무거우면 계정 편입 자체가
  병목이 된다.

## Decision

**단일 허브에 분석·실행·저장·조회를 모두 두고, 대상 계정(스포크)에는 위임 역할과
알람 전달 규칙만 배포한다.** 워커는 대상 계정의 역할을 위임받아 조회·변경하며, 어떤
대상 계정 권한도 워커의 태스크 역할에 상주하지 않는다.

### 대상 좌표 — 계정과 리전

분석과 실행의 대상은 **계정과 리전의 조합**으로 식별한다. 계정만으로는 부족하다 —
같은 계정의 여러 리전에 같은 이름의 리소스가 있을 수 있고, 관측 데이터는 리전에
종속된다.

대상 좌표는 알람 봉투에서 확정하며, 이후 세션·리포트·플레이북·실행 요청·실행 증거가
모두 이 좌표를 보유한다. 좌표를 확정할 수 없는 알람은 세션을 만들지 않는다 — 어느
계정을 조사하는지 모르는 분석은 증거를 수집할 대상이 없다.

### 알람 유입 — 조직 경계 + 계정 등록

알람 유입 경로를 스포크의 이벤트 규칙 → 허브의 전용 이벤트 버스로 바꾸고, 허브가 이를
기존 알람 입력 토픽으로 전달한다.

발행 자격의 판단 기준은 여전히 요청의 출처다([ADR 0001](0001-alarm-ingestion-sns-sqs-fargate.md)).
바뀌는 것은 그 출처의 범위다.

- 이벤트 버스 정책은 **이 조직에 속한 주체만** 전달 자격을 갖도록 요구한다. 서비스
  주체만 허용하면 조직 밖 계정이 다시 발행 자격을 갖는다.
- 조직 소속은 필요 조건이고 충분 조건이 아니다. 조직에 속한 계정이라도 **레지스트리에
  등록되지 않은 계정의 알람은 세션을 만들지 않는다.** 조직 소속만으로 열면 등록 절차
  없이 편입된 계정이 모델 비용을 소모한다.
- 등록 여부 판정은 소비 시점에 일어난다. 계정 편입·제외가 인프라 정책 갱신이 아니라
  레지스트리 데이터 변경이어야 하기 때문이다. 조직 경계는 정책이 막고, 계정 단위
  허용은 데이터가 막는다.

알람 봉투의 형식이 둘로 늘어난다. 기존 알림 형식과 이벤트 형식은 필드 이름과 중첩
구조가 다르므로, 두 형식을 하나의 정규화된 알람 봉투로 해석하는 단일 진입점을 둔다.
정규화된 봉투는 대상 좌표를 필수 필드로 보유한다.

이벤트 경로를 택한 이유는 봉투가 **출처 계정을 위조 불가능한 형태로** 담기 때문이다.
알림 본문의 계정 필드는 발행자가 채우므로 신뢰할 수 없고, 알람 ARN에서 계정을 뽑는
방식은 ARN이 본문의 일부라는 같은 문제를 갖는다.

### 권한 위임 — 스포크 역할 두 개

각 대상 계정에 역할 두 개를 배포한다.

- **조회 역할**: 관측·구성 조회 권한만 갖는다. 어떤 변경 권한도 갖지 않는다.
- **실행 역할**: 넓은 쓰기 권한을 갖는다. 계정·조직·청구·자격 증명 범위는 제외한다
  ([ADR 0008](0008-playbook-execution-stack.md)의 제외 범위를 그대로 스포크로 옮긴다).

두 역할은 각각 허브의 분석 워커 역할과 실행 워커 역할만 신뢰한다. 하나의 역할에 조회와
실행을 합치지 않는다 — 분석 경로의 결함이 쓰기 권한에 닿지 않게 한 경계가 계정을 넘어
무너지면 안 된다.

파괴적 액션의 차단은 계정을 넘어서도 **실행 도구가 수행한다.** 스포크 역할 정책은
명백히 실행 대상이 아닌 범위만 제외하는 보조 경계로 둔다. 정책으로 거부 목록을
표현하려는 시도가 왜 실패하는지는 이전 결정과 같다.

실행 역할이 없는 계정은 **분석만 가능한 계정**이다. 계정 편입이 곧 실행 허용이 되어서는
안 되므로, 실행 허용은 레지스트리의 별도 항목으로 표시하고 조회 역할과 독립적으로
운영한다.

### 승인은 대상 계정을 허가한다

실행 승인은 사람이 읽은 플레이북 내용을 허가하며([ADR agent/0017](../agent/0017-playbook-execution-agent.md)),
여기에 **대상 좌표를 더한다.** 실행 요청은 대상 계정과 리전을 필수로 담고, 그 좌표는
승인 스냅샷 digest의 계산 범위에 포함된다.

좌표를 digest 범위 밖에 두면 한 계정의 리포트로 받은 승인을 다른 계정에 실행하는
경로가 열린다. 실행 워커는 요청의 좌표가 승인 예약의 좌표와 같은지 검증하고, 다르면
실행하지 않는다.

실행 워커는 레지스트리에서 실행이 허용되지 않은 계정의 요청을 실행하지 않는다. 승인이
있어도 계정 수준 허용이 없으면 실행은 성립하지 않는다.

### 계정별 유입 상한

허브의 워커는 계정 수를 늘려도 하나이므로, 큐가 계정 간 공유 자원이 된다. 한 계정의
알람 폭주가 다른 계정의 알람을 큐 뒤로 밀어내는 것을 막아야 한다.

- **계정별 동시 진행 분석 세션은 1건이다.** 같은 계정의 장애는 연쇄적으로 여러 알람을
  만들고 그 알람들은 같은 근본 원인일 가능성이 높다. 동시에 여러 세션을 만들면 같은
  원인을 중복 분석하면서 다른 계정의 알람을 굶긴다. 진행 중 세션이 있는 계정의 새
  알람은 세션을 만들지 않고 기각한다.
- **계정별 일일 분석 세션 상한은 20건이다.** 근거는 허브 워커의 하루 처리 용량이다.
  분석 1건의 평균 소요를 10분으로 보면 20건은 약 3.3시간이고, 등록 계정 6개가 각각
  상한까지 소비하면 약 20시간으로 하루 용량에 근접한다. 상한을 넘은 알람은 세션을
  만들지 않고 기각한다.
- **계정별 동시 진행 실행은 1건이다.** RCA 단위 활성 실행 표식은 같은 리포트의 중복
  실행만 막으므로, 같은 계정에 서로 다른 리포트의 실행이 동시에 들어가는 것을 막지
  못한다. 한 계정에 동시 조치가 겹치면 어느 조치가 관측 변화를 만들었는지 판정할 수
  없다.
- 기각은 유실이 아니다. 기각 사유와 대상 좌표를 남겨 사람이 왜 분석되지 않았는지 알 수
  있어야 한다.

일일 상한의 기준 시각은 UTC 자정이다. 계정별 지역 시간을 쓰면 상한이 언제 초기화되는지
계정마다 달라져 운영자가 예측할 수 없다.

### 플레이북 검색 경계

축적된 플레이북은 **같은 환경 등급의 계정끼리 공유하고, 등급을 넘지 않는다.** 등급은
레지스트리가 계정마다 보유한다.

계정 경계로 검색을 막으면 같은 워크로드가 여러 계정에 배포된 조직에서 이 시스템의 가장
큰 이점이 사라진다. 반대로 등급을 넘어 공유하면 검증 환경에서만 통한 절차가 운영
계정의 대응 근거로 제시되거나, 운영 규모를 전제한 절차가 검증 환경에 제시된다. 검증
상태는 그 절차가 통한 환경에 종속된다.

### 키 설계

계정 차원은 새 저장소를 만들지 않고 기존 세션 테이블에 흡수한다. 유입 판정이 세션 생성과
같은 조건부 쓰기 안에서 일어나야 하므로, 레지스트리와 상한 카운터를 다른 저장소에 두면
판정과 생성 사이가 원자적이지 않게 된다.

- **레지스트리**: 계정 단위 파티션에 등록 항목 하나. 별칭, 환경 등급, 조회 역할 참조,
  실행 허용 여부, 실행 역할 참조를 보유한다.
- **상한 카운터**: 같은 계정 파티션에 날짜 단위 항목. 조건부 증분으로 상한을 넘기지
  않으며, 날짜가 지난 항목은 자동 만료한다.
- **활성 표식**: 같은 계정 파티션에 분석용·실행용 표식 각각 하나. 조건부 생성이
  동시 진행 1건을 보장한다.
- **세션 항목**: 대상 좌표를 속성으로 보유한다. 파티션 키는 RCA 식별자를 유지한다 —
  계정을 파티션에 넣으면 RCA 식별자만 아는 모든 조회 경로가 계정을 함께 알아야 한다.
- **세션 목록 인덱스**: 계정 필터는 엔진 축 안에서 걸린다. 엔진과 계정을 함께 파티션
  키로 갖는 인덱스를 두고 생성 시각으로 정렬한다. 계정만으로 파티션하면 엔진 비교
  화면이 엔진마다 따로 조회해 병합해야 한다. 기존 엔진 축 목록 인덱스는 전체 계정을
  보는 경로로 유지한다.

## 대안 검토

| 대안                                                | 장점                                                                                 | 단점 및 미채택 이유                                                                                                                                                                |
| --------------------------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 계정마다 전체 시스템 배포, 조회 화면만 집계         | 데이터와 권한이 계정 안에 완전히 격리되고 위임이 없다.                               | 플레이북과 유사도 인덱스가 계정별로 갈라져 같은 워크로드의 같은 장애를 계정마다 처음부터 분석한다. 이미지·시크릿·상태 저장소·워커가 계정 수만큼 늘어 편입 비용이 배포 비용이 된다. |
| 허브 집중 + 대상 계정 역할 위임                     | 스포크에 역할과 전달 규칙만 배포하므로 편입이 가볍고, 플레이북이 전 계정에 누적된다. | 위임 자격 증명이 워커 안에서 세션마다 갈려야 하고, 허브의 워커가 계정 간 공유 자원이 되어 상한이 필요하다.                                                                         |
| 관측 데이터만 크로스 계정 관측 기능으로 통합        | 위임이 없고 구성이 가장 가볍다.                                                      | 감사 이력과 리소스 구성 조회를 포함하지 못해 증거 수집이 반쪽이 되고, 실행 경로는 전혀 해결되지 않는다. 보완재이지 대안이 아니다.                                                  |
| 대상 계정에 수집 에이전트를 두고 결과만 허브로 전송 | 대상 계정 권한이 허브로 위임되지 않는다.                                             | 수집 대상이 가설에 따라 달라지므로 에이전트가 대상 계정에서 모델을 호출해야 하고, 결국 계정마다 분석 주체를 배포하는 첫 번째 대안이 된다.                                          |

알람 유입 경로의 대안:

| 대안                                          | 장점                                                                          | 단점 및 미채택 이유                                                                                                                 |
| --------------------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 기존 알림 토픽의 계정 조건을 조직 전체로 확장 | 파이프라인의 봉투 형식이 바뀌지 않는다.                                       | 봉투의 계정 필드가 발행자가 채우는 값이므로 대상 좌표를 신뢰할 수 없고, 등록되지 않은 조직 계정을 걸러낼 지점이 소비 시점뿐이 된다. |
| 스포크마다 허브 토픽으로 직접 발행            | 계층이 늘지 않는다.                                                           | 스포크의 알람 리소스 이름 규칙이 허브 토픽 정책에 들어가 계정 편입마다 정책을 갱신해야 한다.                                        |
| 스포크 이벤트 규칙 → 허브 이벤트 버스         | 봉투가 출처 계정을 위조 불가능하게 담고, 정책이 조직 경계로 한 번만 표현된다. | 봉투 형식이 기존과 달라 정규화 계층이 필요하고, 전달 홉이 하나 늘어난다.                                                            |

## Consequences

### Positive

- 여러 계정의 알람을 한 곳에서 분석하고 플레이북을 한 곳에 축적한다.
- 계정 편입이 스포크 역할·전달 규칙 배포와 레지스트리 등록으로 끝난다.
- 대상 계정 권한이 워커의 태스크 역할에 상주하지 않아, 워커 침해가 곧 대상 계정 권한
  획득이 되지 않는다.
- 분석의 읽기 전용과 실행의 쓰기 권한이 계정을 넘어서도 다른 역할로 갈려 있다.
- 계정 편입·제외가 인프라 배포가 아니라 데이터 변경이다.
- 계정별 상한으로 한 계정의 폭주가 다른 계정의 대응과 모델 비용에 번지지 않는다.
- 승인이 대상 좌표를 허가하므로 계정 간 오실행 경로가 닫힌다.

### Negative

- 대상 좌표가 세션·리포트·플레이북·실행 요청·실행 증거를 관통하므로 기존 저장 항목에는
  좌표가 없다. 좌표 없는 기존 항목은 배포 계정의 것으로 해석해야 한다.
- 봉투 형식이 둘로 늘어 정규화 계층이 유지 대상이 된다.
- 위임 자격 증명이 세션마다 갈려야 하므로, 도구 자격 증명을 컨테이너 수명으로 캐시할 수
  없다([ADR tools/0006](../tools/0006-cross-account-tool-credentials.md)).
- 계정별 동시 1건 제약으로 같은 계정의 서로 다른 원인의 동시 장애가 순차 분석된다.
- 상한 기각이 발생하므로 모든 알람이 분석되지 않고, 운영자가 기각 목록을 읽는 경로가
  하나 늘어난다.
- 스포크 역할의 신뢰 정책이 허브 워커 역할을 참조하므로, 허브 워커 역할을 재생성하면
  모든 스포크의 신뢰 정책이 어긋난다.

### Risks

- 위임 자격 증명이 최악 실행 시간보다 짧게 만료되면 세션 중간에 조회·실행이 실패한다.
  자격 증명은 자동 갱신되는 형태로만 도구에 전달한다([ADR tools/0006](../tools/0006-cross-account-tool-credentials.md)).
- 조직 경계 정책만 통과하고 레지스트리에 없는 계정의 알람이 큐에 도달한다. 큐 비용과
  기각 처리 비용은 발생하지만 세션과 모델 호출은 일어나지 않는다.
- 스포크 실행 역할의 권한이 넓으므로 도구의 파괴성 판정이 계정을 넘어서도 안전의 주
  의존점이다. 실행 허용 계정을 레지스트리로 좁혀 노출면을 줄인다.
- 계정별 일일 상한이 실제 알람량과 맞지 않으면 정상 장애가 기각되거나 상한이 무의미해
  진다. 기각 사유가 기록되므로 상한 조정의 근거를 실측으로 확보한다.
- 플레이북 검색이 같은 등급의 다른 계정 절차를 제시하므로, 계정마다 다른 리소스 이름이
  절차에 남아 있으면 실행이 없는 대상을 조치하려 한다. 실행 도구가 대상 부재를 실패로
  기록하고 회고가 절차를 교정하는 경로로 흡수한다.
- 허브의 단일 워커가 계정 수 증가의 병목이 된다. 상한이 용량을 초과하는 유입을 막지만
  용량 자체를 늘리지는 않으므로, 계정 수가 늘면 워커 확장을 별도로 결정해야 한다.
