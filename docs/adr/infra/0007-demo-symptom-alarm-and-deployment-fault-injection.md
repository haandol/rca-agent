# ADR 0007: 데모 시나리오 — 증상 기반 알람과 배포 기반 장애 주입

Date: 2026-07-29

## Status

Accepted (2026-07-29)

## Context

Healthcare 데모 환경은 RCA 시스템의 근본원인분석 능력을 보여주기 위해 존재한다.
그런데 현재 데모 구성은 분석 능력을 시연하지 못하고 우회하게 만든다.

1. **알람이 원인을 이미 말해준다.** 장애 유형과 알람이 1:1로 대응하고 알람 이름에
   원인이 그대로 드러난다. CPU 부하를 주입하면 CPU 알람이 뜬다. 에이전트는 가설을
   세우고 증거로 검증하는 과정 없이 알람 이름을 읽는 것만으로 정답에 도달할 수 있고,
   관측자는 결과가 추론의 산물인지 동어반복인지 구별할 수 없다.
2. **경쟁 가설을 반증할 데이터가 없다.** 배경 트래픽은 항상 일정하고 무관한 변경
   이벤트가 존재하지 않는다. "트래픽 급증이 아니다", "이 배포가 원인이 아니다"라는
   기각은 반증 증거에 근거하지 않고 데이터의 부재에 근거한다. 기각 능력이 시연되지
   않는다.
3. **장애 주입이 인프라 이벤트를 남기지 않는다.** 장애는 대상 서비스에 대한 직접
   API 호출로 발생하므로 변경 이력 조회로 발견할 수 있는 흔적이 없다. 배포 이력과
   코드 변경을 근거로 원인을 좁히는 것이 제품이 내세우는 핵심 역량인데, 데모에서는
   그 경로에 조회할 대상이 없다.
4. **도메인 영향이 관측되지 않는다.** 수집 가능한 지표는 데이터베이스 커넥션 수와
   컨테이너 자원 사용률뿐이다. 환자 바이탈 수집이 실패하고 이상치 알림이 지연되는
   비즈니스 영향은 어떤 지표에도 나타나지 않는다. 인시던트를 사람이 실제로 인지하는
   방식(증상)과 데모의 진입점(원인 지표)이 다르다.

결과적으로 데모는 "장애를 주입하면 그 장애에 대한 알람이 뜨고 에이전트가 그 알람의
이름을 보고서에 옮겨 적는다"에 가깝다. 제품 요구사항이 규정한 플래그십 시나리오
(증상 인지 → 가설 생성 → 배포 이력과 코드 변경으로 원인 특정 → 복구와 롤백 권고)는
현재 인프라에서 재현할 수 없다.

## Decision Drivers

- 알람은 증상을 전달해야 하고 원인을 전달해서는 안 된다. 에이전트가 알람 메타데이터만
  읽고 근본원인에 도달할 수 있으면 분석 능력을 측정할 수 없다.
- 기각된 가설마다 그것을 기각시킨 관측 데이터가 존재해야 한다.
- 배포 이력 조회와 코드 변경 분석이 실제로 결론에 기여해야 한다. 조회 대상이 없는
  도구는 데모에서 장식이다.
- 장애의 인과 사슬은 실제 시스템에서 성립해야 한다. 시연을 위해 증거를 조작하거나
  사후에 주입하지 않는다.
- 복구 안전 정책은 약화되지 않아야 한다. 알람이 증상 지표로 바뀌어도 자동 복구는
  확정된 원인과 대상 리소스를 서버 측에서 검증한 뒤에만 실행된다.
- 데모 환경의 변경이 저장소 커밋 이력을 오염시키지 않아야 한다.

## Decision

데모 시나리오를 **증상에서 시작해 배포로 수렴하는 단일 플래그십 시나리오**로
재구성한다. 구성 요소는 네 가지다.

### 1. 도메인 증상 지표와 증상 알람

Healthcare 서비스가 자신의 도메인 관점 지표를 발행한다. 바이탈 수집 실패와 이상치
알림 지연을 지표로 노출하고, RCA 진입점 알람을 이 증상 지표에 건다. 증상 알람의
이름과 메타데이터는 어떤 하위 시스템이 원인인지 언급하지 않는다.

지표 발행은 **구조화 로그에 내장된 메트릭 형식**을 사용한다. 검토한 대안:

- **직접 지표 발행 API 호출**: 앱에 지표 쓰기 권한과 재시도·배치 로직이 필요하고,
  발행 실패가 요청 경로에 영향을 줄 수 있다.
- **관측성 수집기 사이드카를 통한 지표 전송**: 이미 트레이싱용으로 존재하지만
  선택적 구성이며, 지표 경로까지 의존하면 사이드카 장애가 RCA 진입점을 없앤다.
- **구조화 로그에 내장된 메트릭 형식(채택)**: 앱은 표준 출력에 로그를 쓸 뿐이고
  지표 추출은 로그 수집 계층이 담당한다. 추가 권한과 네트워크 경로가 없고, 지표와
  그 지표를 만든 로그 이벤트가 같은 스트림에 남아 증거 추적이 쉽다. 지표 반영에
  약간의 지연이 있으나 알람 평가 주기 안에서 수용 가능하다.

기존 커넥션 수·자원 사용률 알람은 제거하지 않는다. 증상 알람이 RCA 진입점이 되고,
원인 지표 알람은 에이전트가 검증 단계에서 찾아내야 하는 증거로 위치를 바꾼다.

### 2. 배포 기반 장애 주입

장애 활성화 경로를 대상 서비스에 대한 직접 호출에서 **컨테이너 실행 정의 갱신과
서비스 배포**로 바꾼다. 장애 플래그는 이미 실행 정의의 환경 설정으로 존재하므로,
플래그 값을 바꾼 새 실행 정의를 등록하고 서비스를 갱신하면 장애가 시작된다.

이 방식은 변경 이력 조회에 실제 배포 이벤트를 남기고, 장애 시작 시각과 배포 시각이
조작 없이 일치한다. 실행 정의의 이전 리비전과 새 리비전을 비교하면 어떤 설정이
바뀌었는지 드러나므로, 에이전트는 배포 → 설정 변경 → 코드 경로 → 증상으로 이어지는
사슬을 스스로 구성할 수 있다.

**결함 코드 경로는 저장소에 실제로 존재한다.** 커넥션을 반환하지 않는 요청 처리
경로를 저장소에 커밋하고, 실행 정의의 장애 플래그가 그 경로를 활성화한다. 에이전트는
배포에서 발견한 설정 변경을 단서로 저장소를 검색해 해당 플래그가 소비되는 지점과
커넥션 미반환 패턴을 코드 변경 이력에서 확인한다. 이로써 배포 이벤트 → 설정 변경 →
결함 코드 → 증상의 사슬이 모든 구간에서 실제 데이터로 성립한다.

결함 코드는 **플래그가 꺼진 기본 상태에서 실행되지 않도록** 격리한다. 데모를 위해
결함이 저장소에 상주하는 것은 의도된 비용이며, 기본 배포 구성은 정상 경로만 사용한다.
실행 정의의 배포된 리비전 식별자를 컨테이너 실행 환경에 명시해 에이전트가 어떤
코드 상태가 배포되었는지 저장소와 대조할 수 있게 한다.

기존 직접 호출 주입 경로는 제거하지 않는다. 빠른 수동 확인과 배포 없는 반복 테스트에
필요하고, 자동 복구가 호출하는 리셋 경로와 대칭을 유지해야 한다.

### 3. 점진적 악화와 반증 가능한 경쟁 가설

장애를 즉시 포화가 아니라 **시간에 따라 누적되는 형태**로 만든다. 커넥션 누수는 요청
처리량에 비례해 쌓이므로 지표에 단절이 아닌 추세로 나타나고, 배포 시각을 기점으로 한
증가 시작점이 관측 가능해진다.

동시에 **반증 가능한 경쟁 가설의 근거를 심는다.**

- 배경 트래픽은 정상 수준을 유지한다. 트래픽 급증 가설은 요청량 지표로 기각된다.
- 원인 배포와 별개로 **증상과 무관한 변경 이벤트**를 하나 더 발생시킨다. 두 배포
  중 어느 것이 증상 시작 시각과 상관되는지 구별해야 원인 배포에 도달한다.
- 데이터베이스 인스턴스 자원 지표는 정상 범위를 유지한다. 인스턴스 자체 문제 가설은
  해당 지표로 기각된다.

레드헤링은 시스템에 실제 영향을 주지 않는 설정 변경으로 한정한다. 실제로 성능을
악화시키는 노이즈는 인과 판정을 모호하게 만들어 정답 라벨을 훼손한다.

### 4. 증상 알람에 대한 복구 대상 검증 확장

자동 복구는 알람의 지표 좌표가 확정 원인 유형에 대응하는 허용 대상과 일치할 때만
실행된다. 증상 알람은 원인 지표와 좌표가 다르므로, 확장 없이는 정당한 복구가 전부
차단된다.

허용 목록을 **증상 지표 좌표까지 포함하도록 확장**한다. 증상 알람에서 시작한 복구는
두 조건을 함께 만족해야 한다. 첫째, 알람이 배포 시 주입된 Healthcare 증상 지표 좌표와
정확히 일치해야 한다. 둘째, 확정된 원인 유형이 가리키는 원인 지표의 대상 리소스가
배포 시 주입된 Healthcare 식별자와 일치해야 한다. 증상 알람은 어떤 원인 유형과도
결합할 수 있으므로 알람 좌표만으로는 대상을 특정할 수 없고, 대상 특정은 확정 원인
유형에서 파생한다.

검토한 대안:

- **복수 알람 상관 요구**: 증상 알람과 원인 지표 알람이 같은 시간대에 모두 발생해야
  복구를 허용한다. 가장 엄격하지만 원인 지표 알람이 임계치에 도달하지 않는 시나리오
  에서 복구가 막히고, 데모가 알람 타이밍에 의존해 다산된다.
- **증상 알람에 대한 대상 검증 면제**: 검증을 느슨하게 만들어 안전 정책의 목적을
  훼손한다. 채택하지 않는다.
- **허용 목록 확장(채택)**: fail-closed 성질을 유지한다. 알람 좌표와 원인 유형 파생
  대상이 모두 허용 목록과 일치해야 하며, 어느 한쪽이라도 불일치하면 차단된다.

복구 완료 판정은 리셋 호출의 성공이 아니라 **진입 알람인 증상 지표의 정상화**로
판단한다. 배포로 활성화된 플래그는 리셋만으로 해소되지 않으므로, 실행 정의 되돌리기를
영구 조치 권고로 보고서에 포함한다.

### 5. 시나리오 계약과 정답 라벨

플래그십 시나리오를 평가 하네스의 **엔진 중립 시나리오 계약**으로 등록한다. 계약은
진입 알람, 필수 증거, 허용 가능한 근본원인 표현, 필수 산출물, 안전한 복구 제안 조건을
규정한다. 기각되어야 하는 가설과 그 기각 근거도 계약에 포함해, 정답을 맞히는 것과
오답을 배제하는 것을 함께 측정한다.

## Consequences

### Positive

- 알람이 원인을 누설하지 않으므로 RCA 결과가 추론의 산물임이 관측자에게 드러난다.
- 배포 이력 조회와 코드 변경 분석이 결론에 실제로 기여하고, 해당 도구 통합이 데모에서
  검증된다.
- 기각된 가설마다 반증 증거가 존재하므로 정밀도와 재현율을 동시에 측정할 수 있다.
- 증상 지표가 도메인 영향을 표현하므로 데모가 기술 지표 나열이 아닌 서비스 영향
  서사를 갖는다.
- 지표 발행에 추가 권한과 네트워크 경로가 없어 데모 인프라의 실패 지점이 늘지 않는다.
- 결함 코드가 저장소에 실재하므로 코드 변경 분석이 조작 없이 결론에 기여한다.

### Negative

- 장애 발현까지의 시간이 길어진다. 배포 롤아웃과 누적 악화를 거쳐야 알람이 발생하므로
  주입에서 분석 시작까지 수 분이 소요된다.
- 데모 준비 절차가 복잡해진다. 배포 갱신, 레드헤링 변경, 상태 되돌리기가 필요하다.
- 증상 알람 하나에서 시작하므로 에이전트가 잘못된 경로로 진행하면 실패가 더 눈에
  띈다. 이는 의도된 결과이나 시연 리스크를 높인다.
- 증상 지표는 로그 수집 계층을 거쳐 반영되므로 원인 지표보다 관측 지연이 있다.
- 커넥션을 반환하지 않는 코드 경로가 저장소에 상주한다. 기본 구성에서 실행되지
  않더라도 코드베이스에 결함이 존재한다는 점은 감수하는 비용이다.

### Risks

- 배포 기반 주입으로 컨테이너 실행 정의 리비전이 누적된다. 되돌리기 절차가 없으면
  데모 환경이 원래 상태로 복구되지 않는다.
- 허용 목록에 증상 지표 좌표를 추가하면 원인 유형과 알람 좌표의 결합이 1:1에서
  N:1로 느슨해진다. 대상 리소스 특정이 확정 원인 유형에서 파생되므로, 원인 유형 확정
  경로의 무결성이 복구 안전성의 단일 지점이 된다.
- 배포로 활성화된 장애는 리셋 호출만으로 완전히 해소되지 않는다. 실행 정의의 플래그가
  남아 있으면 컨테이너 재기동 시 장애가 재발한다. 복구 완료 판정을 증상 지표 정상화로
  두지 않으면 재발할 장애를 복구 성공으로 기록할 수 있다.
- 결함 코드 경로의 플래그 격리가 깨지면 기본 배포에서 누수가 발생한다.

## Implementation Notes

검증에서 확인된 사항:

- EMF 지표 추출은 로그 수집 계층이 자동으로 수행하므로 metric filter 정의와
  지표 쓰기 권한이 모두 불필요하다. 로그 쓰기 권한만으로 성립한다.
- 증상 지표는 요청 경로에서 집계만 하고 주기적으로 방출한다. 방출은 표준 출력
  쓰기이므로 실패가 요청 처리에 전파되지 않는다.
- 누수 경로는 플래그가 꺼지면 세션을 정상 반환하고, 켜지면 요청마다 하나씩
  누적한다. 리셋 이후의 요청은 다시 누수하지 않는다.
- 복구 허용 목록 확장은 fail-closed를 유지한다. 증상 알람이라도 확정 원인 유형에서
  파생한 대상 식별자가 없거나 다르면 차단되고, 한 원인 지표 알람이 다른 원인
  유형의 리셋을 승인하지도 못한다.
- 평가 하네스에 경쟁 가설 기각 차원을 추가했다. 이 차원은 선택 필드에 의존하므로
  기존 시나리오의 점수는 변하지 않는다.
- 프롬프트·하네스 입력이 바뀌면 digest 게이트가 재승인을 요구한다. 새 시나리오의
  엔진 결과 스냅샷은 라이브 평가로만 생성되므로, 재승인 전까지 공통 시나리오
  평가는 실패 상태로 남는다.
- 레드헤링 변경이 의도치 않게 실제 영향을 주면 정답 라벨이 훼손된다.
