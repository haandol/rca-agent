# ADR 0007: 데모 시나리오 — 증상 기반 알람과 배포 기반 장애 주입

Date: 2026-07-29
Updated: 2026-07-31

## Status

Accepted (2026-07-31)

## Context

Healthcare 데모 환경은 RCA 시스템의 근본원인분석 능력을 보여주기 위해 존재한다.
그런데 현재 데모 구성은 분석 능력을 시연하지 못하고 우회하게 만든다.

1. **알람이 원인을 이미 말해준다.** 장애 유형과 알람이 1:1로 대응하고 알람 이름에
   원인이 그대로 드러난다. CPU 부하를 주입하면 CPU 알람이 뜬다. 에이전트는 가설을
   세우고 증거로 검증하는 과정 없이 알람 이름을 읽는 것만으로 정답에 도달할 수 있고,
   관측자는 결과가 추론의 산물인지 동어반복인지 구별할 수 없다.
2. **경쟁 가설을 반증할 데이터가 없다.** 배경 트래픽은 항상 일정하고 무관한 변경
   이벤트가 존재하지 않는다. "트래픽 급증이 아니다", "이 배포가 원인이 아니다"라는
   기각은 반증 증거에 근거하지 않고 데이터의 부재에 근거한다. 기각 능력이 시연되지
   않는다.
3. **장애 주입이 인프라 이벤트를 남기지 않는다.** 장애는 대상 서비스에 대한 직접
   API 호출로 발생하므로 변경 이력 조회로 발견할 수 있는 흔적이 없다. 배포 이력과
   코드 변경을 근거로 원인을 좁히는 것이 제품이 내세우는 핵심 역량인데, 데모에서는
   그 경로에 조회할 대상이 없다.
4. **도메인 영향이 관측되지 않는다.** 수집 가능한 지표는 데이터베이스 커넥션 수와
   컨테이너 자원 사용률뿐이다. 환자 바이탈 수집이 실패하고 이상치 알림이 지연되는
   비즈니스 영향은 어떤 지표에도 나타나지 않는다. 인시던트를 사람이 실제로 인지하는
   방식(증상)과 데모의 진입점(원인 지표)이 다르다.

결과적으로 데모는 "장애를 주입하면 그 장애에 대한 알람이 뜨고 에이전트가 그 알람의
이름을 보고서에 옮겨 적는다"에 가깝다. 제품 요구사항이 규정한 플래그십 시나리오
(증상 인지 → 가설 생성 → 배포 이력과 코드 변경으로 원인 특정 → 복구와 롤백 권고)는
현재 인프라에서 재현할 수 없다.

## Decision Drivers

- 알람은 증상을 전달해야 하고 원인을 전달해서는 안 된다. 에이전트가 알람 메타데이터만
  읽고 근본원인에 도달할 수 있으면 분석 능력을 측정할 수 없다.
- 기각된 가설마다 그것을 기각시킨 관측 데이터가 존재해야 한다.
- 배포 이력 조회와 코드 변경 분석이 실제로 결론에 기여해야 한다. 조회 대상이 없는
  도구는 데모에서 장식이다.
- 장애의 인과 사슬은 실제 시스템에서 성립해야 한다. 시연을 위해 증거를 조작하거나
  사후에 주입하지 않는다.
- 복구 안전 정책은 약화되지 않아야 한다. 알람이 증상 지표로 바뀌어도 실행은 사용자
  승인 뒤에만 시작되고 파괴적 액션은 차단된다.

## Decision

데모 시나리오를 **증상에서 시작해 배포로 수렴하는 단일 플래그십 시나리오**로
재구성한다. 구성 요소는 여섯 가지다.

### 1. 도메인 증상 지표와 증상 알람

Healthcare 서비스가 자신의 도메인 관점 지표를 발행한다. 바이탈 수집 실패와 이상치
알림 지연을 지표로 노출하고, RCA 진입점 알람을 이 증상 지표에 건다. 증상 알람의
이름과 메타데이터는 어떤 하위 시스템이 원인인지 언급하지 않는다.

지표 발행은 **구조화 로그에 내장된 메트릭 형식**을 사용한다. 앱은 표준 출력에 로그를
쓸 뿐이고 지표 추출은 로그 수집 계층이 담당하므로, 추가 권한과 네트워크 경로가 없다.
지표와 그 지표를 만든 로그 이벤트가 같은 스트림에 남아 증거 추적도 쉬워진다.

기존 커넥션 수·자원 사용률 알람은 제거하지 않는다. 증상 알람이 RCA 진입점이 되고,
원인 지표 알람은 에이전트가 검증 단계에서 찾아내야 하는 증거로 위치를 바꾼다.

### 2. 배포 기반 장애 주입

장애 활성화 경로를 대상 서비스에 대한 직접 호출에서 **컨테이너 실행 정의 갱신과
서비스 배포**로 바꾼다. 장애 플래그는 이미 실행 정의의 환경 설정으로 존재하므로,
플래그 값을 바꾼 새 실행 정의를 등록하고 서비스를 갱신하면 장애가 시작된다.

이 방식은 변경 이력 조회에 실제 배포 이벤트를 남기고, 장애 시작 시각과 배포 시각이
조작 없이 일치한다. 실행 정의의 이전 리비전과 새 리비전을 비교하면 어떤 설정이
바뀌었는지 드러나므로, 에이전트는 배포 → 설정 변경 → 코드 경로 → 증상으로 이어지는
사슬을 스스로 구성할 수 있다.

**결함 코드 경로는 저장소에 실제로 존재한다.** 커넥션을 반환하지 않는 요청 처리
경로를 저장소에 커밋하고, 실행 정의의 장애 플래그가 그 경로를 활성화한다. 에이전트는
배포에서 발견한 설정 변경을 단서로 저장소를 검색해 해당 플래그가 소비되는 지점과
커넥션 미반환 패턴을 코드 변경 이력에서 확인한다. 이로써 배포 이벤트 → 설정 변경 →
결함 코드 → 증상의 사슬이 모든 구간에서 실제 데이터로 성립한다.

결함 코드는 **플래그가 꺼진 기본 상태에서 실행되지 않도록** 격리한다. 데모를 위해
결함이 저장소에 상주하는 것은 의도된 비용이며, 기본 배포 구성은 정상 경로만 사용한다.
실행 정의의 배포된 리비전 식별자를 컨테이너 실행 환경에 명시해 에이전트가 어떤
코드 상태가 배포되었는지 저장소와 대조할 수 있게 한다.

기존 직접 호출 주입 경로는 제거하지 않는다. 빠른 수동 확인과 배포 없는 반복 테스트에
필요하고, 플레이북 실행이 호출하는 리셋 경로와 대칭을 유지해야 한다.

### 3. 주입량과 알람 임계치의 정합 계약

증상 알람이 진입점이므로 **주입된 장애가 증상 지표를 실제로 움직여야** 데모가 성립한다.
장애를 주입해도 증상 지표가 변하지 않으면 RCA가 시작되지 않고, 반대로 증상만 뜨고 원인
지표가 임계치에 닿지 않으면 검증 단계에서 찾아낼 증거가 없다.

플래그십 경로인 커넥션 누수에 대해 이 사슬을 수치로 고정한다.

- **증상 발현 조건**: 커넥션 풀이 고갈되면 요청이 커넥션을 얻지 못해 바이탈 수집이
  실패하고, 그 실패가 증상 지표에 나타난다. 즉 **풀 고갈이 증상의 발생 지점**이다.
  누수는 요청마다 하나씩 쌓이므로 풀 용량이 곧 증상까지의 거리다.
- **커넥션 임계치는 풀 고갈 지점보다 낮아야 한다.** 임계치가 풀 용량보다 높으면 누수가
  풀을 다 써도 알람이 뜨지 않아, 원인 지표가 증거로 존재하지 않는다.

  요구사항 값: 애플리케이션 커넥션 풀은 기본 5개에 최대 초과 10개이므로 고갈 지점은
  **15개**이고, 이 인스턴스의 정상 커넥션 사용량은 실측 **3개**다. 따라서 커넥션 알람
  임계치는 **12개**로 둔다 — 정상 사용량의 네 배로 배경 트래픽 변동에 오탐하지 않고,
  고갈 지점보다 낮아 누수가 증상을 만들기 전에 원인 지표가 먼저 관측된다. 이 세 값
  (풀 5+10, 정상 3, 임계치 12)의 순서 관계가 계약이며, 풀 용량을 바꾸면 임계치도
  함께 재계산해야 한다.

- **누수는 풀 용량을 넘길 수 있어야 한다.** 명시적 주입의 기본 누수 개수가 풀 용량보다
  적으면 한 번의 주입으로 증상에 도달하지 못한다.

  요구사항 값: 명시적 주입의 기본 누수 개수는 **20개**로 둔다. 풀 고갈 지점 15개를
  넘기므로 단일 주입으로 증상까지 도달하며, 임계치 12개도 함께 넘긴다.

- **관측 지연**: 커넥션 지표는 1분 주기로 집계되고 증상 지표는 로그 수집 계층을 거치므로,
  주입에서 알람까지 두 지표의 평가 주기와 수집 지연을 합한 시간이 필요하다. 복구 판정도
  같은 지연을 겪으므로, 실행 에이전트의 관측 예산은 진입 알람의 평가 주기 전체를 담을
  수 있어야 한다. 증상 지표는 집계 주기가 30초이고 알람은 1분 주기 2회 평가를 요구하므로,
  주입·복구 각각 최소 2분 30초의 관측 구간을 전제한다.

이 정합은 **커넥션 누수 시나리오에 대해서만** 보장한다. 자원 사용률 계열 장애(컨테이너
CPU·메모리)와 질의 지연 장애는 자기 원인 지표 알람을 갖지만, 바이탈 수집을 실패시키지
않으므로 증상 알람으로 이어지지 않는다. 이들은 **RCA 진입점이 아니라 검증 단계에서
경쟁 가설을 기각하기 위한 원인 지표**로 위치한다. 진입점 역할을 요구하지 않으므로
주입량과 임계치를 증상 발현 기준으로 맞추지 않는다.

### 4. 점진적 악화와 반증 가능한 경쟁 가설

장애를 즉시 포화가 아니라 **시간에 따라 누적되는 형태**로 만든다. 커넥션 누수는 요청
처리량에 비례해 쌓이므로 지표에 단절이 아닌 추세로 나타나고, 배포 시각을 기점으로 한
증가 시작점이 관측 가능해진다.

동시에 **반증 가능한 경쟁 가설의 근거를 심는다.**

- 배경 트래픽은 정상 수준을 유지한다. 트래픽 급증 가설은 요청량 지표로 기각된다.
- 원인 배포와 별개로 **증상과 무관한 변경 이벤트**를 하나 더 발생시킨다. 두 배포
  중 어느 것이 증상 시작 시각과 상관되는지 구별해야 원인 배포에 도달한다.
- 데이터베이스 인스턴스 자원 지표는 정상 범위를 유지한다. 인스턴스 자체 문제 가설은
  해당 지표로 기각된다.

레드헤링은 시스템에 실제 영향을 주지 않는 설정 변경으로 한정한다. 실제로 성능을
악화시키는 노이즈는 인과 판정을 모호하게 만들어 정답 라벨을 훼손한다.

### 5. 증상 알람에서 시작한 복구의 대상 특정

증상 알람은 원인 지표와 좌표가 다르므로, **알람 좌표만으로는 조치 대상을 특정할 수
없다.** 여러 원인 유형이 같은 증상으로 수렴하기 때문이다. 대상 리소스는 분석이 확정한
원인 유형에서 파생해야 하며, 플레이북의 절차가 그 대상을 명시해야 한다
([ADR agent/0008](../agent/0008-playbook-generation.md)).

이 제약은 실행 경계와 별개다. 실행 계층은 대상 리소스를 제한하지 않고 파괴적 액션만
차단하므로([ADR agent/0017](../agent/0017-playbook-execution-agent.md)), 잘못된 대상을
막는 것은 안전 게이트가 아니라 **분석의 정확성과 사용자 승인**이다. 사용자는 리포트에서
확정 원인과 그에 따른 조치 대상을 함께 읽고 승인한다.

복구 완료 판정은 리셋 호출의 성공이 아니라 **진입 알람인 증상 지표의 정상화**로
판단한다. 배포로 활성화된 플래그는 리셋만으로 해소되지 않으므로, 실행 정의 되돌리기를
영구 조치 권고로 리포트에 포함한다. 이 시나리오는 리셋 성공과 증상 해소가 갈라지는
경우이므로, 실행 에이전트의 해결 판정이 관측에 근거해야 하는 이유를 그대로 보여준다.

### 6. 시나리오 계약과 정답 라벨

플래그십 시나리오를 평가 하네스의 **엔진 중립 시나리오 계약**으로 등록한다. 계약은
진입 알람, 필수 증거, 허용 가능한 근본원인 표현, 필수 산출물, 안전한 복구 제안 조건을
규정한다. 기각되어야 하는 가설과 그 기각 근거도 계약에 포함해, 정답을 맞히는 것과
오답을 배제하는 것을 함께 측정한다.

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 앱이 지표 발행 API를 직접 호출 | 지표가 즉시 반영되고 발행 시점을 앱이 통제한다. | 앱에 지표 쓰기 권한과 재시도·배치 로직이 필요하고, 발행 실패가 요청 경로에 영향을 줄 수 있다. |
| 관측성 수집기 사이드카로 지표 전송 | 이미 트레이싱용으로 존재해 재사용할 수 있다. | 사이드카가 선택적 구성이므로 지표 경로까지 의존하면 사이드카 장애가 RCA 진입점 자체를 없앤다. |
| 구조화 로그에 내장된 메트릭 형식 | 추가 권한과 네트워크 경로가 없고, 지표와 그 지표를 만든 로그가 같은 스트림에 남아 증거 추적이 쉽다. | 로그 수집 계층을 거치므로 지표 반영에 지연이 있다 (알람 평가 주기 안에서 수용 가능). |

증상 알람에서 시작한 복구의 대상 검증:

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 증상 알람과 원인 지표 알람의 동시 발생 요구 | 가장 엄격하고 두 관측이 서로를 교차 확인한다. | 원인 지표가 임계치에 도달하지 않는 시나리오에서 정당한 복구가 막히고, 데모가 알람 타이밍에 의존해 불안정해진다. |
| 증상 알람에 대해 대상 검증 면제 | 구현이 가장 단순하다. | 검증을 느슨하게 만들어 안전 정책의 목적 자체를 훼손한다. |
| 허용 목록을 증상 지표 좌표까지 확장 | fail-closed를 유지하면서 증상 진입점을 허용한다. 알람 좌표와 원인 유형 파생 대상이 모두 일치해야 한다. | 원인 유형과 알람 좌표의 결합이 1:1에서 N:1로 느슨해져, 원인 유형 확정 경로가 복구 안전성의 단일 지점이 된다. |

장애를 활성화하는 방법:

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 대상 서비스에 직접 API 호출로 주입 | 즉시 발현하고 반복 테스트가 빠르다. | 변경 이력에 흔적이 남지 않아 배포 이력 조회와 코드 변경 분석 경로에 조회 대상이 없다. 제품의 핵심 역량이 데모에서 검증되지 않는다. |
| 결함 코드를 주입 시점에 생성·배포 | 저장소에 결함이 상주하지 않는다. | 커밋 이력이 시연을 위해 오염되고, 분석 시점의 저장소 상태가 실행 중 코드와 일치한다는 보장이 사라진다. |
| 플래그를 바꾼 실행 정의를 배포 | 실제 배포 이벤트가 남고 장애 시작 시각과 배포 시각이 조작 없이 일치한다. 결함 코드는 저장소에 상주하되 플래그로 격리된다. | 발현까지 수 분이 걸리고, 커넥션을 반환하지 않는 코드 경로가 저장소에 상주한다. |

주입량과 임계치를 맞추는 방법:

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 커넥션 임계치를 인스턴스 한도 기준으로 둔다 | 실제 데이터베이스 포화를 나타내므로 운영 알람으로서 자연스럽다. | 애플리케이션 풀이 인스턴스 한도보다 훨씬 작아 풀이 고갈되어도 임계치에 닿지 않는다. 누수가 증상을 만드는데 원인 지표는 침묵해, 검증 단계에서 찾을 증거가 없다. |
| 풀 용량을 임계치보다 크게 키운다 | 임계치를 그대로 두고 누수가 임계치를 넘게 만들 수 있다. | 데모를 위해 정상 구성의 풀을 과대하게 만들어야 하고, 풀이 커지는 만큼 증상 발현까지의 누수 시간이 길어진다. |
| 임계치를 정상 사용량과 풀 고갈 사이에 둔다 | 누수가 진행되면 원인 지표가 먼저 관측되고 이어서 증상이 발현하므로, 두 신호의 시간 순서가 인과와 일치한다. | 임계치가 인스턴스 한도와 무관해져 운영 알람이 아닌 데모 전용 값이 된다. 풀 용량을 바꿀 때 임계치도 함께 재계산해야 한다. |
| 네 fault 모두 증상까지 연결한다 | 어느 장애를 주입해도 증상 알람이 진입점이 된다. | 자원 사용률·질의 지연은 바이탈 수집을 실패시키지 않으므로 증상을 만들려면 인위적 실패 경로를 심어야 하고, 그러면 인과 사슬이 시연을 위한 조작이 된다. |

## Consequences

### Positive

- 알람이 원인을 누설하지 않으므로 RCA 결과가 추론의 산물임이 관측자에게 드러난다.
- 배포 이력 조회와 코드 변경 분석이 결론에 실제로 기여하고, 해당 도구 통합이 데모에서
  검증된다.
- 기각된 가설마다 반증 증거가 존재하므로 정밀도와 재현율을 동시에 측정할 수 있다.
- 증상 지표가 도메인 영향을 표현하므로 데모가 기술 지표 나열이 아닌 서비스 영향
  서사를 갖는다.
- 지표 발행에 추가 권한과 네트워크 경로가 없어 데모 인프라의 실패 지점이 늘지 않는다.
- 결함 코드가 저장소에 실재하므로 코드 변경 분석이 조작 없이 결론에 기여한다.
- 커넥션 누수가 원인 지표 알람과 증상 알람을 이 순서로 발생시키므로, 진입점과 검증 증거가
  같은 주입 하나로 함께 성립한다.

### Negative

- 장애 발현까지의 시간이 길어진다. 배포 롤아웃과 누적 악화를 거쳐야 알람이 발생하므로
  주입에서 분석 시작까지 수 분이 소요된다.
- 데모 준비 절차가 복잡해진다. 배포 갱신, 레드헤링 변경, 상태 되돌리기가 필요하다.
- 증상 알람 하나에서 시작하므로 에이전트가 잘못된 경로로 진행하면 실패가 더 눈에
  띈다. 이는 의도된 결과이나 시연 리스크를 높인다.
- 증상 지표는 로그 수집 계층을 거쳐 반영되므로 원인 지표보다 관측 지연이 있다.
- 커넥션을 반환하지 않는 코드 경로가 저장소에 상주한다. 기본 구성에서 실행되지
  않더라도 코드베이스에 결함이 존재한다는 점은 감수하는 비용이다.
- 커넥션 알람 임계치가 데이터베이스 인스턴스의 실제 한도와 무관한 데모 전용 값이 된다.
  이 알람은 인스턴스 포화를 알리지 않고 애플리케이션 풀의 누수를 알린다.
- 자원 사용률과 질의 지연 장애는 증상 알람으로 이어지지 않으므로 RCA 진입점이 되지 못한다.
  이들만 주입하면 분석이 시작되지 않는다.

### Risks

- 배포 기반 주입으로 컨테이너 실행 정의 리비전이 누적된다. 되돌리기 절차가 없으면
  데모 환경이 원래 상태로 복구되지 않는다.
- 허용 목록에 증상 지표 좌표를 추가하면 원인 유형과 알람 좌표의 결합이 1:1에서
  N:1로 느슨해진다. 대상 리소스 특정이 확정 원인 유형에서 파생되므로, 원인 유형 확정
  경로의 무결성이 복구 안전성의 단일 지점이 된다.
- 배포로 활성화된 장애는 리셋 호출만으로 완전히 해소되지 않는다. 실행 정의의 플래그가
  남아 있으면 컨테이너 재기동 시 장애가 재발한다. 복구 완료 판정을 증상 지표 정상화로
  두지 않으면 재발할 장애를 복구 성공으로 기록할 수 있다.
- 결함 코드 경로의 플래그 격리가 깨지면 기본 배포에서 누수가 발생한다.
- 커넥션 풀 용량을 바꾸면 임계치와의 순서 관계가 깨질 수 있다. 풀을 임계치보다 작게
  줄이면 고갈이 임계치보다 먼저 와 원인 지표가 침묵하고, 풀을 크게 늘리면 증상 발현까지의
  누수 시간이 길어진다. 풀 용량은 임계치와 함께 조정해야 한다.

## Implementation Notes

검증에서 확인된 사항:

- EMF 지표 추출은 로그 수집 계층이 자동으로 수행하므로 metric filter 정의와
  지표 쓰기 권한이 모두 불필요하다. 로그 쓰기 권한만으로 성립한다.
- 증상 지표는 요청 경로에서 집계만 하고 주기적으로 방출한다. 방출은 표준 출력
  쓰기이므로 실패가 요청 처리에 전파되지 않는다.
- 누수 경로는 플래그가 꺼지면 세션을 정상 반환하고, 켜지면 요청마다 하나씩
  누적한다. 리셋 이후의 요청은 다시 누수하지 않는다.
- 복구 허용 목록 확장은 fail-closed를 유지한다. 증상 알람이라도 확정 원인 유형에서
  파생한 대상 식별자가 없거나 다르면 차단되고, 한 원인 지표 알람이 다른 원인
  유형의 리셋을 승인하지도 못한다.
- 평가 하네스에 경쟁 가설 기각 차원을 추가했다. 이 차원은 선택 필드에 의존하므로
  기존 시나리오의 점수는 변하지 않는다.
- 프롬프트·하네스 입력이 바뀌면 digest 게이트가 재승인을 요구한다. 새 시나리오의
  엔진 결과 스냅샷은 제공된 관측을 사용하는 실모델 의미 평가로 생성하므로,
  재승인 전까지 공통 시나리오 평가는 실패 상태로 남는다.
- 레드헤링 변경이 의도치 않게 실제 영향을 주면 정답 라벨이 훼손된다.
- 배포 기반 누수 주입의 라이브 검증에서 두 알람이 인과 순서대로 발생했다. 주입
  직후 커넥션이 풀 상한까지 차오르며 임계치를 넘어 **약 3분 뒤 커넥션 알람**이
  울리고, 풀이 고갈되어 바이탈 수집이 실패하면서 **약 5분 뒤 증상 알람**이 울렸다.
  원인 지표가 증상보다 먼저 관측되므로 검증 단계에서 찾을 증거가 타임라인에 존재한다.
- 두 엔진이 커넥션 알람으로 세션을 열었고, 뒤이어 도착한 증상 알람 메시지는 진행 중
  분석 뒤에 대기했다. 같은 장애가 두 알람을 만들면 먼저 울린 쪽이 진입점이 되며,
  나중 알람은 별도 세션이 아니라 큐에서 순서를 기다린다.
- 리셋은 커넥션을 기준 수준으로 되돌리고 두 알람을 모두 해제했다. 커넥션 알람이 먼저
  풀리고 증상 알람이 한 주기 뒤에 풀리므로, 해제 순서도 발생 순서를 따른다.
