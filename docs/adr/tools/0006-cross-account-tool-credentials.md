# ADR 0006: 크로스 계정 도구 자격 증명 — 세션 범위 위임 프로파일

Date: 2026-08-07

## Status

Proposed

## Context

증거 수집과 실행 도구는 관리형 MCP 서버가 대행하며, 에이전트 코드는 관측 API를 직접
호출하지 않는다([ADR 0001](0001-metrics-collection.md), [ADR 0002](0002-log-search.md),
[ADR 0004](0004-deploy-history.md)). 이 서버들은 별도 프로세스로 기동되고 실행 환경의
기본 자격 증명을 사용한다. 따라서 조회 대상 계정은 워커가 배포된 계정으로 고정된다.

멀티 계정 RCA는 대상 계정의 위임 역할을 통해 조회·변경하며, 대상 계정 권한은 워커의
태스크 역할에 상주하지 않는다([ADR infra/0009](../infra/0009-multi-account-rca-hub-spoke.md)).
그러면 **세션마다 다른 계정의 자격 증명이 도구 프로세스에 도달해야 한다.** 도구를 자체
구현하지 않기로 한 결정을 유지하는 한, 대상 계정을 도구 호출 인자로 전달할 방법은 없다.
관리형 서버의 도구 스키마에 대상 계정 개념이 없기 때문이다.

같은 워커가 서로 다른 계정의 세션을 순차 처리하므로, 프로세스 전역 자격 증명을 한 번
설정하는 방식은 이전 세션의 대상을 다음 세션이 조회하는 결과를 낳는다.

## Decision Drivers

- 도구 계층을 자체 구현하지 않는 결정을 유지해야 한다. 대상 계정 지원이 도구 재구현의
  이유가 되어서는 안 된다.
- 한 세션의 도구가 그 세션의 대상 계정만 조회·변경할 수 있어야 한다. 다른 계정의 자격
  증명에 접근할 수 있어서는 안 된다.
- 자격 증명이 세션의 최악 소요 시간 안에 만료되어서는 안 된다. 만료가 세션 중간의 조회
  실패로 나타나면 증거 수집이 원인 없이 실패한다.
- 자격 증명이 증거·로그·실행 기록에 남아서는 안 된다.
- 분석 도구와 실행 도구가 서로 다른 스포크 역할을 위임받아야 한다.

## Decision

각 세션마다 **위임 역할을 가리키는 세션 범위 자격 증명 프로파일**을 만들고, 도구
프로세스가 그 프로파일을 사용하도록 환경을 구성한다. 자격 증명 값 자체를 도구에 전달하지
않는다.

### 값이 아니라 위임 지시를 전달한다

프로파일은 위임할 역할과 위임의 출처만 기술한다. 실제 임시 자격 증명은 도구 프로세스의
SDK가 스스로 획득하고, **만료되면 스스로 재획득한다.**

임시 자격 증명 값을 환경 변수로 주입하는 방식을 택하지 않은 이유는 만료 때문이다. 워커의
역할에서 다시 위임받는 형태의 자격 증명은 유효 기간의 상한이 짧고, 분석과 실행의 시간
예산은 그 상한에 근접하거나 초과한다([ADR agent/0006](../agent/0006-termination-conditions.md),
[ADR infra/0008](../infra/0008-playbook-execution-stack.md)). 값을 주입하면 세션 중간에
만료되고, 도구 프로세스는 이미 기동되어 있어 갱신된 값을 받을 방법이 없다. 갱신을 위해
프로세스를 재기동하면 도구 세션의 상태가 사라진다.

### 세션 범위 격리

프로파일 구성은 세션마다 새로 만들어지고 세션이 끝나면 사라지는 위치에 둔다. 워커 전역
구성이나 이미지에 포함된 구성에 쓰지 않는다.

세션 범위로 두는 이유는 두 가지다. 첫째, 같은 워커가 다른 계정의 세션을 이어서 처리하므로
전역 구성은 이전 대상이 남는다. 둘째, 한 세션의 도구 프로세스가 다른 계정의 위임 지시를
읽을 수 있으면 대상 좌표가 도구 수준에서 지켜지지 않는다.

이미 세션마다 격리된 작업 공간과 도구 구성을 렌더링하는 구조가 있으므로, 프로파일 구성은
그 같은 격리 단위에 놓인다.

### 분석과 실행은 다른 역할을 위임받는다

분석 세션의 프로파일은 대상 계정의 조회 역할을, 실행 세션의 프로파일은 실행 역할을
가리킨다. 한 프로파일이 두 역할을 겸하지 않는다 — 읽기 전용 분석과 쓰기 실행의 권한
분리가 도구 자격 증명 수준에서도 유지되어야 한다.

### 위임 실패는 세션 실패다

위임에 실패하면 해당 세션은 실패로 종결한다. 워커의 기본 자격 증명으로 대체하지 않는다.
대체하면 대상 계정을 조사한다고 기록된 세션이 실제로는 허브 계정을 조사하며, 그 결과가
대상 계정의 증거로 저장된다. 잘못된 증거보다 증거 없음이 낫다.

### 자격 증명은 기록되지 않는다

프로파일 구성에는 위임 대상과 출처만 담기며 비밀 값이 없다. 도구가 획득한 임시 자격
증명은 도구 프로세스 안에만 존재한다. 실행 증거의 인자 기록은 자격 증명으로 보이는 값을
가리는 규칙을 이미 따른다([ADR infra/0002](../infra/0002-evidence-storage.md)).

## Consequences

### Positive

- 도구 계층을 자체 구현하지 않고 대상 계정 조회·실행을 지원한다.
- 자격 증명이 세션 예산 전체에 걸쳐 유효하게 유지된다.
- 한 세션의 도구가 다른 계정의 위임 지시에 접근할 수 없다.
- 비밀 값이 구성 파일과 환경에 남지 않는다.
- 분석과 실행의 권한 분리가 도구 자격 증명 수준에서도 유지된다.

### Negative

- 도구 클라이언트를 워커 수명 동안 재사용할 수 없고 세션마다 만들어야 한다. 세션마다
  도구 프로세스 기동 비용이 발생한다.
- 도구 프로세스가 위임 프로파일을 해석한다는 전제에 의존하므로, 그 해석 방식이 바뀌면
  대상 계정 조회가 조용히 허브 계정 조회로 바뀔 수 있다.
- 세션마다 구성을 렌더링하는 단계가 하나 늘어난다.

### Risks

- 도구가 프로파일 지정을 무시하고 기본 자격 증명을 쓰면 대상 계정이 아닌 허브 계정을
  조사하면서 성공한다. 실패보다 조용해서 발견이 늦다. 세션 시작 시 위임된 신원이 대상
  좌표의 계정과 일치하는지 확인하고, 불일치를 세션 실패로 처리한다.
- 위임 역할의 신뢰 정책이 어긋나면 해당 계정의 모든 세션이 실패한다. 실패 사유에 대상
  좌표와 위임 대상이 남아야 원인을 계정 단위로 판정할 수 있다.
- 세션 범위 구성이 정리되지 않으면 종료된 세션의 위임 지시가 남는다. 격리 단위가 세션
  종료와 함께 사라지는 위치여야 한다.
