# ADR 0001: 메트릭 수집 — 관리형 MCP 서버 기반 증거 수집

Date: 2026-04-21

## Status

Accepted (2026-04-21)

## Context

가설 검증에는 CloudWatch 메트릭(자원 사용률, 커넥션 수, 지연, 에러율) 증거가
필요하다. 사람이 콘솔에서 메트릭을 조회하던 과정을 에이전트가 대체해야 한다.

## Decision Drivers

- 에이전트가 관측 데이터를 직접 조회할 수 있어야 한다.
- 관측 도구 코드를 자체 유지보수하지 않아야 한다. RCA 품질에 쓸 노력이 도구 배관에
  소모되면 안 된다.
- 장애 시점과 평상시를 비교할 수 있어야 한다. 절대값만으로는 이상 여부를 판정할 수 없다.
- 도구 인터페이스 변경이 실행 중 RCA를 깨뜨려서는 안 된다.

## Decision

**AWS가 공식 제공하는 CloudWatch MCP 서버**를 에이전트의 도구로 등록한다. 커스텀
도구를 직접 구현하지 않는다.

### 핵심 결정사항

1. **관측 API 직접 호출 금지**: 에이전트 코드는 관측 API를 직접 호출하지 않고 MCP
   서버가 대행한다. 도구 계층을 자체 구현하면 인증·페이지네이션·재시도를 직접
   유지해야 하고, 그 코드가 RCA 로직과 뒤섞인다.

2. **비교 분석은 프롬프트로 지시**: 장애 시점 메트릭과 직전 동일 시간대 메트릭을
   각각 조회해 비교하도록 프롬프트에서 지시한다. 이 비교 로직을 도구에 넣지 않는
   이유는, 무엇과 무엇을 비교할지가 가설에 따라 달라지기 때문이다.

3. **알람 이력 조회를 스코핑에 활용**: 활성 알람과 알람 이력을 조회해 동시 발생
   여부와 영향 범위를 파악한다([ADR agent/0001](../agent/0001-initial-scoping-and-report-similarity.md)).

4. **증거 저장**: 수집된 메트릭은 증거 저장 정책에 따라 보관하고 메타데이터를
   기록한다([ADR infra/0002](../infra/0002-evidence-storage.md)).

5. **MCP 서버 버전 고정**: 도구 인터페이스가 실행 중에 바뀌지 않도록 서버 버전을
   이미지에서 고정한다([ADR infra/0003](../infra/0003-lambda-cc-headless-stack.md)).

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 커스텀 도구로 관측 API 직접 래핑 | 필요한 조회 패턴만 정확히 노출하고 응답 크기를 제어할 수 있다. | 인증·페이지네이션·재시도·트렌드 분석을 모두 자체 유지해야 하고, 그 코드가 RCA 로직과 뒤섞여 유지보수 부담이 커진다. |
| 메트릭을 사전 수집해 자체 저장소에 적재 | 조회가 빠르고 응답 형식을 통제할 수 있다. | 어떤 메트릭이 필요한지 가설이 정해지기 전에는 알 수 없어 대부분이 낭비되고, 적재 파이프라인이 새로운 장애 지점이 된다. |
| 관리형 MCP 서버 등록 | 도구 유지보수가 없고 메트릭 조회·알람 이력·트렌드 분석을 즉시 활용한다. | 서버 버전 업데이트에 의존하고, 조회 패턴 제어를 프롬프트로만 할 수 있다. |

## Consequences

### Positive

- 관측 도구 코드를 자체 유지보수하지 않는다
- 메트릭 조회·알람 이력·트렌드 분석을 추가 구현 없이 활용한다
- 에이전트 프레임워크의 MCP 지원으로 서버 등록만으로 연동된다

### Negative

- MCP 서버 버전 업데이트에 의존성이 생긴다
- 조회 패턴(비교 대상, 기간 확장)을 프롬프트로만 제어하므로 일관성이 떨어질 수 있다

### Risks

- MCP 서버 업데이트로 도구 인터페이스가 변경될 수 있다. 버전을 이미지에 고정해
  완화한다.
