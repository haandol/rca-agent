# ADR 0002: 로그 검색 — 관리형 MCP 서버 기반 증거 수집

Date: 2026-04-21

## Status

Accepted (2026-04-21)

## Context

가설 검증에는 에러 로그와 관련 로그 증거가 필요하다. SRE가 직접 쿼리를 작성하지
않아도 가설에 맞는 로그가 수집되어야 한다.

## Decision Drivers

- 가설마다 필요한 로그가 다르므로 쿼리를 사전에 고정할 수 없다.
- 로그 검색 도구를 자체 유지보수하지 않아야 한다.
- 로그가 없거나 보존 기간이 지난 경우에도 RCA가 진행되어야 한다.
- 로그 응답이 증거 수집 컨텍스트를 압도해서는 안 된다.

## Decision

메트릭 수집과 **같은 CloudWatch MCP 서버**의 로그 도구를 사용한다([ADR 0001](0001-metrics-collection.md)).
커스텀 도구를 직접 구현하지 않는다.

### 핵심 결정사항

1. **단일 MCP 서버로 메트릭과 로그를 함께 커버**: 관측 도구 서버를 하나로 유지해
   버전 고정과 자격 증명 관리 지점을 줄인다.

2. **LLM 쿼리 생성**: 에이전트가 가설에 맞는 로그 쿼리를 생성해 실행한다. 쿼리를
   사전 정의하면 미리 예상한 패턴만 조사할 수 있다.

3. **결과 크기 제어를 프롬프트로 강제**: 로그 쿼리에 결과 상한을 걸고 요약을
   지시한다. 로그 원본은 쉽게 증거 수집 컨텍스트를 넘기므로 수집 시점에 제한한다
   ([ADR agent/0014](../agent/0014-hierarchical-evidence-session-isolation.md)).

4. **수집 불가를 명시적 결과로 취급**: 로그 그룹이 없거나 보존 기간이 지나 증거를
   얻을 수 없으면 "수집 불가"로 기록하고 다른 증거로 판정을 진행한다. 증거 부재를
   조용히 넘기면 검증이 근거 없이 확정할 위험이 생긴다.

5. **로그 검색 범위**: CloudWatch Logs Insights만 사용하고 대용량 검색 엔진을
   도입하지 않는다. 데모·검증 규모에서 Insights의 조회 성능이 충분하고, 별도 검색
   클러스터는 인프라와 적재 파이프라인을 추가한다.

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 가설 카테고리별 사전 정의 쿼리 | 결정적이고 쿼리 품질이 일정하다. | 미리 정의하지 않은 장애 패턴을 조사할 수 없어 RCA의 탐색 능력 자체가 사전 정의 범위로 제한된다. |
| 대용량 로그 검색 엔진 도입 | 대규모 로그에서 검색이 빠르고 질의 표현력이 높다. | 검색 클러스터와 적재 파이프라인이 추가되어 새 장애 지점이 생기고, 현재 규모에서 이점이 비용을 넘지 않는다. |
| 관리형 MCP 서버의 로그 도구 + LLM 쿼리 생성 | 도구 유지보수가 없고 가설에 맞는 쿼리를 유연하게 만든다. | 생성된 쿼리가 비효율적이거나 부정확할 수 있고, 쿼리 타임아웃 재시도를 프롬프트로 제어해야 한다. |

## Consequences

### Positive

- 하나의 MCP 서버로 메트릭과 로그를 모두 커버해 관리 지점을 최소화한다
- 로그 이상 탐지 도구를 추가 구현 없이 활용한다
- LLM이 쿼리를 생성하므로 SRE의 쿼리 작성 부담이 없다

### Negative

- 쿼리 타임아웃 재시도를 프롬프트로 제어해야 한다
- LLM이 생성한 쿼리가 비효율적이거나 부정확할 수 있다
- 대용량 로그 환경에서는 Insights 조회 성능이 병목이 될 수 있다

### Risks

- 로그 그룹이 없거나 보존 기간이 짧으면 증거 수집이 불가하다. "수집 불가"로 표시하고
  다른 증거에 의존해 완화한다.
