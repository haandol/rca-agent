# ADR 0004: 배포 이력 조회 — 관리형 MCP 서버 기반 변경 이벤트 조회

Date: 2026-04-21

## Status

Accepted (2026-04-21)

## Context

장애와 최근 변경의 상관관계를 분석하려면 배포·변경 이력을 자동 조회해야 한다.
커넥션 누수나 메모리 누수처럼 배포 후 수시간~수일 뒤에 발현되는 장애는 짧은 시간
범위만 보면 원인 배포를 놓친다.

## Decision Drivers

- 변경 이력 조회 도구를 자체 유지보수하지 않아야 한다([ADR 0001](0001-metrics-collection.md)).
- 느리게 발현되는 장애의 원인 배포를 놓쳐서는 안 된다. 시간 범위 컷오프가 이 실패를
  만든다.
- 조회 기간 내 배포가 없다는 사실도 증거로 쓸 수 있어야 한다. 배포 가설을 기각할
  근거가 필요하다.
- 배포 이력에서 시작해 코드 변경으로 내려가는 경로가 성립해야 한다.

## Decision

**AWS가 공식 제공하는 CloudTrail MCP 서버**를 에이전트의 도구로 등록한다. 커스텀
도구를 직접 구현하지 않는다.

### 핵심 결정사항

1. **배포 이벤트 필터링을 프롬프트로 지시**: 리소스 이름으로 변경 이벤트를 조회하고
   배포 관련 이벤트만 골라내도록 지시한다. 어떤 이벤트가 배포에 해당하는지는 대상
   서비스에 따라 달라지므로 도구에 고정하지 않는다.

2. **시간 기반 컷오프 없음**: 특정 기간으로 자르지 않고 직전 N개 변경 이벤트를
   확인한다. 느린 누수 장애는 배포와 발현 사이 간격이 크므로, 시간으로 자르면 원인
   배포가 조회 범위 밖으로 밀려난다.

3. **상관관계 판정은 에이전트가 수행**: 변경 시각과 메트릭 이상 시작 시각을 비교해
   가장 상관성 높은 변경을 식별한다. 여러 배포가 있을 때 어느 것이 증상 시작과
   상관되는지 구별하는 것이 이 도구의 핵심 기여다([ADR infra/0007](../infra/0007-demo-symptom-alarm-and-deployment-fault-injection.md)).

4. **배포 부재도 증거로 기록**: 조회 기간 내 배포 이벤트가 없으면 그것을 배포 가설의
   기각 근거로 기록한다. 증거 부재와 반증 증거를 구별해 기록해야 보고서 독자가
   기각의 강도를 판단할 수 있다.

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 배포 파이프라인에서 이력을 직접 수집 | 배포 메타데이터(커밋, 작성자, 릴리스 노트)가 풍부하다. | 파이프라인마다 통합이 필요하고, 파이프라인을 거치지 않은 수동 변경을 놓친다. 변경 이력은 파이프라인이 아니라 클라우드 API 호출 기록이 권위다. |
| 최근 N시간으로 조회 범위 제한 | 조회량이 적고 응답이 작다. | 느리게 발현되는 누수 장애의 원인 배포가 범위 밖으로 밀려나 배포 가설이 근거 없이 기각된다. |
| 관리형 MCP 서버로 변경 이벤트 조회 | 도구 유지보수가 없고 수동 변경까지 포함한 90일 이력을 조회한다. | 이벤트 필터링이 프롬프트에 의존해 일관성이 떨어지고, 이벤트 기록에 지연이 있다. |

## Consequences

### Positive

- 변경 이력 조회 도구를 자체 유지보수하지 않는다
- 90일 범위 조회로 느린 누수 장애의 원인 배포도 탐지 가능하다
- 파이프라인을 거치지 않은 수동 변경도 이력에 포함된다

### Negative

- 배포 이벤트 필터링이 프롬프트에 의존해 일관성이 떨어질 수 있다
- 변경 이벤트 기록에 최대 수분의 지연이 있어 방금 발생한 배포는 조회되지 않을 수 있다

### Risks

- 조회 기간 내 배포 이벤트가 없으면 배포 가설을 증거 부재로 기각하게 된다. 반증
  증거에 의한 기각과 구별해 기록한다.
