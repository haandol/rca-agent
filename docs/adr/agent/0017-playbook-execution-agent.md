# ADR 0017: 플레이북 실행 에이전트 — 사용자 승인 게이트와 파괴적 액션 차단

Date: 2026-07-30
Updated: 2026-09-17

## Status

Proposed

## Context

RCA(근본원인분석)가 대응 지식을 남겨도 실제 조치의 대상과 명령을 정하지 않으면
복구를 시작할 수 없다. 플레이북은 유형별 지식이며, 런북은 이번 사고에 적용할
구체 명령과 순서, 성공 기준이다. 운영자는 원인 판단과 런북을 읽고 실행 시점과
범위를 통제해야 한다.

실행 중 모델이 명령이나 대상을 다시 정하면 사람이 검토한 내용과 실제 쓰기가
달라진다. 승인 범위를 고정하고, 그 범위 안에서도 되돌릴 수 없는 조치는 서버가
거부해야 한다. 명령별 결과를 보존하면 다음 사고의 대응 지식을 교정할 근거도 남는다.

## Decision Drivers

- 이번 사고의 런북이 실행의 직접 근거여야 한다. 실행되지 않은 절차는 검증되지 않는다.
- 실행은 사람의 명시적 승인 없이 시작되어서는 안 된다.
- 실행 대상을 장애 유형별 리셋 목록으로 고정하지 않되, 실제 명령은 승인한 범위 안에 있어야 한다.
- 되돌릴 수 없는 조치는 모델 판단과 무관하게 차단되어야 한다.
- 실행 실패가 이미 만들어진 분석 결과를 훼손해서는 안 된다.
- 실행 과정에서 발생한 명령 오류가 플레이북 개선에 쓰일 수 있어야 한다.

## Decision

플레이북 실행을 **분석과 분리된 별도 에이전트**가 담당하며, **사용자 승인
게이트**를 통과한 뒤에만 시작한다.

### 분석과 분리된 승인 게이트

분석 파이프라인은 정상화 런북을 먼저 제시하고 근본원인·운영 개선을 순차 진행한다.
분석은 확정 여부와 무관하게 어떤 서비스 변경도 수행하지 않는다. 실행은 사람이 명시적으로 요청할 때만
시작하며, 승인 없이 시작된 실행은 존재할 수 없다.

승인 요청은 어느 분석 엔진이 만든 리포트인지와 무관하게 같은 실행 경로로 들어간다.
엔진별 실행 경로를 두지 않는다 — 안전 정책이 두 곳에 복제되면 시간이 지나며
갈라지고, 한쪽의 정책 회귀가 다른 쪽 검증으로 드러나지 않는다.

승인은 **사람이 읽은 현재 런북의 정확한 내용**을 허가한다. 대시보드는 열람한 내용의
지문(digest, 내용이 같은지 비교하는 값)을 expectedDigest로 제출하고 승인 처리 시점의
내용과 비교한다.
다르면 승인 요청을 거부하고 새 내용을 검토하게 한다. 일치하는 승인 내용은
스냅샷(내용을 고정한 사본)으로 보존하고 지문을 실행 요청에 담는다.
실행 워커는 그 사본의 지문을 검증한 뒤 실행한다. 승인 뒤 회고나 재분석이 런북을
바꾸면 새 내용에는 새 승인이 필요하다.

여러 계정을 대상으로 하는 배포에서 승인은 플레이북 내용과 함께 **대상 계정과 리전**을
허가한다. 대상 좌표는 digest 계산 범위에 포함되며, 워커는 요청의 좌표가 승인 예약의
좌표와 다르면 실행하지 않는다([ADR infra/0009](../infra/0009-multi-account-rca-hub-spoke.md)).

대시보드는 큐 발행 전에 실행 항목을 `PENDING_APPROVAL`로 조건부 생성하고, 같은 RCA의
활성 실행 표식을 함께 예약한다. 워커는 큐 메시지만으로 실행 항목을 만들 수 없고 이미
예약된 항목만 `EXECUTING`으로 전이한다. 따라서 큐에 구조가 맞는 메시지를 직접 넣는
것만으로는 승인 사실을 만들 수 없다.

### 실행 근거는 승인된 런북

실행의 직접 근거는 플레이북 지식을 이번 사고에 적용한 **런북**이다. 런북은
승인 전에 확정된 대상·리전·순서·구체 명령과 인자·성공 기준을 보유한다.
승인 스냅샷과 digest는 이 내용을 모두 포함한다. 명령이 없는 과거 자연어
계획은 조회 가능하지만 새 승인과 실행은 거부한다.

실행 도구는 단계 식별자뿐 아니라 요청 명령과 대상이 승인된 목록과 일치하는지
서버에서 확인한다. 실행 중 모델이 새 명령을 만들거나 인자·대상을 교정해 실행할 수 없다.
변경이 필요하면 실행을 해결로 처리하지 않고 사유와 증거를 남기며 새 런북과 승인을 요구한다.
동일 명령의 일시 오류 재시도와 읽기 전용 사후 관측은 승인된 범위 안에서만 허용한다.
사후 관측에 필요한 조치 시각은 같은 실행의 서버 기록에서 결정하고, 모델이
관측 대상·성공 기준·시간 구간을 바꾸는 근거로 사용할 수 없다.

런북의 각 단계는 순서 있는 완성된 명령 목록, 승인된 배포 수렴 확인 또는 아래 고정 구간 사후 관측 연산을 가진다.
사후 관측 연산은 메트릭 좌표·리전·알람·기준 조치·대기 한도를 승인 전에 명시한다.
서버는 승인된 연산에 같은 실행의 조치 종료 시각 또는 배포 수렴 최초 확인 시각을
해당 조치의 계약에 맞게 결합하여 읽기 전용 조회를 만든다.
이 연산은 명령 목록과 구별해 화면에 표시하며, 모델이 임의의 조회 명령이나 좌표를
끼워 넣는 우회 경로로 사용할 수 없다. 관측은 두 60초 구간이며 대기 한도는 900초다.

서버는 승인 단계와 단계 내부 명령의 순서를 검사하고, 성공한 쓰기 명령을 다시
수행하지 않는다. 해결은 필수 명령 전체의 수행과 각 단계 성공 기준 관측이 있을 때만
성립한다. 명령 누락이나 승인 범위 변경 거부가 있으면 모델의 해결 선언으로 덮을 수 없다.

선행 명령이 일반 오류로 실패하면 후속 쓰기를 시작하지 않는다. 승인된 진단용
읽기는 계속할 수 있으며, 동일 명령의 허용된 재시도가 성공하면 다음 명령으로
진행할 수 있다. 명령의 마지막 시도가 실패했거나 아직 끝나지 않았다면 이전 성공
기록만으로 해결을 판정하지 않는다. 뒤이은 시도가 관측을 바꾸면 성공 기준도 다시 확인한다.

선언되지 않은 단계에는 명령을 실행하거나 성공 결과를 기록할 수 없다.
그 호출의 거부 사실은 감사 증거로 남긴다. 거부 기록을 승인된 단계의 실행 증거로
간주하거나 모델의 해결 선언으로 덮지 않는다.

### 안전 경계 — 파괴적 액션 거부

실행 대상은 **승인된 런북의 리소스와 리전**으로 한정한다. 지원할 리소스 종류를
장애 유형별 허용 목록으로 고정하지 않으며, 승인 범위와 별도로 **되돌릴 수 없는
조치를 거부 목록으로 차단**한다.

판정은 **제어 평면 작업 이름의 어휘**를 기준으로 한다. 다음 의미를 가진 작업은
거부한다.

- 리소스·인스턴스·클러스터의 삭제와 영구 종료
- 데이터·스냅샷·백업·아카이브의 삭제
- 자격 증명·정책·권한 부여의 회수와 삭제
- 계정·조직 수준의 구성 변경

다음 작업은 승인된 명령·대상·순서와 일치하고 서버 판정을 통과할 때 허용한다.

- 모든 조회와 관측
- 재시작, 롤링 배포, 스케일 조정
- 구성 값의 변경과 되돌리기
- 검증 환경의 장애 리셋

**판정은 서버가 수행한다.** 실행 에이전트의 프롬프트 지시로 제한하지 않는다.
프롬프트만으로 세운 경계는 우회될 수 있으므로, 실행 도구가 명령을 파싱해 작업
이름을 추출하고 거부 어휘와 대조한 뒤 실행 여부를 결정한다. 작업 이름을 추출할 수
없는 명령은 판정할 수 없으므로 거부한다 — 판정 불가를 허용으로 해석하면 거부
목록이 무력화된다.

차단된 명령은 실행 증거에 차단 사실과 사유로 기록되고, 해당 절차는 수동 조치
필요로 남는다. 이 정책 차단은 일반 명령 실패와 구별한다. 차단이 실행 전체를
중단시키지는 않으며 나머지 승인된 절차를 수행할 수 있다. 수동 조치가 남은
실행을 해결로 판정하지 않는다.

### 실행 증거

플레이북의 정확성을 개선하려면 무엇이 어떻게 실패했는지가 명령 단위로 남아야 한다.
실행 증거는 각 시도마다 다음을 보유한다.

- 실행 중이던 플레이북 절차의 식별자
- 실행한 명령과 전달한 인자
- 종료 상태와 오류 출력
- 실패의 분류
- 동일 명령 재시도 내역과 새 승인이 필요한 교정 사유
- 관측 결과

증거는 실행 단위로 누적되며 실행이 끝난 뒤에도 보존된다. 실패한 실행의 증거도
사람이 읽을 수 있어야 한다.

### 해결 판정과 완료

실행 에이전트는 절차 수행 후 이슈가 해소되었는지 관측하고, 그 결과로 실행 상태를
확정한다. 해소가 확인되면 완료로 전이한다. 해소되지 않았거나 관측으로 확정할 수
없으면 완료로 전이하지 않는다 — 관측 실패를 해결로 추정하면 미해결 장애가 완료로
기록된다.

### 조치 이후 고정 구간의 제한된 관측 대기

승인된 검증 절차는 같은 실행에서 앞선 승인 조치의 실제 성공 시도를 기준으로
읽기 전용 지표 도착을 기다릴 수 있다. ECS 태스크 중지는 서버가 기록한 최초 성공
시도의 종료 시각을 사용한다. ECS 서비스 갱신(UpdateService)은 아래 배포 수렴의
최초 서버 확인 시각을 사용한다. 조회 명령·실패한 조치·다른
실행이나 뒤의 절차·모델이 제시한 시각은 기준이 될 수 없다.

서버는 조회 전에 요청과 조치 시도, 기준 시각, 첫 두 개의 완결된 60초 구간을
영속화한다. 첫 구간은 해당 기준 시각이 속한 분의 다음 분 경계부터 시작하며,
기준 시각이 정확히 분 경계여도 다음 분을 사용한다.
같은 검증 절차의 재호출은 같은 요청의 종결 기록을 반환하고, 다른 인자나 조치로
구간을 옮기거나 중단된 대기 예산을 다시 시작할 수 없다.

지표의 분류 영역(namespace)·이름·대상 구분값(dimensions)·리전은 명시적 입력이며 승인된 현재 문맥과 실제
조회 증거에 연결되어야 한다. 각 고정 구간은 기록 시도 합계가 양수이고 실패 합계가
0이어야 한다. 두 값의 차이는 실제 생산자의 완료된 쓰기 집계 의미가 증명될 때만
성공한 쓰기 수로 남긴다. 집계 의미가 확인되지 않으면 차이는 산술 관측으로만 남기고,
모델은 실제 쓰기 성공을 별도로 관측해야 한다. 승인된 성공 기준이 조회 지연도
요구하는 경우에만 선택적으로 실제 조회 지표의 표본 수(SampleCount)가 양수인지와 해당 알람에서
관측한 통계·단위·임계치 충족 여부를 검증한다. 지연 검증이 없는 승인 절차에 새 지표나
알람을 강제하지 않는다. 필요한 알람 메타데이터를 해석할 수 없으면 성공을 추정하지 않는다.
조회 성공 로그를 쓰기 성공으로 간주하지 않으며 정확한 대상 알람의 OK와 소유자의
해제·롤백 완료는 승인된 성공 기준에 따라 별도로 확인한다.

누락 값은 0이 아니다. 조치 이전·겹치는 구간과 진행 중 구간은 성공 증거에서
제외하고 비유한 수·중복·분 경계와 맞지 않는 자료는 거부한다. 완결된 고정 구간에서
한 번이라도 비정상 값을 관측하면 실패를 종결하며 이후 정상 값으로 덮어쓰지 않는다.
부분 데이터·오류·비정상 값을 포함한 모든 조회의 UTC 관측 시각과 명령 출력은 실행
증거로 보존한다.

대기는 최대 900초이며 기존 실행 전체 예산 3600초의 남은 시간과 실행 MCP 도구 호출의 1200초 한도 안에서만
수행한다. 실행 예산을 연장하지 않는다. 대기와 각 명령 중 취소·실행 소유권·기한을
계속 확인하고, 이를 확인할 수 없거나 소유권을 잃으면 즉시 중단한다. 명령도 남은
예산 안에서 종료되도록 제한한다. 조회는 기존 명령 판정과 감사 경로를 거치며 셸이나
쓰기 권한을 추가하지 않는다. 대기 결과는 관측 영수증이며 전체 실행을 자동으로
해결 처리하거나 승인된 성공 기준을 바꾸지 않는다.

### 정상 기준에 연결된 승인 배포와 수렴

배포 롤백은 실제 장애 이전 정상 저장이 입증된 불변 기준을 사용한다.
[초기 스코핑](0001-initial-scoping-and-report-similarity.md)과
[증거 저장](../infra/0002-evidence-storage.md)의 버킷·허용 영역·지문·실행·서비스·
장애 이전 시각 검증을 통과한 사실만 런북의 정상 대상 근거가 된다. 이전/최대 리비전
번호나 `latest` 태그로 정상 대상을 추정하지 않는다.

| 의무 | 관측 가능한 충족 결과 |
|---|---|
| 정상화 근거와 원인 판정을 구분한다. | 원인 확정 전에도 서버가 정상 기준·현재 대상·입력 호환성·고정 롤백을 검증하고 정상화 단계 완료를 보존하면 사용자 승인이 가능하다. 근거 없는 미확정 명령은 승인하지 않으며 원인 신뢰도·검증 한도는 낮추지 않는다. |
| 현재 결함 대상과 정상 대상을 승인 전에 고정한다. | 계정·리전·클러스터·서비스·컨테이너, 결함 태스크 정의·이미지, 정상 태스크 정의·이미지 지문·정상 저장 근거가 승인 사본에 포함된다. |
| 승인 대상과 명령의 일치를 검사한다. | UpdateService 명령·인자·순서와 유지할 서비스 설정, 수렴 조건, 사후 지표 좌표·단위·통계·알람·기준·시간 규칙이 기존 expectedDigest와 실행 사본 지문 범위에 들어간다. |
| 생성기·대시보드·실행 워커는 같은 필수 단계와 입력을 검증한다. | 생성 가능한 수렴·관측 단계를 화면에서 검토할 수 있고 불완전한 단계는 승인·실행되지 않는다. |
| 승인 전과 쓰기 직전에 현재 결함 대상·설정을 다시 확인한다. | 다른 배포나 설정 변경이 개입하면 쓰기를 중단하고 새 검토를 요구한다. 다른 주체가 정상화한 결과는 해당 실행의 조치 성공이 아니다. |
| 실제 실행 역할과 목표 리비전이 유효해야 한다. | 롤백·읽기 권한 또는 대상 리비전의 유효성이 확인되지 않으면 배포를 시작하지 않는다. |
| API 성공과 배포 수렴을 분리한다. | 승인 정상 태스크 정의·이미지로 실제 앱 태스크가 전환되고 결함 버전과 혼재가 끝나야 수렴한다. |
| 배포 수렴은 서비스와 실제 태스크를 함께 확인한다. | 배포·실행·대기·정상 상태와 컨테이너별 태스크 정의·이미지가 승인 기대 상태와 맞는다. 일부 정상 태스크나 일반 대기 명령 성공만으로 통과하지 않는다. |
| 배포 수렴 확인을 최대 900초로 제한한다. | 상한·기존 실행 남은 시간·해당 도구 호출 남은 시간 중 최솟값에 종결되며 재호출로 시작점을 초기화하지 않는다. |
| 최초 수렴 확인 UTC 시각을 서버가 영속화한다. | 모델이 기준 시각이나 관측 대상을 선택하지 못하며 수렴 이후 다음 분부터 첫 두 완결된 60초 구간이 고정된다. |
| 사후 메트릭 도착을 별도 최대 900초로 제한한다. | 수렴 이후 대기를 시작하되 실행·도구 남은 예산을 넘지 않고 같은 요청의 재시도도 구간·기한을 연장하지 않는다. |
| 고정 두 구간과 실제 저장 성공을 모두 확인한다. | 각 구간 저장 시도 양수·실패 0, 해당 실패 알람 OK, 실제 저장 완료 증거가 있어야 한다. 생산자 계수 의미가 입증되지 않으면 저장 완료 로그 또는 조회 검증이 필요하다. |
| 증거 부족을 해결로 추정하지 않는다. | 남은 예산으로 두 구간을 확보하지 못하거나 누락·진행 중·배포 혼재가 있으면 미해결로 남는다. |

태스크 중지의 기존 관측 의미와 선택적 조회 지연 검증은 유지한다. 배포 조치는
수렴 확인 단계를 거쳐야 사후 관측에 진입한다. 수렴과 메트릭 대기에도 실행 전체의
3600초 강제 종료 기한은 유지하며 도구 호출 한도는 1200초다. 각 호출은 자기 남은 시간 안에서
끝나며 두 대기를 하나의 호출에서 수행하는 경우에도 그 호출의 한도를 공유한다.
재시도마다 취소·소유권·기한을 확인하고 늦은 결과가 종결 기록을 덮지 못하게 한다.

서버는 승인된 좌표·규칙에 실제 수렴 시각만 결합한다. 모델이 중간에 리소스·명령·
인자를 교정하는 권한은 생기지 않는다. 모든 필수 명령, 정상 배포 수렴과 사후 저장
회복이 입증될 때만 해결(RESOLVED)로 판정한다. 운영자 정리는 별도 결과이며 자동 성공이
아니다. 플레이북 라이브러리·변경 제안·보고서 요약·승인 사본 보존 경계는 유지한다.

### 실행 전체 기한과 도구 대기

실행 전체는 기존 **3600초 강제 종료 기한**을 유지한다. 배포 수렴과 사후 메트릭 대기는
**각각 최대 900초**, 실행 MCP 도구 호출은 **1200초**다. 각 대기의 실제 한도는 자기
상한·실행 전체의 남은 시간·해당 도구 호출의 남은 시간 중 최솟값이다. 두 대기를 한
도구 호출에서 수행하면 1200초를 공유하며 재호출로 기한을 초기화하지 않는다.

Strands SDK의 활성 응답 보호는 이 실행 워커의 전체 기한을 해제하지 않는다.
Headless 실행에 새 응답별 SDK 한도를 추가하지 않으며 기존 전체 강제 종료·취소·
소유권 상실 제어와 늦은 쓰기 차단을 유지한다. 승인 내용·순서·소유권 및 최초 수렴
이후 두 완결된 60초 복구 구간은 바꾸지 않는다.

### 생명주기 분리

분석 세션과 실행은 서로 다른 생명주기를 가진다. 실행의 승인·미승인·실패·취소·종료는 뒤 원인·운영 분석의 진행 조건이 아니다.
실행 실패가 분석 세션을 실패로 만들지 않으며 각 분석 사본과 이미 확인된 실행 결과를
서로 덮어쓰지 않는다. 분석 전체 취소와 실행 취소는 각각의 범위를 갖는다.

실행 상태의 허용 전이는 다음과 같다.

- 승인 대기 → 실행 중 (워커가 승인 예약의 처리 소유권인 claim을 획득)
- 실행 중 → 검증 중 → 해결 / 미해결
- 실행 중 → 실패 / 취소

해결은 실행의 종료 상태이며 회고의 진입 조건이다
([ADR 0018](0018-playbook-retrospective.md)). 미해결과 실패는 회고로 진행하지
않는다.

### 멱등성

같은 승인 요청이 재전달되어도 실행이 중복되어서는 안 된다. 실행 요청은 안정적인
식별자를 가지며, 실행 주체는 claim으로 단일 실행을 보장한다. 외부 쓰기는 claim에
종속된 부작용 lease(외부 변경을 시작할 수 있는 유효 기간) 안에서만 시작한다
([ADR infra/0006](../infra/0006-session-recovery-on-restart.md)).

서로 다른 식별자를 가진 동시 승인도 같은 RCA의 활성 실행 표식에 대한 조건부 쓰기로
하나만 성립한다. claim이 만료된 실행은 자동으로 처음부터 재수행하지 않고 실패로
종결해 새 사용자 승인을 요구한다. 이전 워커가 외부 명령을 수행한 뒤 종료됐는지 알 수
없는 상태에서 자동 재수행하면 한 번의 승인이 두 번의 쓰기가 되기 때문이다.

### 조기 런북 승인과 개정본 권위

조기 승인은 현재 사고의 정상화 파트가 저장·검증을 마친 롤백만 대상으로 한다.
실제 정상 기준·현재 배포·입력 호환성·장애 이전 정상 저장, 고정 명령·대상·리전·순서·
성공 기준이 필수다. 전체 RCA 완료나 근본원인 확정을 앞당겨 기록하지 않는다.
원인이 미확정임을 표시하며 모델의 안전 선언이나 추정 대상은 승인 권위가 아니다.

열람 지문 대조, 실제 ECS 현재/정상 전제 검사, 불변 승인 사본 저장 뒤 조건부로 실행을
예약한다. 이 예약은 같은 정상화 개정·지문이 승인 적격이며 철회되지 않았음을 확인하는
조건과 단일 활성 실행 예약을 함께 보장한다. 읽기 뒤 교체·철회된 런북은 예약되지 않는다.
조기 결과가 없던 기존 기록은 기존 완료·확정 경로를 유지하며, 새 결과의 오류·철회를
이전 공개 런북으로 우회하지 않는다.

승인 후 보고서 갱신은 실행 사본을 바꾸지 않는다. 같은 승인 ID의 큐 재전송은 기존
사본을 그대로 사용하고 다른 내용에는 새 승인을 요구한다. 승인 전 철회와 이미 시작한
실행 취소를 혼용하지 않으며, 실행 취소·소유권·기한과 쓰기 직전 전제 검사는 기존대로
검증한다. 삭제·권한 변경 등 파괴적 액션 차단도 그대로 적용한다.

이후 분석에서 원인·운영 제안을 만들었다는 이유로 미실행 절차를 검증됨으로 승격하지
않는다. 해결된 실행의 회고·절차 동일성·새 승인 조건은 유지한다.

## Consequences

### Positive

- 플레이북이 실행 근거가 되므로 절차의 정확성이 실행으로 검증된다.
- 실행 시점이 사람의 통제 아래 있어 오판이 즉시 쓰기 작업으로 이어지지 않는다.
- 사고별 런북을 승인하므로 장애 유형별 리셋 목록 밖의 조치도 검토할 수 있다.
- 실행 경로가 하나이므로 안전 정책을 한 곳에서 유지한다.
- 명령 단위 증거가 남아 플레이북 개선의 입력이 된다.
- 실행 실패가 분석 결과를 훼손하지 않는다.

### Negative

- 사람 승인이 필요하므로 무인 시간대의 자동 복구 효과가 사라진다.
- 승인 내용 일치 검사와 파괴적 액션 판정을 각각 유지해야 한다.
- 명령별 시도와 관측을 보존하므로 실행 증거의 저장량이 늘어난다.
- 실행 상태가 분석 세션과 별도로 관리되어 조회 경로가 늘어난다.

### Risks

- 거부 어휘에 없는 파괴적 작업이 통과할 수 있다. 판정 불가 명령을 거부로
  처리하고 거부 어휘의 확장을 회귀 테스트로 고정한다.
- 명령 파싱을 우회하는 형태로 파괴적 작업이 전달될 수 있다. 셸 합성과 중첩 호출을
  판정 불가로 분류해 거부한다.
- 플레이북 절차가 틀리면 실행이 무의미한 명령을 수행할 수 있다. 파괴적 액션이 아닌
  범위에서는 되돌릴 수 있으므로, 회고가 절차를 교정하는 경로로 흡수한다.
- 관측으로 해결을 확정할 수 없는 장애는 완료로 전이하지 않아 미해결이 누적될 수
  있다. 완료 판정을 추정으로 대체하지 않고 사람이 증거를 읽는 경로를 유지한다.
- 승인 요청이 재전달되면 실행이 중복될 수 있다. 안정 식별자와 claim, 부작용
  lease로 단일 실행을 보장한다.
- 승인 뒤 실행 전에 플레이북이 바뀌면 사람이 보지 않은 절차가 실행될 수 있다.
  승인 시점 스냅샷과 digest를 실행 입력으로 고정하고 불일치 요청을 거부한다.
- 모델이 승인되지 않은 단계나 명령을 호출할 수 있다. 실행 도구는 승인 스냅샷과
  대조해 거부 사실을 남기며, 거부 기록을 단계의 성공 증거로 사용하지 않는다.
