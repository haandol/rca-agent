# ADR 0012: 자동 복구 실행 경계

Date: 2026-04-23
Updated: 2026-07-21

## Status

Accepted (2026-07-21)

## Context

자동 RCA가 근본원인을 찾더라도 복구 실행 주체와 안전 경계가 없으면 MTTR을 줄일
수 없다. 반대로 분석 모델에 일반적인 HTTP·셸·인프라 쓰기 권한을 주면 오판이
실제 장애 확대로 이어질 수 있다.

Strands와 CC Headless는 오케스트레이션 방식이 다르다. Strands는 분석 파이프라인이
코드로 고정되어 있어 외부 이벤트 기반 복구가 적합하다. CC Headless는 하나의
실행 안에서 전문 서브 에이전트를 조정할 수 있으므로 별도 복구 워커를 거치지 않고
동일 실행에서 제한된 복구를 수행할 수 있다.

## Decision Drivers

- 미확정 근본원인에는 자동 쓰기 작업을 수행하지 않아야 한다.
- 모델이 임의 URL, 셸 명령, 일반 ECS 변경을 실행할 수 없어야 한다.
- 중복 호출에도 복구 액션이 안전해야 한다.
- 복구 결과와 사후 검증 상태가 최종 보고서에 남아야 한다.
- 엔진별 실행 모델을 존중하면서도 동일한 안전 정책을 적용해야 한다.

## Decision

자동 복구는 엔진별 오케스트레이션 경계를 사용하되 공통 안전 정책을 따른다.

### 공통 안전 정책

- 최신 RCA 검증 산출물에 확정 근본원인이 없으면 실행하지 않는다.
- 복구 도구는 모델이 전달한 확정 여부를 신뢰하지 않고 산출물을 직접 검증한다.
- 자동 액션은 멱등적인 Healthcare 장애 리셋 허용 목록으로 제한한다.
- 지원하지 않는 원인은 임의 대체 조치 없이 fail-closed로 종료한다.
- 복구 후 관측 결과는 정상화, 실패, 관측 대기로 구분한다.
- 이벤트와 모델 출력은 복구 시작의 힌트일 뿐 확정 여부의 권위가 아니다. 복구
  실행 주체는 서버 소유 세션과 검증 산출물을 다시 읽어 일치 여부를 확인한다.
- 가설 생성·분기 단계가 제안한 복구 유형은 실행 권한을 부여하지 않는다. 검증
  단계가 수집 증거를 바탕으로 독립 확정해 서버 소유 산출물에 저장한 원인 유형만
  허용 목록 액션과 매핑한다. 설명, 증거, 확정 상태, 검증 원인 유형 중 하나라도
  없거나 서로 일치하지 않으면 `UNSUPPORTED`로 fail-closed 처리한다.

### CC Headless

CC Headless의 Remediation 서브 에이전트가 같은 실행 안에서 제한된 복구 도구를
사용한다. 복구 도구는 확정 근본원인과 허용 목록을 서버 측에서 확인한 뒤 해당
리셋만 호출한다. 임의 HTTP 요청과 ECS 강제 배포는 허용하지 않는다.
복구 lease를 획득하기 전에 현재 claim에 저장된 원본 알람의 namespace, metric,
dimensions를 배포 시 주입한 Healthcare ECS cluster/service 또는 RDS instance
식별자와 정확히 비교한다. 확정 fault 유형과 허용 metric 조합이 다르거나 대상
리소스가 일치하지 않으면 모델 산출물이 유효해도 reset을 시작하지 않는다.

복구 결과는 Report 서브 에이전트에 전달되고 최종 보고서와 플레이북에 반영된다.
복구 실패는 RCA 세션을 폐기하지 않으며, 보고서는 실패 원인과 수동 조치 필요성을
기록한다.

복구 도구는 액션 결과와 별도로 제한된 시간 동안 원래 CloudWatch 알람과 지표를
관측한다. 서버가 판정한 `NORMALIZED`, `FAILED`, `PENDING` 상태가 복구 결과의
권위이며 Report 에이전트는 이를 그대로 반영한다. CloudWatch 조회 실패나 관측
시간 부족은 성공으로 간주하지 않고 `PENDING`으로 남긴다.
판정은 원본 알람의 period, evaluation periods, datapoints-to-alarm,
missing-data 정책을 보존한 M-of-N 규칙을 따른다. 복구 이후의 완전한 period만
사용하며, 필요한 관측 구간이 채워지지 않았거나 missing-data 정책으로 상태를
확정할 수 없으면 정상화로 추정하지 않고 `PENDING`으로 남긴다.

CC Headless 완료 이벤트는 Strands의 외부 복구 워커 진입 이벤트와 분리한다. 같은
RCA에서 내부 복구와 외부 복구가 중복 실행되거나 외부 워커의 더 넓은 액션으로
우회되는 것을 차단한다.

### Strands

Strands는 분석 완료 이벤트와 별도 복구 워커를 사용하는 비동기 경계를 유지한다.
복구 워커는 독립적으로 활성화할 수 있으며 기본적으로 비활성 상태를 유지한다.
이를 통해 Strands 분석 태스크가 서비스 쓰기 권한을 직접 소유하지 않게 한다.
워커는 이벤트의 확정 플래그나 원인 문자열을 직접 신뢰하지 않고 서버 소유 RCA
결과를 조회해 검증한다. 검증 자료가 없거나 불일치하면 실행하지 않으며, 허용된
Healthcare 리셋 외의 일반 ECS 변경으로 대체하지 않는다.

Strands 검증기는 가설의 초기 복구 유형과 별도로 증거 기반
`validated_fault_type`을 산출한다. RCA 완료 상태와 선택 가설에는 이 검증 유형을
함께 원자적으로 기록하고, 복구 워커는 선택 가설의 확정 상태, 증거 요약,
검증 유형이 세션의 유형과 일치할 때만 리셋 lease를 획득한다.

복구 결과 발행은 DynamoDB 세션을 durable outbox로 사용한다. 복구 결과, 검증
결과, 결정적 `publication_id`가 포함된 알림 payload, `PENDING` 상태를 복구 claim
완료와 하나의 조건부 쓰기로 먼저 저장한다. 이후 별도 publication lease 소유자만
저장된 payload를 SNS에 발행하고 `SENT`로 전이한다. 발행 실패와 publication
경합은 SQS 메시지를 확인하지 않아 재전달되게 하며, 완료된 복구 claim은 다시
실행하지 않는다.

복구 claim과 publication lease는 reset, CloudWatch 관측 대기, 제한된 AWS SDK
호출, 선택적 LLM 요약, SNS 재시도와 `SENT` 기록의 최악 실행 시간보다 길게
계산한다. 표준 SNS는 저장소와 원자적으로 묶을 수 없어 발행 성공 직후 프로세스가
종료되면 같은 payload가 재발행될 수 있다. 모든 소비자는 `publication_id`를
멱등성 키로 사용해야 한다.

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 모든 엔진이 공통 외부 복구 워커 사용 | 복구 정책과 권한을 한 곳에 집중할 수 있다. | CC Headless의 실행 컨텍스트가 이벤트 변환 과정에서 손실되고 복구 시작이 지연된다. |
| 모든 엔진이 분석 태스크에서 직접 복구 | 메시지 홉이 없고 구현 경로가 짧다. | Strands 분석 태스크까지 쓰기 권한을 가지며 엔진별 안전 경계를 약화한다. |
| 엔진별 오케스트레이션 + 공통 fail-closed 정책 | 각 엔진의 실행 모델에 맞으면서 확정·허용 목록 정책을 공유한다. | 복구 진입점이 둘이므로 정책 회귀 테스트를 양쪽에 유지해야 한다. |

## Consequences

### Positive

- CC Headless는 별도 복구 큐 없이 분석 직후 제한된 복구를 수행한다.
- Strands는 분석과 쓰기 권한의 인프라 분리를 유지한다.
- 지원하지 않는 원인에 대한 일반적인 강제 배포가 차단된다.
- 복구 실패도 최종 보고서에 관찰 가능한 결과로 남는다.
- 실제 CloudWatch 정상화 여부와 보고서 표현이 서버 판정을 통해 일치한다.
- 복구 완료 저장 실패가 결과 이벤트 선행 발행이나 복구 액션 재실행으로 이어지지
  않는다.

### Negative

- 두 실행 경로의 안전 정책이 장기적으로 드리프트할 수 있다.
- CC Headless 태스크는 Healthcare 서비스로의 제한된 네트워크 접근이 필요하다.
- 메트릭 반영 지연 때문에 즉시 검증 결과가 관측 대기로 남을 수 있다.
- 제한된 관측 시간만 사용하므로 늦게 정상화되는 장애는 후속 관측이 필요하다.
- 원본 알람의 평가 구간이 길수록 M-of-N 정상화 판정까지 더 오래 걸릴 수 있다.
- 표준 SNS의 at-least-once 전달 때문에 결과 이벤트 소비자는 `publication_id`
  중복 제거를 유지해야 한다.

### Risks

- 프롬프트만으로 권한을 제한하면 우회될 수 있다. 쓰기 도구 자체가 확정 산출물,
  액션 허용 목록, 대상 서비스를 검증한다.
- 같은 알람이 재처리되면 복구가 반복될 수 있다. 리셋 API의 멱등성과 세션
  멱등성 키를 함께 사용한다.
- 세션 reclaim과 복구 호출이 겹치면 이전 실행이 늦게 쓰기를 시작할 수 있다.
  복구 호출은 claim에 종속된 부작용 lease 안에서만 시작한다.
- 엔진 완료 이벤트가 혼선되면 두 복구 경로가 중복 실행될 수 있다. 엔진별 이벤트
  경계를 분리하고 계약 테스트로 고정한다.
- 엔진별 정책이 달라질 수 있다. 공통 계약 테스트에서 확정 게이트와 fail-closed
  동작을 검증한다.
