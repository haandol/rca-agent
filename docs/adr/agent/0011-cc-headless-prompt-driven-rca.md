# ADR 0011: CC Headless 전문 서브 에이전트 오케스트레이션

Date: 2026-04-22
Updated: 2026-07-21

## Status

Accepted (2026-07-21)

## Context

CC Headless는 하나의 장시간 실행 안에서 스코핑, 가설 탐색, 증거 수집, 보고서
작성, 복구 권고를 수행한다. 단일 에이전트가 모든 책임을 직접 수행하면 프롬프트가
커지고, 분석용 읽기 권한과 복구용 쓰기 권한의 경계가 흐려지며, 각 단계의 성공과
실패를 독립적으로 검증하기 어렵다.

Claude Code의 서브 에이전트는 같은 실행 컨텍스트 안에서 역할별 지시와 도구
허용 범위를 분리할 수 있다. 이를 이용하면 별도 워크플로 엔진을 추가하지 않고도
RCA, 복구, 보고서 책임을 명시적으로 나눌 수 있다.

## Decision Drivers

- RCA 증거 수집은 서비스 변경 권한 없이 읽기 전용으로 수행되어야 한다.
- 복구는 근본원인이 확정되고 허용 목록에 매칭될 때만 실행되어야 한다.
- 복구 실패가 RCA 결과와 최종 보고서 생성을 막아서는 안 된다.
- 최종 보고서는 권고가 아니라 실제 복구·검증 결과를 구분해 기록해야 한다.
- 한 알람의 산출물과 서브 에이전트 실행은 다른 실행과 격리되어야 한다.

## Decision

CC Headless의 메인 에이전트는 직접 분석하거나 복구하지 않는 오케스트레이터로
동작하며, 한 실행 안에서 다음 전문 서브 에이전트를 순차 호출한다.

1. **RCA 에이전트**는 관측·변경 이력·코드 정보를 읽어 스코핑, 가설 생성,
   증거 수집, 검증을 수행한다. 서비스나 인프라를 변경할 수 없다.
2. **Remediation 에이전트**는 RCA 산출물에 확정 근본원인이 있을 때만 호출된다.
   복구 도구도 확정 산출물을 다시 검증하며, 허용된 장애 리셋만 실행한다.
   미확정 원인과 지원하지 않는 원인은 fail-closed로 종료한다.
3. **Report 에이전트**는 RCA와 복구 결과를 받아 최종 보고서와 플레이북을
   생성한다. 복구 미실행, 성공, 실패, 검증 대기를 명시적으로 구분한다.

실행 순서는 `RCA → 조건부 Remediation → Report`이다. RCA가 미확정이어도 Report
에이전트는 실행된다. Remediation이 실패해도 Report 에이전트는 실패 원인과
수동 조치 요구를 포함한 보고서를 생성한다.

메인 오케스트레이터와 모든 서브 에이전트는 실행별 격리 컨텍스트를 공유한다.
산출물 저장은 제한된 저장 도구만 사용하며, wrapper가 산출물을 감지하여 세션
트레이스를 기록한다. 세션은 전체 오케스트레이션 동안 분석 중 상태를 유지하고,
필수 보고서와 플레이북이 모두 저장된 뒤에만 완료된다. 완료 게이트는 파일 존재만
확인하지 않고 RCA, 서버 소유 복구 결과, 보고서, 플레이북의 상태·원인·검증 참조가
서로 일치하는지 검증한다. 모델이 서버 소유 복구 결과를 누락하거나 과장하면
세션을 완료하지 않고 재전달 대상으로 남긴다.

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 단일 CC 에이전트가 전체 흐름 직접 수행 | 컨텍스트 전달이 단순하고 호출 수가 적다. | 역할과 권한이 결합되어 복구 안전 경계와 단계별 검증 요구를 충족하지 못한다. |
| 외부 워크플로 엔진이 단계별 CC 실행을 조정 | 단계 격리와 재시도가 명확하다. | 실행 간 컨텍스트 전달과 인프라가 늘어나며 한 알람의 자율 탐색 흐름이 단절된다. |
| 단일 CC 실행 안의 전문 서브 에이전트 | 컨텍스트를 유지하면서 역할·도구·산출물 계약을 분리할 수 있다. | 같은 프로세스 경계를 공유하므로 쓰기 도구 자체에도 서버 측 안전 검증이 필요하다. |

## Consequences

### Positive

- 분석, 복구, 보고서 책임과 실패 경계가 명확해진다.
- RCA 에이전트는 읽기 전용 도구만 사용한다.
- 최종 보고서가 실제 복구 결과를 포함한다.
- 별도 CC 복구 워커와 메시지 홉 없이 한 실행에서 복구를 시작할 수 있다.

### Negative

- 서브 에이전트 간 결과 계약과 프롬프트 회귀 테스트를 유지해야 한다.
- 여러 서브 에이전트 호출로 토큰 사용량과 실행 시간이 증가할 수 있다.
- 같은 런타임 안의 논리적 권한 분리만으로는 충분하지 않아 복구 도구가 자체
  검증을 중복 수행해야 한다.

### Risks

- 오케스트레이터가 잘못된 순서로 에이전트를 호출할 수 있다. 필수 산출물과
  호출 순서를 계약 테스트로 고정한다.
- RCA 결과가 미확정인데 복구를 요청할 수 있다. 복구 도구가 최신 검증 산출물을
  직접 확인하여 차단한다.
- Report 에이전트가 복구 상태를 과장할 수 있다. 복구 결과가 없으면 미실행으로,
  실패 결과가 있으면 실패로 기록하도록 산출물 계약과 완료 전 교차 검증을
  강제한다.
