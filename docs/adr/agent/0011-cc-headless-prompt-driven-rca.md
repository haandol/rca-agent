# ADR 0011: CC Headless 전문 서브 에이전트 오케스트레이션

Date: 2026-04-22
Updated: 2026-07-31

## Status

Accepted (2026-07-30)

## Context

CC Headless는 하나의 장시간 실행 안에서 스코핑, 가설 탐색, 증거 수집, 보고서
작성을 수행한다. 단일 에이전트가 모든 책임을 직접 수행하면 프롬프트가 커지고,
각 단계의 성공과 실패를 독립적으로 검증하기 어렵다.

이 실행은 **분석만 수행하고 어떤 쓰기 작업도 하지 않는다.** 복구는 사용자 승인 뒤의
별도 에이전트가 수행한다([ADR 0017](0017-playbook-execution-agent.md)). 분석 실행에
쓰기 권한이 없으므로 읽기·쓰기 경계를 한 프로세스 안에서 논리적으로 나눌 필요도 없다 —
경계는 프로세스와 태스크 역할이 물리적으로 세운다.

Claude Code의 서브 에이전트는 같은 실행 컨텍스트 안에서 역할별 지시와 도구
허용 범위를 분리할 수 있다. 이를 이용하면 별도 워크플로 엔진을 추가하지 않고도
증거 수집과 보고서 작성 책임을 명시적으로 나눌 수 있다.

이 오케스트레이션의 동작은 대부분 코드가 아니라 하네스 자산(에이전트 정의,
스킬, 워크스페이스 계약, 프롬프트)이 결정한다. 하네스를 로컬에서 다듬고
클라우드용으로 다시 옮겨 쓰면 두 벌이 갈라지고, 로컬에서 관찰한 품질이 배포
동작을 보증하지 못한다. 따라서 로컬에서 검증한 하네스가 변형 없이 그대로
배포 대상이 되어야 한다.

## Decision Drivers

- 분석 실행 전체가 서비스 변경 권한 없이 읽기 전용으로 수행되어야 한다.
- 보고서 생성이 증거 수집 결과와 독립적으로 검증 가능해야 한다.
- 한 알람의 산출물과 서브 에이전트 실행은 다른 실행과 격리되어야 한다.
- 로컬에서 검증한 하네스와 배포된 하네스가 동일 소스에서 나와야 한다.

## Decision

CC Headless의 메인 에이전트는 직접 분석하지 않는 오케스트레이터로 동작하며, 한
실행 안에서 다음 전문 서브 에이전트를 순차 호출한다.

1. **RCA 에이전트**는 관측·변경 이력·코드 정보를 읽어 스코핑, 가설 생성,
   증거 수집, 검증을 수행한다. 서비스나 인프라를 변경할 수 없다.
2. **Report 에이전트**는 RCA 산출물을 받아 플레이북을 포함한 최종 리포트를
   생성한다([ADR 0007](0007-rca-report-generation.md)). 근본원인 확정 여부와
   플레이북이 아직 검증되지 않은 초안임을 명시적으로 구분한다.

실행 순서는 `RCA → Report`이다. RCA가 미확정이어도 Report 에이전트는 실행되며,
미확정임을 표기한 리포트를 만든다.

**이 실행에는 쓰기 도구가 존재하지 않는다.** 복구는 사용자 승인 뒤 별도 실행
에이전트가 담당하므로([ADR 0017](0017-playbook-execution-agent.md)), 분석 실행의
어느 서브 에이전트도 서비스·인프라를 변경하는 도구를 갖지 않는다. 산출물 저장만이
유일한 부작용이다.

### 하네스 단일 소스 원칙

오케스트레이션 동작을 정의하는 하네스 자산은 엔진 패키지 안에 한 벌만 두고,
로컬 실행과 컨테이너 실행이 같은 자산을 읽는다. 배포 이미지는 이 자산을
변환하거나 재작성하지 않고 그대로 담는다. 하네스 자산은 다음 네 층이다.

1. **워크스페이스 계약** — 오케스트레이터의 호출 순서, 역할별 허용 도구, 산출물
   목록, 금지 사항.
2. **역할 정의** — 각 전문 에이전트의 지시와 도구 허용 목록.
3. **역할별 실행 가이드** — 증거 수집·가설·보고 절차를 담은 스킬.
4. **프롬프트** — 알람 컨텍스트 위에 조립되는 시스템·사용자 프롬프트 조각.

CLI 호출 인자(루트 에이전트, 허용 도구 목록, MCP 설정 범위, 세션 비지속)도
하네스의 일부로 보아 코드 한 곳에서만 정의하고, 로컬과 배포가 같은 값을
사용한다. 로컬 실행과 컨테이너 실행의 차이는 자격 증명, 대상 계정, 알람 입력
경로로만 한정한다.

이 원칙이 성립하려면 MCP 서버 참조가 실행 환경에 종속되지 않아야 한다. 하네스가
가리키는 도구 경로는 컨테이너 배치 위치가 아니라 패키지 기준으로 해석되어야
하며, 그렇지 않으면 로컬에서는 같은 하네스를 기동할 수 없어 검증 대상과 배포
대상이 갈라진다.

하네스 자산 사이의 일관성(역할 집합, 도구 허용 범위, 산출물 이름, MCP 서버
집합)은 외부 호출 없이 도는 계약 테스트로 고정한다. 로컬에서 하네스를 고치면
배포 전에 같은 테스트가 그 변경을 검사한다.

메인 오케스트레이터와 모든 서브 에이전트는 실행별 격리 컨텍스트를 공유한다.
산출물 저장은 제한된 저장 도구만 사용하며, wrapper가 산출물을 감지하여 세션
트레이스를 기록한다. 세션은 전체 오케스트레이션 동안 분석 중 상태를 유지하고,
플레이북을 포함한 필수 리포트가 저장된 뒤에만 완료된다. 완료 게이트는 파일 존재만
확인하지 않고 RCA 산출물과 리포트의 원인·확정 상태가 일치하는지, 그리고 리포트의
서술된 절차와 구조화된 절차가 일치하는지 검증한다
([ADR 0007](0007-rca-report-generation.md)).

산출물 검증은 **저장 시점과 완료 시점의 두 계층**으로 나눈다. 저장 도구는 산출물이
스스로 소유한 형태(필수 필드, 단계 값, 문서 구조)를 저장 시점에 검사하고 위반하면
저장을 거부한다. 거부 응답은 누락된 필드를 지목하므로 작성 주체가 같은 실행 안에서
교정할 수 있다. 완료 게이트는 여러 산출물 사이의 일치를 검사한다.

이 분리는 검증 시점이 교정 가능성을 결정하기 때문이다. 형태 오류를 완료 시점에만
검사하면 모든 저장이 성공한 실행이 종료 직후 실패하고, 작성 주체는 이미 사라져
교정할 수 없다. 반대로 산출물 간 일치를 저장 시점에 요구할 수는 없다. 앞선 단계의
산출물이 저장 시점에 아직 없을 수 있기 때문이다. 두 계층의 판정 기준이 갈라지면
같은 문제가 다시 발생하므로, 완료 게이트가 요구하는 자체 필드 집합과 저장 시점이
검사하는 집합의 일치를 계약 테스트로 고정한다.

**검증이 요구하는 모든 것은 프롬프트가 먼저 말해야 한다.** 게이트가 프롬프트에 없는
형식을 요구하면, 작성 주체는 알 수 없는 이유로 거부당하고 정상적으로 도출된 분석이
형식 문제로 폐기된다. 따라서 게이트의 요구 집합과 프롬프트 자산의 서술을 대조하는
검사를 유지한다. 이 검사는 게이트 정의에서 요구 집합을 직접 도출하므로, 게이트에
규칙을 추가하면 프롬프트가 그것을 서술할 때까지 실패한다. 표현의 일치가 아니라
누락만 검사해 프롬프트 문구를 고정하지 않는다.

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 단일 CC 에이전트가 전체 흐름 직접 수행 | 컨텍스트 전달이 단순하고 호출 수가 적다. | 증거 수집과 보고서 작성의 실패 경계가 합쳐져 단계별 검증 요구를 충족하지 못한다. |
| 외부 워크플로 엔진이 단계별 CC 실행을 조정 | 단계 격리와 재시도가 명확하다. | 실행 간 컨텍스트 전달과 인프라가 늘어나며 한 알람의 자율 탐색 흐름이 단절된다. |
| 단일 CC 실행 안의 전문 서브 에이전트 | 컨텍스트를 유지하면서 역할·도구·산출물 계약을 분리할 수 있다. | 서브 에이전트 간 결과 계약을 유지해야 하고 호출 수만큼 토큰이 늘어난다. |

하네스를 어디에 두고 어떻게 배포할지에 대한 대안:

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 로컬 실험용 하네스와 배포용 하네스를 따로 유지 | 로컬에서 도구·모델을 자유롭게 바꿔 실험할 수 있다. | 두 벌이 갈라져 로컬 검증 결과가 배포 동작을 보증하지 못하고, 하네스 변경마다 이중 반영이 필요하다. |
| 하네스를 런타임에 외부 저장소에서 내려받아 주입 | 이미지 재빌드 없이 프롬프트를 교체할 수 있다. | 실행 시점 자산이 검증 시점 자산과 달라질 수 있고, 이미지 태그만으로 동작을 재현할 수 없다. |
| 하네스를 엔진 패키지에 한 벌 두고 이미지에 그대로 포함 | 로컬 검증 대상과 배포 대상이 동일하고, 이미지 태그가 하네스 버전을 함께 고정한다. | 프롬프트만 바꿔도 이미지 재빌드·재배포가 필요하다. |

## Consequences

### Positive

- 증거 수집과 보고서 책임, 실패 경계가 명확해진다.
- 분석 실행 전체가 읽기 전용이므로 오판이 서비스 변경으로 이어질 경로가 없다.
- 쓰기 도구가 없어 같은 런타임 안의 논리적 권한 분리를 유지할 필요가 없다.
- 로컬에서 하네스를 다듬은 결과가 그대로 배포 동작이 되므로, 프롬프트·역할 변경을
  배포 전에 로컬에서 관찰할 수 있다.
- 이미지 태그 하나가 코드와 하네스 버전을 함께 고정하므로 실행 동작을 재현할 수
  있다.
- 산출물 형태 오류가 작성 주체에게 즉시 전달되므로, 같은 실행 안에서 교정되어
  전체 RCA가 형식 문제로 폐기되지 않는다.

### Negative

- 서브 에이전트 간 결과 계약과 프롬프트 회귀 테스트를 유지해야 한다.
- 여러 서브 에이전트 호출로 토큰 사용량과 실행 시간이 증가할 수 있다.
- 분석과 실행이 다른 실행 컨텍스트에 있으므로, 실행 에이전트는 리포트에 담긴
  내용만으로 절차를 수행해야 한다. 분석 과정의 암묵적 맥락은 전달되지 않는다.
- 프롬프트나 스킬만 수정해도 이미지 재빌드와 서비스 재배포가 필요하다.
- 산출물 형태 규칙이 저장 시점과 완료 시점 두 곳에 존재하므로, 스키마를 바꿀 때
  양쪽을 함께 갱신해야 한다.

### Risks

- 오케스트레이터가 잘못된 순서로 에이전트를 호출할 수 있다. 필수 산출물과
  호출 순서를 계약 테스트로 고정한다.
- Report 에이전트가 미확정 원인을 확정으로 서술할 수 있다. RCA 산출물의 확정
  상태와 리포트 서술의 일치를 완료 게이트가 검증한다.
- 리포트의 서술된 절차와 구조화된 절차가 어긋날 수 있다. 사용자가 승인한 것과
  실행되는 것이 달라지므로 완료 게이트가 둘의 일치를 검증한다.
- 저장 시점 검사와 완료 게이트의 판정 기준이 갈라질 수 있다. 두 계층이 요구하는
  자체 필드 집합의 일치를 계약 테스트로 고정한다.
- 게이트에 규칙을 추가하면서 프롬프트를 갱신하지 않으면 알 수 없는 이유의 거부가
  생긴다. 게이트 요구 집합과 프롬프트 서술의 대조 검사가 이 누락을 배포 전에 잡는다.
  다만 이 검사는 요구가 언급되었는지만 보므로, 서술이 실제로 충분한지는 보증하지
  않는다.
- 저장이 거부됐는데 작성 주체가 무시하고 다음 단계로 넘어갈 수 있다. 이 경우
  필수 산출물이 없으므로 완료 게이트가 세션을 완료하지 않는다.
- 하네스 자산이 컨테이너 배치 경로에 종속되면 로컬에서 같은 하네스를 기동할 수
  없어 패리티가 이름만 남는다. MCP 서버 참조를 패키지 기준으로 해석하고, 계약
  테스트가 환경 종속 참조를 차단한다. 두 환경에서 같은 하네스가 각자의 패키지
  경로로 해석되는 것을 확인했다.
- CLI 인자나 도구 허용 목록이 로컬과 배포에서 갈라질 수 있다. 두 값을 코드 한
  곳에서만 정의하고 계약 테스트로 고정한다.
