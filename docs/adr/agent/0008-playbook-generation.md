# ADR 0008: 플레이북 생성 — 유형별 대응 지식의 축적과 사고별 런북

Date: 2026-04-21
Updated: 2026-09-15

## Status

Accepted (2026-09-15)

## Context

동일 유형의 장애가 재발할 때 과거 경험을 활용하려면, RCA(근본원인분석) 결과를
재사용 가능한 플레이북으로 만들고 의미가 비슷한 내용을 찾는 벡터 검색에 등록해야 한다.
플레이북은 임시·영구·예방 조치와 담당자에게 대응을 넘기는 기준을 기록한다.
초기 스코핑(조사 범위 설정)의 유사도 검색은 RCA 보고서 인덱스를 사용한다
([ADR 0001](0001-initial-scoping-and-report-similarity.md)). 플레이북은 대응 지식이
중심이므로, 원인 가설을 만드는 데에는 증상과 근본 원인이 연결된 보고서가 필요하다.

플레이북은 신규 RCA에서 검색·보강하는 대응 지식이며 사람이 판단할 때도 참조한다.
실행은 이 지식을 이번 사고에 적용한 런북을 근거로 한다. 사용자는 실제 대상과 명령을
읽고 승인해야 하므로, 런북은 승인 전에 실행 가능한 형태로 구조화되어야 한다
([ADR 0017](0017-playbook-execution-agent.md)).

## Decision Drivers

- 같은 유형의 장애가 반복될 때 플레이북이 중복 축적되지 않고 하나가 점진적으로 보강되어야 한다.
- 플레이북 검색은 표현이 달라도 같은 장애 유형을 찾아야 한다. 유사도 매칭이 수치 차이에 걸려 실패하면 병합이 일어나지 않는다.
- 기존 플레이북을 보강할 때 과거 내용이 사라져서는 안 된다. 축적이 되돌려지면 플레이북의 가치 자체가 없다.
- 플레이북 생성 실패가 RCA 파이프라인을 중단시켜서는 안 된다.
- 유형별 지식은 재사용할 수 있어야 하며, 사고별 런북은 사람이 실제 명령을 읽고 승인할 수 있어야 한다.
- 완료되지 않은 분석의 중간 플레이북이 사람에게 최종 결과처럼 보이거나 다음 분석의
  보강 입력으로 재사용되어서는 안 된다.
- 검색 인덱스 장애가 완성된 리포트의 전달과 승인을 막아서는 안 되며, 재시도로
  검색 가능성을 회복할 수 있어야 한다.

## Decision

**LLM(대규모 언어 모델) 기반 플레이북 자동 생성 + 벡터 인덱싱** 전략을 채택한다.
플레이북은 해당 장애 및 관련 장애에서 확인할 메트릭, 판단 기준, 대응 지식이다.
런북은 그 지식을 이번 사고에 적용한 대상·순서·구체 명령·성공 기준이다.
두 내용은 하나의 분석 산출물 안에서 구분하며, 실행 승인은 런북을 대상으로 한다.

### 플레이북 구조

- 장애 유형 분류 (예: DB 커넥션 누수, CPU 폭증, 메모리 릭 등)
- 증상 패턴 (어떤 알람/메트릭이 이 유형의 장애를 시사하는지)
- 심각도 판단 기준 (이 패턴 발생 시 critical/high/medium/low 구분 조건)
- 확인 절차 (단계별 검증 방법 — 이번 RCA에서 검증한 경로 기반)
- **이번 사고의 런북** (재사용 지식과 구분된, 실행 에이전트가 수행할 순서 있는 명령 목록)
- 임시 조치 절차 (예: 롤백, 리소스 증설)
- 영구 조치 가이드 (코드 수정 방향, 설정 변경)
- 에스컬레이션 기준 (언제, 누구에게 에스컬레이션할지)
- 예방 조치 (모니터링 추가, 알람 임계치 조정)
- 관련 메트릭 (이 장애 유형과 관련된 핵심 메트릭 및 대시보드)

### 실행 절차의 요구사항

실행 근거가 되는 절차는 다음을 만족해야 한다.

- **순서와 식별자를 가진 단계 목록**이다. 실행 증거가 어느 단계에서 무엇이 실패했는지
  지목하고, 회고가 그 단계를 교정하려면 단계마다 안정적인 식별자가 필요하다
  ([ADR 0018](0018-playbook-retrospective.md)).
- 각 단계는 **의도와 수행할 작업**, 그리고 **성공을 판정하는 관측 기준**을 함께 기술한다.
  관측 기준이 없으면 실행 에이전트가 해결 여부를 확정할 수 없다.
- 되돌릴 수 없는 조치를 절차에 담지 않는다. 담더라도 실행 계층이 거부하므로 그 단계는
  수동 조치로 남는다([ADR 0017](0017-playbook-execution-agent.md)).

런북은 승인 전에 대상 리소스와 리전, 각 단계의 구체 명령과 인자, 실행 순서,
성공 판정 기준을 확정한다. 자연어 작업 설명만으로는 실행 가능한 런북이 아니다.
대상이나 명령을 확인할 증거가 부족하면 명령을 추정하지 않고 실행 불가 사유를 남긴다.
명령이 없는 과거 기록은 원문을 열람할 수 있지만 새 실행 승인 대상은 아니다.

플레이북의 유형·패턴·메트릭·대응 지식은 재사용하되, 새 사고의 런북은 두 분석 엔진 모두
현재 사고의 근거로 전체를 새로 작성한다. 과거 런북의 대상·명령·빈 갱신 보존 규칙을
새 사고에 상속하지 않는다. 런북이 달라지면 검증 상태는 초안이다.

### 핵심 결정사항

1. **검색 우선(Search-First) 전략**: 이번 분석의 유형·패턴을 만든 뒤 벡터 인덱스에서 유사 플레이북을 검색한다. 유사도 **0.80 이상**인 기존 플레이북이 있으면 LLM이 새 RCA 결과와 비교해 보강할 내용이 있는지 판단한다. 보강이 필요하면 기존 플레이북 식별자를 유지한 채 내용을 갱신한다. 보강할 지식이 없다는 판단이 이번 사고의 런북 작성을 생략하거나 과거 명령을 상속하는 근거가 되지는 않는다. 임계치를 일반 조회보다 높게 두는 이유는, 다른 유형의 장애를 같은 플레이북으로 병합하면 대응 지식이 뒤섞이기 때문이다.

   보강이 불필요하면 같은 지식을 가진 새 플레이북 식별자를 만들지 않는다.
   이번 사고의 런북은 기존 식별자 아래 현재 사고의 근거로 작성한다.

   **0.80은 재발 시 표현 차이를 허용하기 위한 기준이다.** 기록된 표본에서는 같은
   유형·패턴을 다른 문장으로 쓴 경우의 유사도가 0.83, 글자까지 동일한 경우가
   0.96이었다. 이 근거는 해당 표본과 임베딩 모델에 한정된다.

   임계치를 낮추면 무관한 플레이북에 병합할 위험이 오르지만, 잘못된 병합에는 하한이 셋 있다. 상세를 로드해 LLM이 보강 여부를 다시 판단하고, 병합이 삭제 없이 추가·교정만 하고(결정사항 3), 실행 계층이 절차 내용과 무관하게 파괴적 액션을 거부한다([ADR 0017](0017-playbook-execution-agent.md)). 반대로 임계치가 높아 병합이 아예 일어나지 않는 실패에는 하한이 없다 — 축적이 갈라진 채 조용히 진행되고, 회고가 매번 같은 교정을 다시 한다.

   **보강 판단 전에 기존 플레이북의 상세 절차를 반드시 로드한다.** 벡터 인덱스는 경량 메타데이터만 보유하므로(결정사항 4) 인덱스에 담긴 RCA 식별자로 상태 저장소를 한 번 더 조회한다. 상세 로드에 실패하면(레코드 만료·조회 실패) 그 후보는 보강 대상에서 **제외**하고 다음 후보로 넘어간다 — 기존 절차를 보지 못한 상태의 "보강"은 같은 식별자로 과거 내용을 덮어써 축적을 되돌리므로, 병합을 포기하고 신규 생성으로 떨어지는 편이 안전하다.

   **로드하는 상세는 게시가 확정된 회고 개정본이 있으면 그것이고, 없을 때만 분석이
   기록한 원본이다.** 회고에서 축적한 지식을 다음 분석이 잃지 않기 위한 규칙이다
   ([ADR 0018](0018-playbook-retrospective.md)). 과거 런북은 참고 증거로 읽으며,
   새 사고의 대상·명령·순서는 현재 사고의 근거로 작성한다. 승인 화면은 현재
   개정본을 보여주고, 실행 워커는 승인 시점에 고정한 사본만 읽는다.

2. **벡터 임베딩 템플릿 공유**: 장애 유형·증상 패턴·메트릭으로 구성된 구조화 템플릿으로 임베딩 텍스트를 만들고, 각 필드를 상한 길이로 truncate한다. 저장과 검색에 각 용도에 맞는 입력 유형을 적용한다. **RCA 보고서 인덱스와 같은 템플릿을 사용**해 두 인덱스의 임베딩 공간 일관성을 유지한다([ADR 0001](0001-initial-scoping-and-report-similarity.md)).

   **저장과 검색은 같은 성질의 텍스트를 넣어야 한다.** 템플릿을 공유하는 것으로 충분하지 않다 — 같은 렌더러에 다른 종류의 문장을 넣으면 임베딩 공간이 갈라진다. 플레이북의 장애 유형·증상 패턴은 다른 리소스의 같은 장애에 재사용하기 위해 **일반화된 서술**이고, 보고서의 근본 원인·인시던트 요약은 이번 사건의 리소스 식별자·리비전·시각을 담은 **개별 서술**이다. 저장에 전자를, 검색에 후자를 쓰면 같은 장애를 놓고도 유사도가 낮게 나오며, 이 실패는 검색 결과가 비어 돌아오는 형태라 오류로 드러나지 않는다. 검색 쿼리는 이번 분석이 만든 **플레이북의** 유형·패턴으로 구성한다.

3. **병합 규칙을 코드로 보장**: 보강 여부와 갱신된 플레이북 내용을 구조화 출력으로 받되, LLM이 특정 필드를 비워 반환하면 기존 값을 유지한다. "추가·보강만 하고 삭제하지 않는다"는 규칙을 프롬프트 지시가 아니라 코드에 둔다 — 프롬프트 지시만으로는 모델이 필드를 누락할 때 축적이 조용히 사라진다.

   이 부분 갱신 규칙은 비실행 지식과 회고에 적용한다. 두 엔진의 새 RCA가 생성한
   런북에는 아래 **현재 사고 전체 계획의 권위**를 적용한다.

   검증 상태는 **실제로 실행된 절차 내용에 종속된다**. 설명·태그처럼 실행 절차 밖의
   필드만 보강하면 기존 검증 상태를 유지하지만, 런북 내용이나 순서가 달라지면
   결과는 다시 초안이 된다. 바뀐 절차는 아직 실행으로 입증되지 않았기 때문이다.
   회고가 실행 절차 갱신을 생략하면 기존 절차와 상태를 보존한다. 새 사고의 빈 런북은
   이전 사고의 명령을 지우며 승인 대상으로 만들지 않는다.

4. **벡터 인덱스는 경량 메타데이터만 보유**: 인덱스 메타데이터에는 크기 제한이 있어 검색·판별에 필요한 최소 필드와 RCA 식별자만 담고, 확인·조치 절차 같은 상세는 상태 저장소에서 조회한다. 상세를 인덱스에 중복 저장하면 갱신 시 두 저장소가 어긋난다([ADR infra/0002](../infra/0002-evidence-storage.md)).

   **검증 상태는 이 최소 필드에 포함된다.** 절차 본문이 아니라 그 절차가 실행으로 입증되었는지를 나타내는 판별 값이므로, 상세를 로드하지 않고도 검색 결과에서 보여야 한다. 승격은 개정본과 인덱스 양쪽에 함께 반영되며([ADR 0018](0018-playbook-retrospective.md)) 한쪽만 갱신하면 승격이 한 경로에서만 보인다.

5. **태깅**: LLM이 생성한 태그를 플레이북에 포함해 유형별 분류에 활용한다.

6. **타임아웃 및 fallback**: 각 LLM 호출에 타임아웃을 적용하고, 실패 시 최소 정보만 담은 플레이북을 생성한다.

7. **비차단(non-blocking) 실행**: 플레이북 생성은 파이프라인을 중단시키지 않는다. 실패하면 실패를 기록하고 알림·세션 완료로 계속 진행한다. 양쪽 엔진에 동일하게 적용한다 — 플레이북은 미래를 위한 자산이고 이번 RCA의 결과물은 보고서이므로, 자산 생성 실패가 결과 전달을 막아서는 안 된다.

8. **모델 티어**: **Planning 티어**를 사용한다. 장애 패턴 추출, 절차 작성, 기존 플레이북 업데이트 판단에 추론이 필요하다([ADR agent/0010](0010-model-tier-architecture.md)).

### Requirement contract

#### 현재 사고 전체 계획의 권위

두 분석 엔진이 새 RCA에서 생성하고 완료 검증을 통과한 `execution_steps`는 이번 사고의
전체 계획이다. 검색 우선 병합은 기존 플레이북 식별자와 비실행 지식의 보강 규칙을 유지하되,
실행 단계는 생성된 목록과 정확히 같아야 한다. 빈 목록도 기존 절차를 모두 비우며, 같은
단계 식별자여도 과거 단계의 필드·대상 바인딩·순서를 상속하지 않는다. 검색이나 상세 조회가
실패해 신규 생성으로 돌아가더라도 현재 생성 계획을 사용한다.

단계 내용과 순서 전체가 기존 목록과 정확히 같을 때만 기존 검증 상태를 유지한다.
단계 추가·삭제·재배치·대상 변경이 있으면 `DRAFT`로 돌아간다. 완료 세션, 리포트, 알림,
검색 인덱스 게시에 같은 최종 계획을 사용한다.

이는 새 분석의 실행 계획을 정하는 계약이다. 회고의 부분 교정은 기존 단계 보존과
추가·교정 규칙을 유지하며, 이미 승인된 실행의 불변 스냅샷과 과거 증거는 바꾸지 않는다.

#### 완료 후 게시

분석 중 생성된 플레이북 파일과 트레이스는 진행 상황을 설명하는 중간 산출물이다.
사람이 열람하고 승인하거나 다음 분석이 검색·병합할 수 있는 플레이북은 **세션이
완료되면서 확정한 최종 플레이북 하나뿐**이다.

- 상태 저장소의 완료 세션이 플레이북 게시의 권위다. 진행 중·실패·취소·건너뜀
  세션의 플레이북은 리포트 열람, 승인, 유사도 검색, 병합 대상이 아니다.
- 리포트 본문, 완료 세션이 가리키는 구조화 플레이북, 완료 알림, 검색 인덱스는 같은
  플레이북 식별자와 같은 실행 절차 집합·순서를 가져야 한다. 검색 우선 병합이
  발생했다면 병합 결과가 이 네 소비처의 최종 값이다.
- 리포트 원본을 저장한 뒤 세션 완료를 먼저 확정한다. 완료 세션은 플레이북 검색
  게시가 남았음을 기록하며, 그 뒤에만 벡터 인덱스를 갱신한다.
- 벡터 게시 상태는 **대기와 게시 완료** 두 상태다. 게시 실패는 완료된 분석을
  실패로 되돌리지 않고 대기로 남아 같은 완료 handoff의 재전달에서 멱등 재시도된다.
- 검색 결과의 상세를 읽을 때 완료 세션의 플레이북 식별자와 일치하는지 검증한다.
  게시 상태가 있는 신규 기록은 게시 완료만 허용하며, 상태 도입 전에 만들어진
  완료 세션은 식별자 일치로 읽기 호환한다.
- 인덱스 게시나 완료 알림이 대기 중인 세션은 삭제할 수 없다. 완료 handoff의 권위
  레코드가 외부 게시보다 먼저 사라지면 고아 인덱스와 재시도 불가 상태가 생기기
  때문이다.
- 근본 원인이 미확정이어도 분석은 정상 완료될 수 있다. 이 경우 플레이북은 열람할
  수 있지만 실행 절차가 빈 목록이므로 승인과 실행 대상은 아니다.

이 순서는 인덱스를 원본이나 완료 권위로 취급하지 않기 위해 필요하다. 완료 전에 같은
플레이북 식별자의 벡터를 덮어쓰면 후속 리포트 저장이나 완료 기록이 실패했을 때
실패한 분석이 기존의 유효한 축적을 대체한다. 반대로 완료 뒤 게시하면 인덱스 장애는
검색 지연으로만 남고 승인 대상 리포트와 플레이북은 상태 저장소에서 일관되게 읽힌다.

### 실행과의 경계

플레이북은 런북 작성의 근거이며, 실행 권한은 사람이 승인한 런북 범위에 한정된다.
실행 계층은 승인된 명령·대상·순서를 검사하고 파괴적 액션도 독립적으로 거부한다
([ADR 0017](0017-playbook-execution-agent.md)). 승인된 명령이라도 파괴적 액션
판정을 통과하지 못하면 실행할 수 없다.

이 분리가 필요한 이유는 플레이북이 LLM 생성물이기 때문이다. 절차가 곧 권한이 되면
모델이 쓴 자유 텍스트가 쓰기 액션의 권위가 되어 안전 경계가 무너진다. 두 층을 나누면
절차의 표현력을 열어 두면서도 되돌릴 수 없는 조치는 차단된다.

새 런북은 실행되지 않은 상태에서는 **초안**이다. 초안임이 리포트에 표기되어야 하며,
실행과 회고를 거친 뒤에야 검증된 절차가 된다. 검증 상태의 값과 전이 방향, 승격 주체는
회고 결정이 보유한다([ADR 0018](0018-playbook-retrospective.md)).

**분석은 초안 외의 검증 상태를 쓸 수 없다.** 신규 생성이든 기존 플레이북 보강이든
분석 단계가 산출하는 검증 상태는 초안뿐이며, 모델이 다른 값을 반환하면 산출물을
거부한다. 분석은 어떤 절차도 실행해 보지 않았으므로 검증 여부를 판정할 근거가 없다.

다만 **실행 절차가 그대로인 병합은 기존 검증 상태를 낮추지 않는다.** 분석이 초안만
쓸 수 있다는 것은 새로 부여하는 값의 제한이고, 실행 절차가 바뀌지 않은 경우에는
기존 값의 보존이 적용된다. `execution_steps`가 달라진 경우만 새 절차의 검증을 위해
`DRAFT`로 돌아간다.

근본 원인이 미확정인 RCA는 신규 생성뿐 아니라 기존 플레이북 병합에서도
`execution_steps`가 항상 빈 목록이어야 한다. 새 분석이 빈 목록을 냈다는 이유로 기존
플레이북의 실행 절차를 복원하면 미확정 원인 뒤에 승인 가능한 절차가 생긴다.

## Consequences

### Positive

- 검색 우선 전략으로 중복 플레이북 축적 방지 — 동일 유형 장애의 플레이북이 점진적으로 보강됨
- 두 엔진이 게시된 회고 개정본을 같은 우선순위로 읽으므로 다음 분석이 실행에서 얻은 지식을 참조할 수 있다
- 검증 상태가 인덱스에 있으므로 상세를 로드하지 않고도 검색 결과에서 승격 여부가 보인다
- 과거 RCA 경험이 플레이북으로 체계적으로 축적되어 조직 지식 자산화
- 유사도 인덱싱으로 동일 유형 장애의 플레이북을 찾아 보강할 수 있다
- 재발 장애 대응 시 사람이 참조할 검증된 절차가 남아 MTTR이 추가로 단축된다
- 플레이북이 실행 근거이므로 절차의 정확성이 실행으로 검증되고, 회고를 통해 개선된다

### Negative

- 플레이북 품질이 RCA 결과의 정확도에 의존 — 오판된 RCA에서 잘못된 플레이북 생성 가능
- 임베딩 저장이 실패하면 검색이 불가하다 (플레이북 본문은 보존됨)
- 완료와 벡터 게시 사이에는 검색에 아직 반영되지 않은 짧은 구간이 생길 수 있다
- 보강 판단을 위한 LLM 호출과 상세 로드 조회가 후보당 추가로 발생한다
- 플레이북 상세의 수명이 상태 저장소 보존 주기에 묶인다. 보존 기간이 지난 플레이북은 검색되어도 상세를 로드할 수 없어 병합 대상에서 제외되고, 같은 장애 유형의 플레이북이 새 식별자로 다시 생성된다
- 절차가 실행 가능한 구조를 갖춰야 하므로 생성 스키마가 커지고, 단계 식별자의 안정성을 유지해야 한다

### Risks

- 근본 원인 미확정 RCA에서 생성된 플레이북이 향후 유사 장애 시 오도할 수 있다. "추정 원인 기반" 플레이북으로 명시하고 검증 부족 항목을 표기하여 완화한다.
- 유사도 임계치를 거리로 오해석하면([ADR 0001](0001-initial-scoping-and-report-similarity.md)) 보강 경로의 통과 조건이 반전되어, 무관한 플레이북을 병합하거나 반대로 병합이 전혀 일어나지 않는다. 어느 쪽이든 조용히 실패하므로 거리→유사도 변환을 인덱스 어댑터로 단일화하고 계약 테스트로 고정한다.
- 절차가 실행 근거가 되므로 잘못된 절차의 영향이 사람의 오독에서 잘못된 명령 실행으로 커진다. 실행 계층의 파괴적 액션 거부가 하한을 지키고, 사용자 승인이 실행 시작을 통제한다.
- 부분 갱신으로 단계 식별자가 재배치되면 과거 실행 증거가 가리키는 단계를 찾을 수 없다. 회고의 부분 갱신은 식별자를 유지하며 추가·교정만 하고, 두 엔진의 새 전체 계획은 과거 승인 스냅샷을 변경하지 않는다.
- 병합 결과를 필드마다 다시 조립하는 경로에서 검증 상태를 무조건 보존하면 변경된
  절차까지 검증됨으로 보인다. 실행 절차가 동일할 때만 상태를 보존하고, 절차가
  달라지면 초안으로 돌아가는 계약을 테스트로 고정한다.
- 보강 대상 상세를 회고 개정본이 아니라 분석 원본에서 읽으면 병합이 모든 필드를 보존해도 결과가 교정 이전으로 퇴행한다. 검색과 병합이 정상 동작하므로 로그에도 실패로 남지 않고, 같은 장애가 반복될수록 회고가 매번 같은 교정을 다시 하게 되어 축적이 제자리에 머문다. 상세 조회가 개정본을 우선한다는 것을 계약 테스트로 고정한다.
- 저장과 검색에 다른 종류의 문장을 넣으면 검색이 항상 빈 손으로 돌아오고, 그것이 "닮은 플레이북이 없다"와 구별되지 않는다. 병합 경로 전체가 실행되지 않는데도 로그에는 정상적인 신규 생성만 남으므로, 라이브에서 재발을 관측하기 전까지 드러나지 않는다. 검색 쿼리와 저장 텍스트가 같은 필드에서 나온다는 것을 계약 테스트로 고정한다.
- 임계치는 임베딩 모델에 종속된다. 모델을 바꾸면 같은 장애의 유사도 분포가 이동하므로, 재발 시나리오 표본으로 분포를 다시 측정한 뒤 기준 변경을 결정한다.
- 임베딩 입력 필드를 바꾸면 기존 인덱스 레코드는 옛 텍스트로 임베딩된 상태로 남아 새 쿼리와 공간이 어긋난다. 전환 시점 이전 레코드는 검색되지 않으므로, 축적을 이어가려면 재적재가 필요하다.
- 완료 세션을 확인하지 않는 읽기 경로가 하나라도 남으면 실패한 분석의 중간
  플레이북이 다시 축적에 섞일 수 있다. 대시보드와 두 엔진의 상세 로더가 같은 완료
  및 식별자 검증을 수행하는 계약 테스트로 이 경계를 고정한다.
