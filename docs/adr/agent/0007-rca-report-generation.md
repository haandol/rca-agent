# ADR 0007: RCA 보고서 생성 — LLM 기반 자동 보고서 작성

Date: 2026-04-21
Updated: 2026-05-25

## Status

Accepted (2026-04-21)

## Context

근본 원인이 확정(또는 미확정)된 후 SRE 팀이 활용할 수 있는 종합 RCA 보고서를 자동으로 생성해야 한다. 수동 보고서 작성은 수시간이 소요되며, 에이전트가 이미 수집한 증거와 추론 경로를 구조화하면 작성 시간을 크게 단축할 수 있다.

## Decision Drivers

- 보고서는 확정과 미확정을 명확히 구분해야 한다. SRE가 미확정 결과를 확정으로 오독하면 잘못된 조치가 시작된다.
- 보고서 생성 실패가 RCA 결과 자체를 잃게 만들어서는 안 된다.
- 인과 사슬은 "운영자 실수" 같은 사람 지목에서 멈추지 않고 시스템·프로세스 결함까지 내려가야 한다. 사람에서 멈춘 분석은 재발 방지 조치를 만들 수 없다.
- 보고서의 각 주장은 수집된 증거나 타임라인 이벤트에 연결되어야 한다.

## Decision

**LLM 기반 구조화 보고서 자동 생성** 전략을 채택한다.

### 보고서 구조

- 장애 요약 (알람 정보, 발생 시각, 영향 범위)
- 심각도 (서비스 영향 범위와 지속 시간 기반: critical/high/medium/low)
- 영향 평가 (영향받은 서비스, 사용자 범위, 지속 시간, 에러율/지연 등 정량적 영향)
- 탐지 방법 (어떤 알람/메트릭/모니터링이 인시던트를 감지했는지)
- 근본 원인 (확정된 가설, 신뢰도)
- **5 Whys** (증상 → 시스템·프로세스 결함까지의 인과 사슬 — Toyota / AWS COE 가드레일 적용)
- 가설 도출 경로 (트리에서 근본 원인까지의 경로, 기각된 가설 목록)
- 증거 목록 (메트릭 스냅샷, 로그 스니펫, 배포 이력, 코드 diff 참조)
- 임시 조치 방안 (예: 서비스 롤백, 리소스 증설)
- 영구 조치 방안 (예: 코드 수정, 설정 변경)
- 조치 항목 (재발 방지, 영향 축소, 프로세스 개선으로 분류된 후속 작업)
- 교훈 (탐지/대응에서 잘된 점, 개선할 점, 운이 좋았던 점)
- 타임라인 (알람 발생 → 스코핑 → 가설 생성 → 검증 → 확정까지 시간 흐름)

### 핵심 결정사항

1. **LLM 구조화 출력 + 오케스트레이션 메타데이터 결합**: 위 섹션 목록을 구조화 출력으로 받고, 오케스트레이션 계층이 수집한 메타데이터(RCA 식별자, 가설 경로, 증거 목록, 기각된 가설)를 덧붙여 최종 보고서를 구성한다. 탐색 과정에서 실제로 일어난 일은 모델이 아니라 오케스트레이터가 알고 있으므로, 이 부분을 모델 출력에 의존하지 않는다.

2. **Markdown 저장**: 보고서를 Markdown으로 렌더링해 오브젝트 스토리지에 보관한다. 저장 대상이 설정되지 않은 환경에서는 업로드를 건너뛰고 파이프라인을 계속 진행한다.

3. **근본 원인 미확정 처리**: 근본 원인이 확정되지 않은 보고서는 본문에 미확정임을 명시하고 해당 원인을 "가장 유력한 후보"로 표기한다.

4. **타임아웃 및 fallback**: 보고서 생성에 타임아웃을 적용하고, 실패 시 알람 요약과 최적 가설만으로 최소 보고서를 생성한다. 보고서 생성 실패가 RCA 결과 전체의 손실이 되어서는 안 된다.

5. **모델 티어**: **Planning 티어**를 사용한다. 구조화된 보고서 작성에 깊은 추론이 필요하다([ADR agent/0010](0010-model-tier-architecture.md)).

6. **5 Whys 사고 프레임 (Toyota / AWS COE)**: 보고서의 5 Whys 섹션은 단순 양식이 아니라 증상 → 시스템·프로세스·설계 결함까지의 인과 사슬 추적이다. LLM 프롬프트에 다음 가드레일을 강제한다.
   - **"휴먼 에러" 종착 금지**: "운영자 실수" 같은 답에서 멈추지 않고 "왜 그게 가능했는가? (검증 부재? 권한 과다? 런북 결함?)" 까지 풀어 시스템·프로세스 결함으로 표현.
   - **단일 원인 가정 회피**: 다요인이 함께 작용한 경우 주축 사슬은 가장 부하가 큰 요인으로 잡되, 각 단계의 답에 공동 요인(co-factors)을 한 줄로 명시.
   - **사실 기반 절단**: 각 "왜?"의 답은 수집된 증거 또는 타임라인 이벤트와 연결되어야 하며, 추측이면 사슬을 거기서 자르고 "증거 부족" 으로 명시.
   - **Blameless 톤**: 사람·팀을 비난하지 않고 시스템 관점으로만 기술.

   가드레일은 가설 생성 단계에도 동일하게 적용된다([ADR agent/0002](0002-hypothesis-tree-lifecycle.md)). CC Headless 엔진도 시스템 프롬프트의 공통 원칙과 보고서 단계 프롬프트로 같은 가드레일을 주입한다([ADR agent/0011](0011-cc-headless-prompt-driven-rca.md)) — 두 엔진의 보고서가 같은 품질 기준으로 비교되어야 하기 때문이다.

7. **복구 결과의 구분 기록**: 복구가 수행된 세션의 보고서는 미실행, 성공, 실패, 검증 대기를 명시적으로 구분한다. 이 상태는 모델 서술이 아니라 서버가 판정한 결과를 따른다([ADR agent/0012](0012-automated-remediation.md)).

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 템플릿 채우기(LLM 없이 필드 조립) | 결정적이고 비용이 없으며 형식이 항상 일정하다. | 증거 간 인과 관계와 5 Whys 사슬을 서술할 수 없어 SRE가 다시 해석해야 하고, 자동화의 이점이 사라진다. |
| 자유 서술 보고서(구조 없는 산문) | 모델이 맥락에 맞게 유연하게 서술한다. | 필수 항목 누락을 검증할 수 없고, 확정·미확정 구분과 복구 결과가 서술에 묻힌다. 플레이북 생성과 유사도 인덱싱의 입력으로도 쓸 수 없다. |
| 구조화 출력 + 오케스트레이션 메타데이터 결합 | 필수 항목을 강제하면서 서술 품질을 얻고, 탐색 사실은 모델 출력에 의존하지 않는다. | 스키마 유지 비용이 들고 모델 출력이 스키마를 만족하지 못하면 재시도가 필요하다. |

## Consequences

### Positive

- 수동 보고서 작성 시간(수시간)을 자동화로 크게 단축
- 에이전트의 추론 경로와 증거가 체계적으로 문서화
- 표준화된 구조로 보고서 품질 일관성 확보
- 5 Whys 가드레일로 재발 방지 조치를 도출할 수 있는 결함 수준까지 사슬이 내려간다

### Negative

- LLM 생성 보고서의 문체가 조직 표준과 다를 수 있음
- 증거 요약 과정에서 핵심 정보가 누락될 수 있음
- 보고서 구조가 플레이북·유사도 인덱스의 입력이므로 섹션을 바꾸면 소비처를 함께 갱신해야 한다

### Risks

- 저장된 증거 조회에 실패하면 메타데이터만으로 보고서를 작성하게 되어 증거 세부 내용이 부족할 수 있다.
- 5 Whys의 각 단계가 증거에 연결되지 않으면 그럴듯한 추측 사슬이 만들어진다. 추측인 단계에서 사슬을 자르고 "증거 부족"으로 명시하도록 강제한다.
