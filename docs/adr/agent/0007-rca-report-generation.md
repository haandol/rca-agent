# ADR 0007: RCA 보고서 — 정상화 우선 3파트와 단계별 원본

Date: 2026-04-21
Updated: 2026-09-17

## Status

Proposed

## Context

운영자는 전체 원인 분석이 끝나기 전에 검증 가능한 정상화 방법을 필요로 한다.
정상 기준과 롤백 대상이 확인됐는데 코드·프로세스 분석을 기다리면 장애 시간이 늘어난다.
반대로 정상화 제안을 원인 확정이나 실제 복구 성공으로 표시하면 근거가 다른 상태가 섞인다.

한 사고에서 정상화 런북, 근본원인과 코드 수정, 운영 개선을 순차 공개하고 실행은
사용자 승인에 따라 독립적으로 진행해야 한다. 이미 승인한 내용과 당시 분석 원본은
뒤 분석이나 실행 결과로 바뀌어서는 안 된다.

## Decision Drivers

- 검증된 정상화 런북을 전체 원인 분석보다 먼저 검토·승인할 수 있어야 한다.
- 승인 대기·실행 실패가 근본원인과 운영 개선 분석을 막아서는 안 된다.
- 원인 판정·조기 승인 적격·실행 결과·운영 개선 적용 상태를 구분해야 한다.
- 주장·코드 위치·개선 제안은 확인한 원본과 연결되고 없는 내용을 만들어 채우지 않아야 한다.
- 과거 보고서와 승인 사본은 당시 내용과 순서를 보존해야 한다.

## Decision

사고 화면은 공통 요약과 **빠른 정상화 → 근본원인 → 운영 개선** 세 파트로 구성한다.
선택된 분석 엔진의 담당은 이 순서로 결과 또는 명시적 한계를 저장한다.
사용자는 준비된 파트를 즉시 읽으며, 실제 서비스 변경은 별도 사용자 승인 실행만 수행한다.

### 파트별 작성과 공개

| 파트 | 내용과 완료 결과 |
|---|---|
| 빠른 정상화 | 현재 서비스·버전, 검증된 정상 버전·입력 호환성·원본 근거, 고정 런북·성공 기준 또는 제안 불가 사유 |
| 근본원인 | 서버의 확정/미확정·신뢰도·선택 가설, 인과 사슬·대안 기각·직접 증거, 소스 리비전·파일·행과 코드 수정 PR 미리보기 |
| 운영 개선 | 실제 CI/CD·검사 설정의 확인 범위, 스키마 호환성 lint·실제 DB 계약 검사 등 예방 제안, 담당·우선순위·차단 조건·검증 상태 |

정상화 담당의 결과가 저장되면 근본원인 담당이 시작한다. 근본원인 결과 또는 미확정·실패
사유가 저장되면 운영 개선 담당이 시작한다. 런북의 미승인·거절·미실행·실행 중·해결·미해결·
실패·취소는 뒤 파트 시작의 전제조건이 아니다. 분석 전체 취소·소유권 상실·전체 예산
부족 등 공통 중단 조건은 유지하고 미시작 또는 실패 사유를 표시한다.

단계 완료와 분석 전체 완료를 구분한다. 조기 런북을 공개하려고 전체 분석을 완료로
기록하지 않는다. 단계 원문은 불변 사본으로 보존하며, 개정은 새 식별자를 갖는다.
뒤 담당이 이전 담당의 원문·명령을 덮어쓰거나 누락된 결과를 대신 창작하지 않는다.
최종 보고서는 세 파트의 원문 또는 명시된 한계를 연결한 한 사고의 산출물이며,
공개 당시의 내용과 출처를 보존한다. 단계별 상태를 전체 성공 한 가지 값으로 숨기지 않는다.

### 정상화 런북의 승인

정상화 제안은 근본원인 확정을 뜻하지 않는다. 원인이 미확정이고 전체 분석이 진행 중이어도
서버가 동일 사고·서비스의 정상 기준, 현재 배포, 입력 호환성, 구체 명령·순서·성공 기준을
검증한 롤백 런북은 사람이 승인할 수 있다([ADR 0017](0017-playbook-execution-agent.md)).
근거가 없거나 단계가 미완성·철회·만료·손상된 경우에는 승인하지 않는다.
근본원인 신뢰도 기준을 낮추거나 정상화 제안에 확정 값을 대신 부여하지 않는다.

승인 화면은 정확한 현재 개정본의 대상·리전·전체 명령과 인자·순서·대기 설정·성공 기준을
보여준다. 읽은 지문과 예약 시점의 개정본·승인 적격·미철회 상태를 조건부로 대조한다.
승인 사본의 전체 내용과 지문은 고정하며 후속 보고서 갱신으로 변경하지 않는다.
변경된 런북에는 새 승인이 필요하다. 새 조기 승인 경로가 없는 과거 기록은 기존 완료·확정
검증을 유지한다. 명령 없는 과거 기록은 원문으로 읽을 수 있지만 실행 명령을 추정하지 않는다.

조기 공개는 현재 사고의 검토·승인용이며 공개 재사용 플레이북 지식으로의 게시·승격과
구분한다([ADR 0008](0008-playbook-generation.md)). 후속 원인·운영 제안이 새 명령을
제안해도 이미 승인된 절차의 변경 권한이 생기지 않는다.

### 보존할 보고서 정보

공통 요약에는 사고·알람·발생 시각·관측 구간·영향 범위·심각도·다음 조치와 세 파트 및
실행의 개별 상태를 표시한다. 심각도는 critical/high/medium/low를 유지한다.
기존 정보는 아래와 같이 보존하며 세 파트 구조를 이유로 삭제하지 않는다.

- 장애 요약, 심각도, 사용자·서비스 영향과 기간·에러율·지연 수치, 탐지 방법.
- 근본원인 확정/미확정·신뢰도·선택 가설 ID/제목, 가설 경로·기각 목록과 직접 인용.
- 5 Whys, 증거 목록·코드 diff 참조, 사고와 분석의 타임라인.
- 정상화용 임시 조치, 코드 영구 수정, 재발 방지·영향 축소·프로세스 개선 조치 항목.
- 탐지·대응에서 잘된 점, 개선점, 확인된 아차 사례에 대한 교훈.
- 유형별 메트릭·판단 기준·대응 지식인 플레이북과, 사고별 고정 실행 절차인 런북.
- 생성에 실제 사용한 자료의 당시 개정·활용 용도 및 변경 제안. 검색 후보를 사용 자료로 바꾸지 않는다.

원인 상태·신뢰도·선택 가설은 서버 판정과 같고 모델 서술이 이를 바꾸지 못한다.
원인과 기각에는 각각 지지·반증 증거를 연결한다. 5 Whys는 사람 비난에서 멈추지 않고
시스템·프로세스 원인을 탐색하되, 각 연결의 근거가 없으면 사슬을 거기서 중단하고
자료 부족을 표시한다. 다요인인 경우 공동 요인을 보존한다. 운영 개선 담당이 CI 설정을
읽지 못했다는 이유로 검사 부재를 확정하지 않는다.

코드 PR과 CI/CD 변경은 미리보기·작업 제안이다. 실제 저장소·리비전·파일·행·비교 원본을
읽어 최소 diff와 테스트 계획·실행 결과를 구분한다. 소스·테스트 결과가 없으면 미확인·
미실행으로 표시한다. 분석은 PR 게시·머지나 서비스·운영 파이프라인 변경을 하지 않는다.

### 증거 시각과 실행 상태

정상화 전 장애 시간 구간, 현재 배포·소스 식별, 오류·지표 원본 또는 불변 참조를
고정한다. 뒤 원인 분석은 당시 증거를 사용하며 복구 후 정상 관측으로 대체하지 않는다.
복구 결과가 늦게 도착하면 실행 ID·시각을 갖는 별도 증거로 연결하고, 기존 분석 사본에
당시 알고 있었던 사실처럼 덧쓰지 않는다.

실행 성공이 원인 확정·운영 개선 검증을 자동 통과시키지 않는다. 분석 완료도 실제 복구를
뜻하지 않는다. 이미 해결된 실행은 후속 분석 실패로 가려지거나 취소되지 않는다.
실행으로 런북을 검증됨으로 승격하는 회고는 해결된 실행을 요구하는 조건을 유지한다
([ADR 0018](0018-playbook-retrospective.md)).

### 요약·상세 열람과 실패

첫 화면은 정상화 제안과 다음 행동을 먼저 보여주고 원인·운영 파트의 진행·미확정·실패
상태를 별도로 표시한다. 파트 조회 갱신은 실행 폴링과 독립적이며 실행 종료 뒤에도
뒤 분석의 진행·결과를 읽는다. 늦은 조회 응답이 최신 개정본을 덮지 않고 검토 중 런북을
자동 교체하지 않는다. 개정이 바뀌면 재검토가 필요함을 표시한다.

상세는 같은 페이지의 하나의 모달에서 원문·증거·짧은 5 Whys 사슬의 세부 근거·타임라인·
승인 런북·생성 참고·실행 증거·회고를 읽는다. 중첩 모달이나 페이지 전환 없이 닫으면
이전 선택·스크롤로 돌아가며 모바일도 같은 열람 계약이다. 조회 실패는 해당 상세의
오류·재시도로 격리하고 이미 보인 요약을 유지한다.

생성 실패는 실패 사실과 확보한 결과를 보존한다. 원인 미확정 결과는 가장 유력한 후보와
부족한 증거로 표시하고, 정상화 제안 불가를 승인 가능한 절차가 있는 것처럼 쓰지 않는다.
과거 보고서에 없는 새 파트·코드 위치·명령을 만들어 채우지 않으며 원문 열람을 유지한다.

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|---|---|---|
| 원인·리포트 전체 완료 뒤 런북 공개 | 완료 상태 하나로 읽기와 승인을 제어한다. | 정상화 근거가 준비돼도 코드·운영 분석을 기다린다. |
| 세 분석과 실행을 모두 동시에 시작 | 지연을 줄일 수 있다. | 승인 전 쓰기와 증거·산출물 소유권 혼선을 허용한다. |
| 정상화 우선 순차 분석과 별도 승인 실행 | 빠른 검토와 후속 분석의 독립성, 원본·승인 보존을 함께 제공한다. | 단계별 공개·개정·승인 권위와 상태 조회를 관리해야 한다. |

## Consequences

### Positive

- 정상화 런북을 먼저 검토하면서 원인과 운영 개선을 계속 받을 수 있다.
- 근거가 다른 승인 적격·원인 판정·실행·개선 상태를 구분한다.
- 과거 원문·승인 사본과 현재 개정본의 관계를 추적할 수 있다.

### Negative

- 단계별 저장·조회·실패·개정과 최종 보고서 정합성 검증이 필요하다.
- 원인 확정 전 제안에는 불확실성이 남으므로 실제 정상 기준·대상·호환성 검증과 사람 승인이 필요하다.

### Risks

- 롤백이 장애 상태를 바꾼다. 정상화 전 원본을 고정하고 이후 관측을 분리한다.
- 뒤 분석이 승인된 내용을 바꿀 수 있다. 독립 사본과 개정본 조건부 예약·재승인으로 차단한다.
- 부분 결과가 전체 성공으로 읽힐 수 있다. 파트·실행 상태를 따로 표시한다.
