# ADR 0014: 계층형 증거 수집 세션 격리 — 가설별 독립 컨텍스트 윈도우 관리

Date: 2026-04-24
Updated: 2026-09-15

## Status

Proposed

## Context

증거 수집 에이전트가 관측·변경 이력·코드 MCP 도구를 호출하면 **도구 응답이 에이전트 대화 컨텍스트에 누적**된다. 하나의 증거 수집 에이전트를 beam 내 전체 가설에 순차 재사용하면 가설 수가 늘어남에 따라 컨텍스트가 모델 한도를 초과한다. 실제 운영에서 20만 토큰 한도를 넘긴 오버플로우가 관측되었다.

같은 구조는 두 번째 문제도 만든다. 증거 수집이 얻은 **전체 원본 데이터(로그 원본, 메트릭 시계열, 코드 diff)가 오케스트레이터를 거쳐** 검증 단계 프롬프트까지 전달된다. 오케스트레이터가 판단에 필요한 것은 요약 수준인데 실제로는 수십 KB의 원본이 흘러다닌다.

가설 트리가 분기될 때도 문제가 있다. 하위 가설의 증거 수집은 부모 가설이 무엇을 관측했는지 알아야 하지만, 모든 증거가 계층 없는 평면 구조로 관리되면 부모-자식 관계를 반영한 정보 전달을 할 수 없다.

## Decision Drivers

- 가설 수가 늘어나도 증거 수집이 모델 컨텍스트 한도를 넘지 않아야 한다.
- 오케스트레이터와 검증 단계는 판단에 필요한 만큼만 보유해야 한다. 원본 데이터가 상위 단계로 올라오면 후속 단계의 토큰 효율이 함께 나빠진다.
- 하위 가설은 부모 가설의 관측 결과를 알아야 하되, 부모의 원본까지 물려받아서는 안 된다.
- 수집된 원본은 사후 검증을 위해 보존되고 필요할 때 조회할 수 있어야 한다.
- 한 가설의 증거 수집 실패가 다른 가설의 수집을 오염시켜서는 안 된다.

## Decision

**가설별 컨텍스트 격리 + 계층적 요약·핵심 사실 전달**을 채택한다. 도구 응답 크기 제한을 보조 수단으로 병행한다.

### 핵심 결정사항

1. **가설별 독립 증거 수집 컨텍스트**: 가설마다 새 증거 수집 컨텍스트를 만들어 도구 응답 누적을 격리한다. 컨텍스트만 분리하고 MCP 연결은 공유해 초기화 비용을 억제한다.

2. **수집 주체의 직접 영속화**: 수집한 전체 증거를 수집 주체가 상태 저장소(요약·핵심 사실)와 오브젝트 스토리지(원본)에 직접 저장하고, 오케스트레이터에는 **요약·핵심 사실·원본 참조**를 반환한다. 저장 책임을 오케스트레이터에 두면 원본이 반드시 오케스트레이터 컨텍스트를 통과해야 하므로, 저장 책임과 컨텍스트 경량화는 함께 결정된다.

3. **오케스트레이터·검증 컨텍스트 경량화**: 오케스트레이터와 검증 단계는 500자 이내의 산문 요약과 별도 핵심 구조화 사실·원본 참조를 보유한다. 전체 원본은 상위 단계 컨텍스트에 진입하지 않는다.

4. **계층적 정보 흐름**: 하위 가설의 증거 수집 프롬프트에는 **부모 가설의 증거 요약·핵심 사실·원본 참조**를 포함하고 부모의 원본은 전달하지 않는다. 기각된 가설은 기각 사실만 짧게 전달한다. 가설당 산문 요약은 500자 이내이며 핵심 사실은 이 절단 상한 밖에서 보존한다. beam 폭 3 × 깊이 3과 기존 탐색 한도를 유지한다. 하위 가설이 부모의 세부가 필요하면 저장소에서 직접 조회할 수 있는 경로를 열어둔다.

5. **증거 수집 실패 시 CONFIRMED 방지**: 증거 수집이 실패한 가설은 필수 증거를 요구하는 경우 확정을 금지하고 최대 추가조사까지만 허용한다([ADR 0002](0002-hypothesis-tree-lifecycle.md)).

6. **엔진별 컨텍스트 관리**: Headless Codex는 필요한 산출물 파일만 읽고 CLI가 컨텍스트를 관리하므로 Strands의 가설별 컨텍스트 생성 방식을 강제하지 않는다. 두 엔진에 전달되는 핵심 사실의 의미와 미완료 증거 확정 금지 계약은 같다.

7. **도구 응답 크기 제한 (보조 수단)**: 증거 수집 프롬프트에서 로그 쿼리에 결과 상한을 걸고 요약을 지시한다. 단독 해결책이 아닌 방어적 가드레일이다 — 어디서 잘라도 중요 증거를 놓칠 위험이 있으므로 격리를 대체하지 못한다.

8. **원본 증거 온디맨드 조회**: 대시보드는 가설 상세에 요약을 기본 표시하고, 요구 시 저장된 원본 증거를 조회한다. 요약만으로 판단이 어려울 때 사람이 원본을 확인할 수 있어야 격리가 정보 손실이 되지 않는다.

| 오케스트레이터 | 가설당 산문 요약 500자 이내 + 별도 핵심 사실·원본 참조 |

| 하위 가설 프롬프트 | 부모 요약·핵심 사실·원본 참조 |

### 핵심 사실과 수집 생명주기 계약

핵심 사실은 실제 SQLSTATE, SQL의 관계·컬럼 식별자와 지문, 실제 스키마, 태스크 정의와
이미지 연결, 관측 시각·원본 참조다. 산문 축약 시 이 사실이 잘리지 않아야 하며 첫 가설과
최종 검증 입력을 실제 원본과 대조할 수 있어야 한다. 미관측 필드는 미확인으로 남긴다.
다른 서비스·시간 구간·배포의 자료를 합치지 않으며 민감 매개변수나 전체 원본 컨텍스트를
핵심 사실에 넣지 않는다.

수집 상태는 개념적으로 미시작(NOT_STARTED), 실행 중(RUNNING), 실패(FAILED),
완료(COMPLETE)를 구분한다. 이름과 저장 형식은 구현이 정하되 아래 전이를 보존한다.

| 의무 | 관측 가능한 충족 결과 |
|---|---|
| 시작하지 않은 가설은 미시작으로 남긴다. | 예산 부족 사유가 남고 다른 가설의 시간 초과만으로 실패·완료로 바뀌지 않는다. |
| 실제 호출을 시작할 때만 실행 중으로 전이한다. | 시작·종료 시각, 남은 예산, 실제 외부 요청 종료 여부가 남는다. |
| Strands 수집 배치의 1800초와 전체 3600초 예산으로 신규 호출·재시도·실행 순서를 정한다. | 시작 예산이 소진되면 다음 수집을 시작하지 않고 미시작 사유를 남긴다. 이미 데이터를 받는 모델 응답은 총 경과 시간 때문에 끊지 않으며 다른 가설을 거짓 실패로 처리하지 않는다. |
| 미시작 가설은 남은 예산이 있으면 다시 후보가 된다. | 예산이 충분한 후속 차례에 실제 수집을 시작할 수 있다. |
| 동일 가설의 일시적 실패는 최대 1회 재수집한다. | 기존 전체 시간·검증 한도 안에서 재시도 이유와 횟수가 남고 권한·입력 오류는 재시도하지 않는다. |
| 이전 외부 요청이 끝난 것을 확인한 뒤 재수집한다. | 아직 실행 중이거나 종료가 확인되지 않은 요청과 동일 수집을 중복 시작하지 않는다. |
| 같은 사고·대상·조회 범위의 완료 증거만 캐시 재사용한다. | 실패 표식이 성공 캐시로 쓰이지 않고 허용된 재수집 후보를 영구 제외하지 않는다. |
| 유휴 읽기 실패·취소·소유권 상실로 무효화된 시도의 늦은 쓰기를 차단한다. | 이전 결과가 현재 시도의 상태나 완료 증거를 덮지 못한다. 시작 예산만 경과한 활성 응답을 무효 시도로 취급하지 않는다. |
| 실패 전 수신한 원본은 진단용으로 보존한다. | 미완료 증거가 확정 근거로 승격되지 않으며 실패 원본은 사후 조회할 수 있다. |

```mermaid
stateDiagram-v2
    [*] --> NotStarted
    NotStarted --> Running: 남은 예산으로 실제 시작
    Running --> Complete: 유효 시도의 수집 완료
    Running --> Failed: 실패·유휴 한도 초과·취소
    Failed --> Running: 외부 요청 종료 확인·일시 실패 최대 1회
    Complete --> [*]
```

Strands SDK 모델 응답은 스트리밍으로 받으며 첫/다음 소켓 데이터 사이의 300초 유휴 한도를 적용한다.
응답 전체의 총시간 제한은 없고, 수신 중인 응답이 배치·단계·전체 시작 예산을 넘었다는
이유만으로 취소·실패·재시도하지 않는다. 명시적 취소나 소유권 상실은 응답 중단 요청과
늦은 쓰기 차단을 요구한다. 일반 AWS 읽기 한도는 60초다. 이 활성 응답·시작 예산 계약은 Strands SDK에만 적용하며,
Headless 분석의 기존 60분 강제 프로세스 기한은 유지한다.

기존 신뢰도와 확정 규칙, 승인된 시작 예산 및 탐색·검증 횟수는
[가설 트리](0002-hypothesis-tree-lifecycle.md)와 [종료 조건](0006-termination-conditions.md)을
따른다. 특정 데모를 확정 처리하거나 실패한 수집을 완료로 취급하는 예외를 두지 않는다.

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| SDK 내장 슬라이딩 윈도우 대화 관리 | 구현 비용이 거의 없다. | 오래된 **턴**을 제거하는 방식이라 단일 턴 안에서 도구 응답이 폭발하는 경우에 대응하지 못한다. 증거 수집은 한 번의 호출 안에서 여러 도구를 연쇄 호출하므로 윈도우 크기를 조절해도 해결되지 않는다. |
| 도구 응답 크기 제한만 적용 | 기존 구조 변경 없이 적용 가능하다. | 어디서 자를지 결정할 근거가 없고 중요 증거(에러 스택의 마지막 줄, 특정 시각의 스파이크)를 놓칠 수 있다. 근본 해결이 아니라 보조 수단으로만 유효하다. |
| 가설별 격리 (평면) | 오버플로우를 근본 해결하고 가설 간 도구 결과가 섞이지 않는다. | 하위 가설이 부모의 관측 결과를 물려받지 못해 분기 이후 탐색이 부모의 발견을 반복한다. |
| 가설별 격리 + 계층적 요약 전달 | 오버플로우를 해결하면서 트리 구조를 따라 관측 결과가 전달되고, 상위 단계는 추상화된 정보만 보유한다. | 요약 품질이 하위 분석과 검증 정확도에 직접 영향을 주고, 계층 간 정보 전달 로직이 추가된다. |

## Consequences

### Positive

- 컨텍스트 오버플로우 근본 해결 — 가설별 격리로 여러 가설의 도구 결과가 누적되지 않는다
- 오케스트레이터 경량화로 검증·분기 등 후속 단계의 토큰 효율 향상
- 계층적 추상화로 트리 깊이가 증가해도 상위 수준의 판단 품질 유지
- 전체 증거가 영속화되므로 요약이 부족할 때 사람이 원본을 조회할 수 있다
- 가설별 격리로 한 가설의 증거 수집 실패가 다른 가설에 영향을 주지 않음

### Negative

- 가설마다 수집 컨텍스트를 만들므로 초기화 비용이 증가한다 (MCP 연결 공유로 완화)
- 요약·핵심 사실·원본 참조의 정합성과 수집 상태를 함께 관리해야 한다
- 수집 주체가 저장소에 직접 쓰므로 수집 경로에 저장 의존성을 주입해야 한다

### Risks

- **요약 품질 의존**: 증거 요약의 품질이 낮으면 검증이 잘못된 판단을 내린다. 시간·수치·오류의 핵심 사실을 별도로 보존하고 원본과 대조한다. 모델의 요약 품질만으로 사실 전달을 보장하지 않는다.
- **MCP 연결 비용**: 가설마다 도구 서버에 재연결하면 지연이 발생한다. 연결을 상위에서 만들어 공유하고 컨텍스트만 분리해 완화한다.
- **단일 가설 내 오버플로우**: 한 가설에 대해서도 도구 호출이 과도하면 한도를 넘을 수 있다. 관측된 오버플로우는 여러 가설의 결과가 한 컨텍스트에 누적된 경우였고, 단일 가설만으로는 도달하기 어렵다. 도구 응답 크기 제한을 보조 방어로 병행한다.
