# ADR 0018: 플레이북 회고 — 실행 증거로 절차를 교정하는 학습 루프

Date: 2026-07-30
Updated: 2026-09-17

## Status

Proposed

## Context

플레이북은 장애 유형별 메트릭·판단 기준·대응 지식이며, 런북은 이번 사고의 구체
명령과 대상·순서·성공 기준이다. 새 런북은 실행으로 검증되지 않은 초안이다.
실행 에이전트가 승인된 런북의 명령을 수행하면([ADR 0017](0017-playbook-execution-agent.md))
그 과정에서 인자 오류, 권한 부족, 선행 조건 누락 같은 실패가 드러나고, 에이전트는
실패 증거를 남긴다. 다른 명령이 필요한 교정은 새 런북과 승인으로 이어진다.

이 교정 과정이 플레이북에 반영되지 않으면 같은 유형의 장애에서 같은 실수를 반복한다.
새 RCA(근본원인분석)의 결과와 함께 실행 과정에서 드러난 명령별 실패와 관측도 교정 근거로
남겨야 한다. 실행 상태의 요약만으로는 어떤 명령과 선행 조건이 잘못됐는지 알 수 없다.

또한 개선의 근거를 사람이 검토할 수 없으면 자동 갱신을 신뢰할 수 없다. 플레이북이
런북 작성의 근거이므로, 무엇을 근거로 어떻게 바꿨는지가 남아야 한다. 바뀐 명령은
새 승인 없이 실행할 수 없다.

## Decision Drivers

- 실행 중 발생한 명령 오류가 플레이북 교정으로 이어져야 한다.
- 미해결 장애의 절차가 검증된 절차로 승격되어서는 안 된다.
- 실행으로 입증된 절차는 검증됨으로 표기되어야 한다. 사람이 승인 판단에서 초안과
  입증된 절차를 구분하지 못하면 초안 표기 자체가 의미를 잃는다.
- 갱신의 근거와 변경 내용을 사람이 대조할 수 있어야 한다.
- 회고 실패가 이미 확정된 실행 결과를 훼손해서는 안 된다.
- 갱신이 기존 플레이북의 축적을 되돌려서는 안 된다.

## Decision

**실행이 이슈를 해소한 직후 회고를 자동 수행**하고, 실행 증거를 종합해 플레이북을
갱신한다.

### 진입 조건 — 해결된 실행만

회고는 실행 상태가 해결로 확정된 직후에만 시작한다. 미해결과 실패는 회고 대상이
아니다. 이슈를 해소하지 못한 실행의 절차는 올바름이 입증되지 않았으므로, 그 명령을
검증된 절차로 승격하면 플레이북이 오히려 나빠진다.

실패한 실행의 증거는 보존되어 사람이 읽을 수 있지만, 자동 갱신의 입력으로는 쓰지
않는다.

### 자동 트리거

해결 확정과 회고 시작 사이에 사람의 개입을 두지 않는다. 개선의 가치는 다음 장애가
오기 전에 반영되는 데 있고, 사람의 검토를 트리거 조건으로 두면 축적이 검토 대기에
막힌다. 사람의 검토는 갱신 결과를 열람하는 사후 경로로 둔다.

### 갱신 대상 — 실행에서 드러난 결함

회고는 유형별 플레이북 지식과 이번 사고의 런북을 구분하여 교정한다.
실행 중 승인 범위를 바꿀 수 없으므로 다른 명령이나 대상이 필요한 교정은
현재 실행에 적용하지 않는다. 교정된 런북은 새 승인 대상이며 과거 승인
스냅샷과 실행 증거는 그대로 보존한다.

회고는 실행 증거에서 **절차의 결함으로 환원되는 실패**를 찾아 해당 절차를 교정한다.
교정 대상은 다음이다.

- 잘못된 인자와 누락된 필수 인자
- 빠진 선행 조건과 순서 오류
- 실제로는 불필요했던 단계
- 관측으로 해결을 확정하기 위해 필요했던 검증 절차

일시적 오류와 환경 요인은 절차의 결함이 아니므로 교정하지 않는다. 재시도로 같은
명령이 성공했다면 절차 자체는 옳았다.

### 검증 상태 — 현재 런북 내용에 종속

플레이북의 검증 상태가 가질 수 있는 값은 **초안과 검증됨 둘뿐**이다. 상태는 플레이북
식별자에 영구히 붙는 등급이 아니라 **현재 런북 내용이 해결된 실행으로
입증되었는지**를 뜻한다.

승격은 **해결된 실행의 회고가 갱신을 반영할 때에만** 일어난다. 회고가 이 상태의 유일한
승격 주체인 이유는 해결 판정과 절차 교정을 모두 통과한 지점이 여기뿐이기 때문이다.
회고가 교정할 결함을 찾지 못해 갱신이 없더라도 승격은 일어난다 — 절차가 그대로
이슈를 해소했다면 그것이 가장 강한 검증이다. 단, 무변경 판정도 판단 근거와 빈
갱신안을 가진 회고 산출물이 영속화되어야 한다. 모델 프로세스가 성공 종료했지만 회고
산출물이 없으면 검토를 완료했다는 증거가 아니므로 회고 실패로 기록한다. 반대로
회고가 실패하면 승격도 일어나지 않는다. 갱신을 반영하지 못한 회고는 절차를 확인한
것이 아니다.

회고가 설명·태그처럼 실행 절차 밖의 메타데이터만 바꾸면 실행된 절차 내용은 같으므로
검증됨으로 승격하거나 기존 검증됨을 유지한다. 그러나 회고나 이후 분석 병합이
런북 내용을 추가·교정하면 결과는 초안이다. 교정의 근거가 해결된 실행에
있더라도 새 절차 본문 자체는 아직 실행되지 않았으므로, 다음 실행과 회고가 그 내용을
입증해야 다시 검증됨이 된다.

이 상태는 **서버가 소유한다.** 모델이 반환한 갱신안에 검증 상태가 담겨 있어도
무시한다. 분석 단계도 이 값을 올릴 수 없으며 초안만 쓸 수 있다
([ADR 0008](0008-playbook-generation.md)). LLM(대규모 언어 모델)의 출력이 검증 여부의 권위가 되면
실행되지 않은 절차가 검증됨으로 표기되어 사람이 승인 판단의 근거로 삼는다.

병합은 기존 내용을 누락했다는 이유만으로 상태를 낮추지 않는다. 실행 절차가 동일하면
검증됨을 보존하고, 절차 내용이 달라진 경우에만 초안으로 전환한다. 축적 보존은
절차와 메타데이터의 유실을 막는 규칙이지, 실행되지 않은 새 절차에 과거 검증 상태를
상속하는 규칙이 아니다.

### 축적 보존

갱신은 추가와 교정만 수행하고 기존 내용을 삭제하지 않는다. 이 규칙은 프롬프트
지시가 아니라 코드로 보장한다 — 모델이 필드를 누락해 반환하면 기존 값을 유지한다.
비실행 지식 병합도 이 축적 규칙을 사용한다. 두 분석 엔진의
새 RCA 전체 실행 계획은 별도 계약이며, 이 회고의 부분 교정·과거 승인 스냅샷 보존 규칙을
변경하지 않는다([ADR 0008](0008-playbook-generation.md#현재-사고-전체-계획의-권위)).

갱신은 기존 플레이북 식별자를 유지한 채 내용을 바꾼다. 새 식별자로 분기하면 같은
장애 유형의 지식이 흩어진다.

### 열람 계약

회고 결과는 다음 네 가지를 **함께** 조회할 수 있어야 한다.

1. 이슈 — 어떤 장애였는지
2. 실행 전 플레이북과 승인 런북 — 무엇을 근거로 실행했는지
3. 실행 증거 — 승인된 명령의 시도, 실패, 재시도와 관측
4. 갱신 diff — 그 결과 절차가 어떻게 바뀌었는지

이 넷이 분리되어 조회되면 갱신의 타당성을 판단할 수 없다. 실행 전 플레이북은 갱신
시점에 별도로 보존해야 한다 — 갱신이 원본을 덮어쓰므로 사후에 복원할 수 없다.

### 비차단 실행

회고 실패는 실행 결과를 되돌리지 않는다. 이미 이슈는 해소되었고 그 사실은 확정된
상태다. 회고는 실패를 기록하고 종료하며, 플레이북은 갱신 전 상태로 남는다.

개정본과 검색 인덱스는 같은 플레이북 내용을 게시해야 한다. 두 저장이 모두 성공한
경우에만 회고 갱신을 완료로 기록하며, 저장이 실패 결과를 반환하는 경우도 실패로
처리한다. 상태 저장소에 먼저 실행별 준비 개정본을 저장하고, 검색 인덱스에도
같은 실행을 가리키는 게시 식별자를 쓴다. 그 뒤 정식 개정본을 같은 식별자로
게시 완료로 확정하고 준비본을 삭제한다. 검색은 정식 개정본과 검색 인덱스의
게시 식별자가 일치할 때만 검증됨을 노출한다. 따라서 검색 인덱스 게시 뒤 정식 개정본
확정이 실패해도 미완료 승격이 검색 결과에 검증됨으로 보이지 않는다. 보상 쓰기로
이전 벡터를 복원하는 것은 권위 계약이 아니며, 실패한 회고는 준비본과 진단 로그를
남기고 종료한다.

### 실행과 독립된 원인·운영 분석과의 구분

정상화 우선 분석의 근본원인·코드 PR 미리보기와 운영 개선·CI/CD 제안은 이 실행 회고와
다른 책임이다. 두 분석은 런북 승인·실행·해결 여부를 기다리지 않고 순차 수행한다.
미실행·실패 상태에서도 관측과 한계를 근거로 제안할 수 있으나, 이를 실행 성공이나
검증된 런북으로 승격하는 근거로 쓰지 않는다.

이 회고의 해결된 실행 전용 진입·실행 증거·절차 동일성·게시 일치·원본 보존 조건은
유지한다. 조기 런북 실행이 전체 분석보다 먼저 해결돼도 승인 사본은 불변이고, 원인·운영
결과가 나중에 갱신됐다는 이유로 승인 내용을 교체하지 않는다. 공개 기준 원문이 아직
없거나 게시 준비 중이면 원본·상태를 검증하지 않은 공개 교정·승격을 하지 않고 그 사유를
별도로 보존한다. 이 후속 상태가 이미 확정된 실행 해결이나 뒤 분석을 취소하지 않는다.

| 성공·실패 무관하게 항상 회고                  | 실패 원인 지식도 축적된다.                                  | 이슈를 해소하지 못한 절차가 검증된 절차로 승격되어 플레이북이 나빠진다.                           |
| 사람이 대시보드에서 회고를 트리거             | 잘못된 갱신을 사전에 막는다.                                | 축적이 검토 대기에 막혀 다음 장애 전에 반영되지 않는다. 자동화의 이점이 사라진다.                 |
| 해결된 실행 직후 자동 회고 + 사후 열람        | 다음 장애 전에 반영되고, 갱신 근거를 사람이 대조할 수 있다. | 잘못된 갱신이 일단 반영되므로 다음 실행 전에 사람이 읽지 않으면 걸러지지 않는다.                  |

| ----------------------------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------- |
| 한 번 획득한 `VERIFIED`를 플레이북 식별자에 영구 보존 | 상태가 단조 증가하고 구현이 단순하다.      | 실행되지 않은 새 `execution_steps`도 검증된 것으로 표시되어 상태 의미가 무너진다. |
| 현재 `execution_steps` 내용이 바뀌면 `DRAFT`로 전환   | 상태가 실제로 실행된 절차 내용과 일치한다. | 교정된 절차는 다음 해결 실행까지 다시 초안으로 보인다.                            |

## Consequences

### Positive

- 실행에서 드러난 명령 오류가 다음 실행 전에 절차로 교정된다.
- 플레이북의 절차가 실행과 회고를 거치며 개선된다.
- 갱신의 근거와 결과를 대조할 수 있어 자동 갱신을 신뢰할 근거가 생긴다.
- 회고 실패가 확정된 실행 결과에 영향을 주지 않는다.
- 초안과 실행으로 입증된 절차가 구분되어, 사람이 승인 판단에서 절차의 신뢰도를
  읽을 수 있다.

### Negative

- 실행 전 플레이북 사본을 별도 보존해야 하므로 저장량이 늘어난다.
- 잘못된 갱신도 사람 검토 전에 게시되므로, 다음 승인자가 교정된 런북을 검토해야 한다.
- 실패한 실행에서는 학습이 일어나지 않아 반복 실패 유형의 지식이 축적되지 않는다.
- 회고가 실패하면 갱신 전 검증 상태를 유지한다. 초안이었던 런북은 해결된 실행과
  회고가 다시 완료될 때까지 승격되지 않는다.
- 절차를 교정한 회고는 해결된 실행 뒤에도 개정본을 `DRAFT`로 게시한다. 교정된 절차는
  다음 해결 실행까지 검증됨으로 표시되지 않는다.

### Risks

- 일시적 오류를 절차 결함으로 오분류하면 불필요한 방어 단계가 절차에 쌓인다.
  재시도로 성공한 명령은 절차가 옳았다는 판단 기준을 유지한다.
- 갱신이 기존 절차를 덮어써 축적이 사라질 수 있다. 삭제 금지를 코드로 보장하고
  실행 전 사본을 보존한다.
- 실행 증거가 커지면 회고 입력이 컨텍스트 한도를 넘을 수 있다. 절차 단위로 증거를
  묶어 요약하고, 요약 실패는 회고 실패로 처리해 잘못된 갱신보다 미갱신을 택한다.
- 같은 실행에 회고가 중복 실행되면 diff가 중복 반영될 수 있다. 회고는 실행 단위로
  한 번만 수행되도록 처리 소유권인 claim으로 보장한다.
- 병합 경로가 검증 상태를 재구성 대상에서 빠뜨리면 절차가 동일한데도 승격이 조용히
  취소될 수 있다. 두 엔진 모두 절차 동일성 비교를 거쳐, 동일하면 상태를 보존하고
  달라지면 `DRAFT`로 전환하는 계약을 테스트로 고정한다.
- 개정본과 벡터 인덱스 중 하나만 갱신되면 승인과 다음 분석이 서로 다른 플레이북을
  읽을 수 있다. 실행별 준비본, 게시 식별자, 정식 개정본의 확정 상태를 대조하고
  불일치하면 검색 결과를 초안으로 낮춰 부분 게시를 검증됨으로 숨기지 않는다.

### 관찰 가능한 완료 조건

- 갱신 없는 회고와 메타데이터만 바꾼 회고는 승격되고, 실행 절차를 추가·교정한 회고는
  `DRAFT`로 남으며 개정본과 검색 인덱스 양쪽에 같은 상태가 반영됨을 확인
- 미해결 실행은 회고에 진입하지 않으며 승격과 개정본 저장이 없음을 확인
- 회고 게시가 실패하면 정식 게시와 승격을 완료로 기록하지 않으며, 준비본과 진단
  기록을 보존하고 검색에서 미완료 승격을 노출하지 않음을 확인
- 프로세스가 성공 종료해도 영속화된 회고 산출물이 없으면 회고 실패로 기록되고
  승격하지 않음을 확인
- 벡터 게시 뒤 정식 개정본 확정이 실패해도 게시 식별자가 일치하지 않아
  검색 결과가 `VERIFIED`로 노출되지 않음을 확인
- 모델이 갱신안에 검증 상태를 담아도 무시되고, 상태는 서버의 절차 동일성 판정으로만
  결정됨을 확인
- 승격과 교정이 갱신 전 사본의 내용을 바꾸지 않음을 확인
- 읽을 수 없는 기록 값이 검증됨으로 되살아나지 않고 초안으로 처리됨을 확인
- 두 엔진 모두 검증 상태가 초안과 검증됨뿐이며, 동일 절차는 상태를 보존하고
  변경된 절차는 초안으로 전환함을 확인
- 승인 화면이 개정본을 통해 상태를 읽고, 기록된 검증됨 외의 값은 초안으로 표시함을
  확인 — 분석 산출물만 읽으면 승격이 영구히 보이지 않는다
- 교정된 런북을 새 승인 없이 실행할 수 없고 과거 승인 사본과 실행 증거가
  교정 전 내용으로 보존됨을 확인
