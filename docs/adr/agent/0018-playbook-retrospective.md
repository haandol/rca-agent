# ADR 0018: 플레이북 회고 — 실행 증거로 절차를 교정하는 학습 루프

Date: 2026-07-30
Updated: 2026-07-31

## Status

Accepted (2026-07-31)

## Context

플레이북은 RCA 결과에서 생성되는 초안이다. 실제로 실행해 보기 전까지는 절차의
명령이 올바른 인자를 쓰는지, 필요한 선행 조건을 빠뜨리지 않았는지 알 수 없다. 실행
에이전트가 플레이북을 근거로 명령을 수행하면([ADR 0017](0017-playbook-execution-agent.md))
그 과정에서 인자 오류, 권한 부족, 선행 조건 누락 같은 실패가 드러나고, 에이전트는
교정해 가며 결국 이슈를 해소한다.

이 교정 과정이 플레이북에 반영되지 않으면 같은 유형의 장애에서 같은 실수를 반복한다.
기존 축적 경로는 다음 RCA가 유사도 검색으로 플레이북을 찾아 LLM이 보강 여부를
판단하는 방식인데, 그 입력은 새 RCA의 분석 결과다. **실행 과정에서 무엇이 실패했는지는
어디에도 입력되지 않는다.** 실행 증거는 실행이 끝나면 상태 요약만 남고 명령 단위
실패는 사라진다.

또한 개선의 근거를 사람이 검토할 수 없으면 자동 갱신을 신뢰할 수 없다. 플레이북이
실행 근거가 된 이상 잘못된 갱신은 다음 실행의 잘못된 명령으로 직결되므로, 무엇을
근거로 어떻게 바꿨는지가 남아야 한다.

## Decision Drivers

- 실행 중 발생한 명령 오류가 플레이북 교정으로 이어져야 한다.
- 미해결 장애의 절차가 검증된 절차로 승격되어서는 안 된다.
- 실행으로 입증된 절차는 검증됨으로 표기되어야 한다. 사람이 승인 판단에서 초안과
  입증된 절차를 구분하지 못하면 초안 표기 자체가 의미를 잃는다.
- 갱신의 근거와 변경 내용을 사람이 대조할 수 있어야 한다.
- 회고 실패가 이미 확정된 실행 결과를 훼손해서는 안 된다.
- 갱신이 기존 플레이북의 축적을 되돌려서는 안 된다.

## Decision

**실행이 이슈를 해소한 직후 회고를 자동 수행**하고, 실행 증거를 종합해 플레이북을
갱신한다.

### 진입 조건 — 해결된 실행만

회고는 실행 상태가 해결로 확정된 직후에만 시작한다. 미해결과 실패는 회고 대상이
아니다. 이슈를 해소하지 못한 실행의 절차는 올바름이 입증되지 않았으므로, 그 명령을
검증된 절차로 승격하면 플레이북이 오히려 나빠진다.

실패한 실행의 증거는 보존되어 사람이 읽을 수 있지만, 자동 갱신의 입력으로는 쓰지
않는다.

### 자동 트리거

해결 확정과 회고 시작 사이에 사람의 개입을 두지 않는다. 개선의 가치는 다음 장애가
오기 전에 반영되는 데 있고, 사람의 검토를 트리거 조건으로 두면 축적이 검토 대기에
막힌다. 사람의 검토는 갱신 결과를 열람하는 사후 경로로 둔다.

### 갱신 대상 — 실행에서 드러난 결함

회고는 실행 증거에서 **절차의 결함으로 환원되는 실패**를 찾아 해당 절차를 교정한다.
교정 대상은 다음이다.

- 잘못된 인자와 누락된 필수 인자
- 빠진 선행 조건과 순서 오류
- 실제로는 불필요했던 단계
- 관측으로 해결을 확정하기 위해 필요했던 검증 절차

일시적 오류와 환경 요인은 절차의 결함이 아니므로 교정하지 않는다. 재시도로 같은
명령이 성공했다면 절차 자체는 옳았다.

### 검증 상태의 승격 — 회고가 유일한 승격 주체

플레이북의 검증 상태가 가질 수 있는 값은 **초안과 검증됨 둘뿐**이며, 허용되는 전이는
초안 → 검증됨 **한 방향뿐이다**. 검증됨에서 초안으로 되돌리는 전이는 없다 — 한 번
실행으로 입증된 절차가 이후 분석이나 병합으로 미검증 상태로 떨어지면, 상태가
"실행으로 입증되었는가"를 더 이상 뜻하지 않는다.

승격은 **해결된 실행의 회고가 갱신을 반영할 때에만** 일어난다. 회고가 이 상태의 유일한
승격 주체인 이유는 해결 판정과 절차 교정을 모두 통과한 지점이 여기뿐이기 때문이다.
회고가 교정할 결함을 찾지 못해 갱신이 없더라도 승격은 일어난다 — 절차가 그대로
이슈를 해소했다면 그것이 가장 강한 검증이다. 반대로 회고가 실패하면 승격도 일어나지
않는다. 갱신을 반영하지 못한 회고는 절차를 확인한 것이 아니다.

이 상태는 **서버가 소유한다.** 모델이 반환한 갱신안에 검증 상태가 담겨 있어도
무시한다. 분석 단계도 이 값을 올릴 수 없으며 초안만 쓸 수 있다
([ADR 0008](0008-playbook-generation.md)). LLM 출력이 검증 여부의 권위가 되면
실행되지 않은 절차가 검증됨으로 표기되어 사람이 승인 판단의 근거로 삼는다.

병합은 이 상태를 낮추지 않는다. 검증된 플레이북을 이후 RCA가 유사도 검색으로 찾아
보강할 때, 갱신된 내용이 실행으로 입증되지 않았더라도 이미 획득한 검증 상태는
유지된다. 축적 보존과 같은 이유다 — 병합이 되돌리지 않는 것에 검증 상태도 포함된다.

### 축적 보존

갱신은 추가와 교정만 수행하고 기존 내용을 삭제하지 않는다. 이 규칙은 프롬프트
지시가 아니라 코드로 보장한다 — 모델이 필드를 누락해 반환하면 기존 값을 유지한다.
플레이북 생성 단계가 같은 규칙을 쓰는 이유와 동일하다
([ADR 0008](0008-playbook-generation.md)).

갱신은 기존 플레이북 식별자를 유지한 채 내용을 바꾼다. 새 식별자로 분기하면 같은
장애 유형의 지식이 흩어진다.

### 열람 계약

회고 결과는 다음 네 가지를 **함께** 조회할 수 있어야 한다.

1. 이슈 — 어떤 장애였는지
2. 실행 전 플레이북 — 무엇을 근거로 실행했는지
3. 실행 증거 — 무엇이 어떻게 실패하고 교정되었는지
4. 갱신 diff — 그 결과 절차가 어떻게 바뀌었는지

이 넷이 분리되어 조회되면 갱신의 타당성을 판단할 수 없다. 실행 전 플레이북은 갱신
시점에 별도로 보존해야 한다 — 갱신이 원본을 덮어쓰므로 사후에 복원할 수 없다.

### 비차단 실행

회고 실패는 실행 결과를 되돌리지 않는다. 이미 이슈는 해소되었고 그 사실은 확정된
상태다. 회고는 실패를 기록하고 종료하며, 플레이북은 갱신 전 상태로 남는다.

## 대안 검토

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 다음 RCA의 유사도 검색으로만 보강 (기존 경로) | 추가 단계가 없고 이미 동작한다. | 입력이 새 RCA의 분석 결과이므로 실행 중 드러난 명령 오류가 반영되지 않는다. 같은 실수가 반복된다. |
| 성공·실패 무관하게 항상 회고 | 실패 원인 지식도 축적된다. | 이슈를 해소하지 못한 절차가 검증된 절차로 승격되어 플레이북이 나빠진다. |
| 사람이 대시보드에서 회고를 트리거 | 잘못된 갱신을 사전에 막는다. | 축적이 검토 대기에 막혀 다음 장애 전에 반영되지 않는다. 자동화의 이점이 사라진다. |
| 해결된 실행 직후 자동 회고 + 사후 열람 | 다음 장애 전에 반영되고, 갱신 근거를 사람이 대조할 수 있다. | 잘못된 갱신이 일단 반영되므로 다음 실행 전에 사람이 읽지 않으면 걸러지지 않는다. |

검증 상태의 승격 주체에 대한 대안:

| 대안 | 장점 | 단점 및 미채택 이유 |
|------|------|---------------------|
| 초안 단일 상태로 두고 승격하지 않음 | 상태 전이가 없어 구현이 가장 단순하고 잘못된 승격도 없다. | 모든 플레이북이 영구히 초안이므로 초안 표기가 아무것도 구분하지 못한다. 실행으로 입증된 절차와 한 번도 실행되지 않은 절차가 사람에게 같은 신뢰도로 보인다. |
| 해결 판정 직후 실행 에이전트가 승격 | 회고 실패와 무관하게 입증 사실이 반영된다. | 회고가 교정할 결함을 찾기 전에 승격되므로, 인자 오류를 남긴 절차가 검증됨으로 표기된다. 실행이 성공했다는 것과 절차가 옳다는 것은 다르다. |
| 모델이 갱신안에 검증 상태를 담아 반환 | 추가 코드가 없다. | LLM 출력이 검증 여부의 권위가 되어, 실행되지 않은 절차가 검증됨으로 표기될 수 있다. 승인 판단의 근거가 무너진다. |
| 해결된 실행의 회고 반영 시점에 서버가 승격 | 해결 판정과 절차 교정을 모두 통과한 지점이며 권위가 서버에 남는다. | 회고가 실패하면 입증된 실행도 승격되지 않아 다음 실행까지 초안으로 남는다. |

## Consequences

### Positive

- 실행에서 드러난 명령 오류가 다음 실행 전에 절차로 교정된다.
- 플레이북의 정확성이 실행 횟수에 따라 단조 개선된다.
- 갱신의 근거와 결과를 대조할 수 있어 자동 갱신을 신뢰할 근거가 생긴다.
- 회고 실패가 확정된 실행 결과에 영향을 주지 않는다.
- 초안과 실행으로 입증된 절차가 구분되어, 사람이 승인 판단에서 절차의 신뢰도를
  읽을 수 있다.

### Negative

- 실행 전 플레이북 사본을 별도 보존해야 하므로 저장량이 늘어난다.
- 잘못된 갱신이 사람 검토 전에 반영되므로, 다음 실행이 그 절차를 쓸 수 있다.
- 실패한 실행에서는 학습이 일어나지 않아 반복 실패 유형의 지식이 축적되지 않는다.
- 회고가 실패하면 이슈를 해소한 실행의 절차도 초안으로 남는다. 다음 실행이 해결되면
  그때 승격되므로 승격이 지연될 뿐 유실되지는 않는다.
- 검증됨은 한 번 획득하면 내려가지 않으므로, 이후 병합이 절차를 나쁘게 바꾸어도 상태는
  검증됨을 유지한다. 갱신 diff 열람이 이 경우를 사람이 발견하는 경로다.

### Risks

- 일시적 오류를 절차 결함으로 오분류하면 불필요한 방어 단계가 절차에 쌓인다.
  재시도로 성공한 명령은 절차가 옳았다는 판단 기준을 유지한다.
- 갱신이 기존 절차를 덮어써 축적이 사라질 수 있다. 삭제 금지를 코드로 보장하고
  실행 전 사본을 보존한다.
- 실행 증거가 커지면 회고 입력이 컨텍스트 한도를 넘을 수 있다. 절차 단위로 증거를
  묶어 요약하고, 요약 실패는 회고 실패로 처리해 잘못된 갱신보다 미갱신을 택한다.
- 같은 실행에 회고가 중복 실행되면 diff가 중복 반영될 수 있다. 회고는 실행 단위로
  한 번만 수행되도록 claim으로 보장한다.
- 병합 경로가 검증 상태를 재구성 대상에서 빠뜨리면 승격이 조용히 취소되어, 검증됨이
  다음 RCA의 보강 한 번으로 초안으로 돌아간다. 어느 쪽 엔진에서든 상태를 낮추는
  전이가 성립하지 않음을 계약 테스트로 고정한다. 구현 시점에 이 결함이 실제로 두 곳에
  있었다 — 보강 결과를 필드마다 조립하는 경로와 기록을 다시 읽는 경로 모두 이 값을
  빠뜨려, 회고가 승격해도 다음 보강이나 다음 로드에서 초안으로 되돌아갔다. 두 경로
  모두 기본값으로 흡수되어 오류를 내지 않았다.

### 검증

- 갱신 없는 회고, 교정을 반영한 회고 모두 승격되고, 개정본과 검색 인덱스 양쪽에 같은
  상태가 반영됨을 확인
- 회고 실패와 미해결 실행에서 승격도 개정본 저장도 일어나지 않음을 확인
- 모델이 갱신안에 검증 상태를 담아도 무시되고, 검증됨을 초안으로 낮추려는 갱신안도
  반영되지 않음을 확인
- 승격이 원본 딕셔너리를 제자리에서 바꾸지 않아 갱신 전 사본이 오염되지 않음을 확인
- 읽을 수 없는 기록 값이 검증됨으로 되살아나지 않고 초안으로 처리됨을 확인
- 두 엔진의 상태 어휘가 같은 두 값이고 상태를 낮추는 연산이 어느 쪽에도 없음을 계약
  테스트로 확인
- 승인 화면이 개정본을 통해 상태를 읽고, 기록된 검증됨 외의 값은 초안으로 표시함을
  확인 — 분석 산출물만 읽으면 승격이 영구히 보이지 않는다
- `pnpm verify` 통과 (agent 506, cc-headless 494, healthcare 42, infra 30, 계약 47,
  오프라인 평가 8), dashboard·infra build 통과
