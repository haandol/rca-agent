# 두 엔진 실모델 평가 결과

Strands와 Headless를 각각 실행했다. 두 엔진 모두 `timestamp` 대신 존재하지 않는
`sampled_at`을 INSERT 컬럼으로 사용한 결함을 원인으로 확정했지만, 필수 평가
조건은 통과하지 못했다. 평가 기준선은 `pending`을 유지했고 푸시하지 않았다.

실모델 입력은 `563378f`의 `write-column-regression` 시나리오다. 입력 지문은
`sha256:4235f059e5c8e75c4dc3253be37febf13558323726a979db172dbf6c3a373cc7`이다.
실행 식별자는 UTC 기준 `20260916T232909Z`다. 실제 로컬 PostgreSQL 관측을
제공한 모델 평가이며, AWS 장애 주입·증거 탐색·승인 실행·복구 성공의 측정은 아니다.

## 최종 판정

| 항목 | Strands | Headless |
|---|---|---|
| 모델의 원인 확정 | 컬럼 불일치 확정, 신뢰도 0.90 | 컬럼 불일치 확정 |
| 원인 판정과 필수 증거 연결 | 실패: 직접 인용에 obs-02·03 누락 | 통과 |
| 전체 필수 증거 인용 | 통과: obs-01~05 | 실패: obs-05 누락 |
| 필수 분석 산출물 | 통과 | 통과 |
| 연결 누수 대안 기각 | 통과 | 실패: 유효한 기각 판정 없음 |
| 실행 가능한 안전한 복구 절차 | 실패: 실행 단계 없음 | 실패: 실행 단계 없음 |
| 전체 평가 | 실패 | 실패 |

Strands의 `rootCauseIdentified=false`는 원인을 잘못 추론했다는 뜻이 아니다.
평가기의 이 항목은 올바른 유형·확정 상태와 함께 원인 판정에 직접 연결된 필수
관측 인용도 요구한다. 이 실행의 직접 인용은 obs-01·04뿐이었다. 가설 본문이나
보고서의 일반 인용을 확정 판정의 인용으로 소급해 채우지 않았다.

Headless는 원인 판정에 obs-01~04를 연결했다. 그러나 obs-05를 필수 증거로
인용하지 않았고, 연결 누수를 `rejected`로 판정한 유효한 validation 항목도 없어
그 대안은 정규화 결과에서 `inconclusive`로 남았다.

두 엔진 모두 파괴적인 복구 명령을 실행한 것은 아니다. 모델 평가는 실행하지 않는다.
`remediationSafe` 실패에는 실행 가능한 절차가 비어 있다는 조건이 포함된다.

## 복구 절차를 만들지 않은 이유

현재 시나리오는 `requireExecutableRemediation=true`를 요구하지만, 입력은 로컬
PostgreSQL 관측과 합성 알람 외곽 정보다. 실제 ECS 서비스·정상 태스크 정의·이미지
지문과 서버가 검증한 정상 기준이 없다. 두 엔진 모두 이 정보를 추정하지 않고
`execution_steps=[]`, `rollback_context=null`인 초안을 만들었다.

이 불일치를 해결하려면 같은 실제 AWS 사고에 속한 정상 기준 원본, 배포 대상,
사고 시점의 서비스·태스크 관측을 확보하고 서버가 검증해 재생할 수 있어야 한다.
과거 승인 명령이나 복구 결과를 모델 입력으로 넣거나, 현재 로컬 사고에 다른
실행의 AWS 대상을 붙이면 안 된다. 단순히 필수 실행 조건을 끄는 방식도 적용하지 않았다.

## Headless 실행 환경

첫 시도는 로컬 CLI 0.154.0이었다. SSE 응답 데이터가 오지 않아 idle timeout과
재연결이 발생했다. 이후 일부 응답은 받았으나, 배포용 Dockerfile이 고정한 0.151.0과
버전이 달라 이 시도는 중단하고 판정에서 제외했다.

별도 임시 도구 경로에 0.151.0을 설치한 뒤 같은 입력으로 다시 실행했다.
RCA와 report 프로세스는 모두 종료 코드 0으로 완료됐고, 정규화 결과를 얻은 뒤
필수 평가 조건에서 실패했다. 버전을 맞춘 재실행은 완료됐지만, 이 한 번의 비교로
앞선 연결 오류의 원인이 CLI 버전이었다고 단정하지 않는다.

모델 ID, reasoning effort, provider는 배포 태스크에서 읽은 값과 일치했다.
사용자 전역 CLI나 배포 이미지는 변경하지 않았다.

## 발견한 평가기 결함과 수정

Strands는 플레이북을 생성·저장했지만, 평가기가 revision 없는 공개 라이브러리
조회로 다시 읽으려 해서 상세가 없는 것으로 채점했다. 공개 라이브러리는 revision
일치를 요구하므로 이 조회는 거부된다.

평가기가 이미 읽은 완료 기록의 `CompletionHandoff.playbook`을 사용하도록
수정했다. 완료 상태, 요청한 RCA ID, 완료 기록·알림·플레이북의 RCA ID, 플레이북 ID가
모두 일치해야 상세를 채점한다. 이후 변경될 수 있는 최신 공개본을 대신 읽지 않는다.

실제 보존 스냅샷을 오프라인으로 재생하면 `available=true`가 되지만 실행 단계는
여전히 빈 배열이다. 원본 스냅샷과 최초 실모델 결과는 바꾸지 않았다. 이 재생은
새로운 실모델 평가나 실행 가능 요건 통과가 아니다.

회귀 테스트는 다른 사고·플레이북 ID, 누락된 사본, 미완료 상태의 거부와 빈 초안의
보존을 검사한다. 관련 테스트는 수정 전 101개, 수정 후 124개 통과했다.
전체 Agent 테스트는 1,198개 통과, 실모델 선택 실행 2개 건너뜀이며 Ruff와 포맷도
통과했다. 원인 인용 추출, 임계값, 시나리오, 실행 조건은 변경하지 않았다.

수정 후 입력 지문은 기존 동기화 명령으로 다시 기록하고 승인 대기를 유지했다.
수정 전 두 엔진 결과를 수정 후 코드의 승인 결과로 사용하지 않았다.
수정 커밋은 `ca735d5`다. 최종 `pnpm verify`에서는 패키지·루트 계약 테스트
3,842개와 포맷·린트가 통과했고, 별도 `pnpm typecheck`도 통과했다.
마지막 `eval:offline`은 승인 대기 및 승인 fixture 부재로 실패했다. 실제 실패 결과는
별도 실행 디렉터리에 있으므로, 이 메시지의 결과 부재는 모델을 호출하지 않았다는 뜻이 아니다.

## 보존과 정리

원본 정규화 결과는 `tests/results/model/20260916T232909Z/results/`에 보존했다.
상세 로그·스냅샷·정리 증거는 `/tmp/rca-model-eval-current/`에 있다.
실패 결과를 `tests/fixtures/results/`의 승인 결과로 게시하지 않았다.

Strands 평가가 만든 RCA·활성 인시던트·플레이북 기록은 원본을 백업하고 다른
참조가 없는지 확인했다. 완료된 독립 평가의 ID·소유권·revision 조건과 실행 부재를
확인한 뒤 DynamoDB 항목 20개, 보고서 S3 객체 1개, 검색 벡터 2개만 정리했다.
해당 항목의 잔여 수는 0이다. 다른 사고 데이터는 삭제하지 않았다.

Headless는 격리된 로컬 평가 하네스로 실행했다. 알람 큐 소비 워커를 기동하지 않았다.
종료 후 배포 설정은 Headless 분석 0개·Strands 1개로 재확인했다.
SNS 알림은 평가에서 비활성화했고, 장애 주입·복구 명령·배포는 수행하지 않았다.

## 남은 차단 조건

실제 관측과 일치하는 복원 기준을 평가 입력으로 검증·재생하는 경로가 필요하다.
원인 및 대안 판정에 필수 증거를 연결하지 못한 결과도 재검증해야 한다.
두 엔진의 필수 조건을 만족한 실제 결과가 없으므로 기준선을 승인하거나
`pnpm verify`의 모델 승인 게이트를 통과했다고 보고할 수 없다.
