RCA 에이전트·보고서 템플릿 — 정상화 우선 3단계

상태: 사용자 확인을 마친 RCA 3파트 계약의 구현 템플릿. 두 엔진과 대시보드에 반영했으며 로컬 테스트를 통과했다. 실제 모델 평가와 배포 환경의 전체 장애 시연은 아직 검증하지 않았다. <...>는 실제 증거로 채울 자리다. 미확인 값은 미확인으로 남기며 명령의 자리표시자는 승인 전에 모두 해소한다. 실제 사용자 보고서는 공통 사고 머리말과 세 파트의 출력 양식으로 구성한다. 담당 에이전트의 작업 지침과 아래 ADR 변경 설명은 작성·구현 지침이며 사고 보고서에 반복 출력하지 않는다.

공통 진행 규칙

선택된 분석 엔진 안에서 정상화 담당 → 근본원인 담당 → 운영 개선 담당 순서로 진행한다. Strands와 Headless가 같은 알람을 동시에 소비한다는 뜻은 아니다. 본 시연의 분석 엔진은 Strands이며, 승인된 쓰기는 별도 실행 워커가 담당한다.

  1. 정상화 담당은 검증 가능한 롤백 대상과 런북을 먼저 만들고 저장한다. 제안할 수 없으면 부족한 근거와 제안 불가 사유를 남긴다.
  2. 1번 결과가 저장되면 근본원인 담당이 시작한다. 사용자의 런북 승인·거절·미응답이나 실행 중·성공·실패·취소 상태를 기다리지 않는다.
  3. 근본원인 담당이 분석 결과 또는 미확정·실패 사유를 저장하면 운영 개선 담당이 시작한다. 미확정 원인을 사실로 취급하지 않고, 확인된 관측과 부족한 자료를 구분해 제안한다.
  4. 세 담당은 자기 파트만 작성한다. 오케스트레이터는 호출·상태·전달을 관리하며 누락된 원인·명령·검증 결과를 대신 만들어 채우지 않는다.
  5. 분석 에이전트는 서비스 변경이나 PR 게시·머지를 실행하지 않는다. 코드와 CI/CD 변경은 검토 가능한 제안으로 제시한다.
  6. 사용자에게는 세 파트를 같은 사고 화면에서 순차 공개한다. 파트 1이 준비되면 나머지가 진행 중이어도 해당 런북을 검토할 수 있다.
  7. 조기 공개를 위해 RCA 전체를 먼저 COMPLETED로 바꾸지 않는다. 정상화 파트의 완료·검증과 전체 분석 완료를 따로 기록한다.
  8. 기존 전체·단계 예산과 재시도 한도를 지키며, 다음 파트에서 전체 기한을 다시 시작하지 않는다. 전체 예산 부족으로 후속 파트를 시작하지 못하면 미시작 사유를 표시하고 전체 분석 성공으로 세지 않는다.

런북 실행 상태와 세 분석 파트의 진행 상태를 분리한다. 런북 실행 취소를 분석 전체 취소로 해석하지 않는다. 분석 전체 취소·소유권 상실·저장 실패 등 기존 중단 조건은 유지하며, 취소된 작업을 독립 실행이라는 이유로 계속 쓰게 하지 않는다.

파트 1. 빠른 정상화 — 먼저 실행할 수 있는 런북

담당 에이전트의 작업

질문: 지금 어떤 서비스를 어떤 검증된 버전으로 되돌리면 되는가?

  • 현재 증상, 최근 배포, 현재 서비스·태스크·설정과 장애 이전 정상 기준을 먼저 확인한다.
  • 전체 가설 트리와 코드 행 단위 분석, 운영 프로세스 검토가 끝날 때까지 기다리지 않는다.
  • 근본원인을 확정한 것처럼 쓰지 않는다. 이 단계는 관측에 근거한 임시 정상화 제안이다.
  • 정상 대상과 현재 대상, 입력 이벤트 호환성, 원본 근거가 검증되지 않으면 제안 불가로 기록한다.
  • 검증된 고정 런북 또는 제안 불가 사유를 저장하면 이 담당의 작업을 마치고 다음 담당에 넘긴다.

  • 실행·검증 상태: <승인 전 / 실행 기록 링크; 제안을 실행 성공으로 표시하지 않음>

완성되지 않은 명령은 승인 대상이 아니다. 배포 수렴·지표 대기 각 900초, 실행 전체 3600초와 도구 호출 1200초의 기존 한도는 유지한다. 조회 증거, 시도 양수·실패 0인 두 구간, 해당 알람 OK와 실제 완료 쓰기를 확인하며 API 성공만으로 해결을 선언하지 않는다.

롤백이 뒤의 원인 분석에 필요한 장애 상태를 없애지 않도록, 정상화 담당은 조기 런북을 공개하기 전에 장애 시간 구간·현재 B의 식별·관련 원본 근거를 고정한다. 이는 전체 근본원인 분석을 먼저 끝내라는 뜻이 아니다. 뒤 담당이 당시 소스와 관측을 다시 읽을 수 있을 만큼의 증거를 보존하고, 복구 후 현재 상태로 대체하지 않는다.

조기 승인에 대한 계약 변경 제안

근본원인 확정과 분석 전체 완료를 기다리지 않고도, 위 정상화 근거와 고정 런북이 서버 검증을 통과한 경우 해당 서비스 롤백을 사용자가 승인할 수 있게 한다.

이는 검증된 정상 기준으로 되돌리는 롤백에 한정한 제안이다. 임의의 복구 명령이나 정상 기준이 없는 대상을 원인 미확정 상태에서 허용하는 제안이 아니다. 근본원인 신뢰도 기준을 낮추거나 confirmed=true를 대신 부여하지 않는다.

조기 공개는 이번 사고의 검토·승인용이다. 전체 분석이 끝난 공개 플레이북 지식으로 검색 게시하거나 검증됨으로 승격하는 것은 별도 계약을 따른다. 실제 승인 시 expectedDigest, 현재 배포·정상 대상, 권한과 단계 계약을 확인하고 불변 승인 사본을 저장한다. 이후 파트가 새 조치를 제안하면 새 런북·새 승인이 필요하다.

승인 예약 시점에도 같은 정상화 개정본이 현재 승인 가능하고 철회되지 않았는지 조건부로 대조한다. 읽은 뒤 교체·철회된 제안을 뒤늦게 예약하지 않는다. 승인 사본의 전체 내용은 기존 지문 검사 대상이며, 파트 2·3은 별도 산출물로 저장해 그 사본의 원인 설명·예방 내용·명령을 나중에 바꾸지 않는다. 예약 후 큐 전송을 재시도할 때도 같은 실행 ID와 같은 사본을 사용하며, 새 보고서 내용으로 기존 승인 ID를 재사용하지 않는다.

파트 2. 근본원인 — 잘못된 코드와 영구 수정

담당 에이전트의 작업

질문: 왜 실패했으며 어떤 코드·매핑을 고쳐야 하는가?

  • 파트 1 결과와 원본 관측을 읽고, 코드·이벤트 스키마·DB 스키마·배포를 대조한다.
  • 장애 시점에 고정한 B의 소스·관측 구간을 분석한다. 롤백 후 A의 관측은 사후 관측으로 구분하고 당시 장애가 없었다는 근거로 바꾸지 않는다.
  • 런북 실행 기록은 있으면 추가 근거로 읽지만, 없어도 분석한다.
  • 가설을 검증하고 원인 확정과 대안 기각에 각각 실제 사용한 증거를 연결한다.
  • 기존 서버 소유 확정·신뢰도·검증 루프·재생성 기준을 유지한다.
  • 코드 수정 PR 미리보기를 만들되 실제 수정 전 원본·파일·행·비교 기준을 확인한다.

  • 적용 상태: <제안 / 미적용; 실제 게시·머지와 구분>

5 Whys와 타임라인: 확인된 증상에서 기술적 원인까지 연결한다. 근거가 없는 “왜”에서 멈추고 부족한 자료를 표시한다. 운영자 실수나 확인하지 않은 CI 공백을 확정 원인으로 채워 넣지 않는다.

코드 원본을 못 읽었다면 파일·행·diff를 지어내지 않는다. 원인 미확정·자료 부족도 결과로 저장해 다음 운영 개선 담당이 무엇을 확인해야 하는지 알 수 있게 한다. 후속 분석이 파트 1 런북의 변경을 요구해도 이미 승인한 사본을 덮어쓰지 않는다.

파트 3. 운영 개선 — 배포 전에 같은 문제를 막는 절차

담당 에이전트의 작업

질문: 이 결함이 다시 배포되지 않게 어떤 운영 검사를 추가해야 하는가?

  • 파트 2 결과와 실제 CI/CD·테스트·배포 설정을 읽는다. CI/CD는 빌드·검사·배포를 자동으로 이어 주는 절차다.
  • 런북이 미승인·미실행·실패·취소 상태여도 진행한다. RESOLVED를 기다리지 않는다.
  • 현재 존재하는 검사와 확인하지 못한 검사를 구분한다. 설정을 못 읽었다는 이유만으로 “검사가 없었다”고 단정하지 않는다.
  • 개선마다 검사할 계약, 삽입 지점, 배포 차단 조건, 검증 방법과 담당을 제시한다.

출력 양식

운영 관점의 확인된 공백: <실제 검사·배포 설정의 근거 또는 확인 필요>

개선 제안 넣을 단계 검사·차단 조건 검증 방법 담당·상태
이벤트–DB 스키마 호환성 lint <PR/빌드 검사> <이벤트 필드·내부 매핑·SQL 컬럼이 선언된 DB 스키마와 불일치하면 실패> <정상/결함 사례의 통과·실패> <담당·제안 상태>
실제 DB 쓰기 계약 테스트 <CI 테스트> <v1·v2 처리, 원래 시각, 실제 커밋이 어긋나면 실패> <격리된 PostgreSQL 테스트 결과> <담당·제안 상태>
롤백 호환성 검사 <배포 전> <현재 이벤트 버전을 정상 복원 버전이 처리하지 못하면 차단> <동일 v2 입력으로 후보 버전 시험> <담당·제안 상태>
정상 기준·스모크 검사 <배포 전후> <검증된 정상 기준이나 실제 저장 증거가 없으면 승격하지 않음> <기준 파일과 실제 저장 관측> <담당·제안 상태>

lint는 코드를 실행하기 전에 규칙 위반을 찾는 자동 검사다. 정적 스키마 검사만으로 실제 DB 동작까지 검증했다고 보지 않고 실제 쓰기 계약 테스트를 함께 제안한다. 구체 검사 도구와 파일은 저장소를 확인해 정하며, 없는 CI 파일·행이나 테스트 결과를 만들지 않는다.

조치 항목: <재발 방지 / 영향 축소 / 프로세스 개선별 담당·우선순위·완료 기준>

교훈: <잘된 점 / 개선점 / 확인된 아차 사례; 근거 없는 항목은 미확인>

운영 개선 PR 또는 작업 제안: <확인한 CI/CD 파일과 변경안, 적용·테스트 상태>

분석 에이전트가 CI/CD를 직접 변경하거나 PR을 자동 머지하지 않는다. 제안이 작성됐다는 이유로 운영 통제가 이미 적용됐다고 표시하지 않는다.

실행 결과와 분석 원본의 관계

  • 실행 결과가 나중에 도착하면 실행 ID·시간이 있는 별도 증거로 연결한다. 실행 전 작성한 원인·운영 제안에 당시 알고 있었던 사실처럼 소급 삽입하지 않는다.
  • 실행이 성공해도 파트 2의 원인 확정이나 파트 3의 개선 검증을 자동 통과시키지 않는다.
  • 세 분석 파트가 끝나도 서비스가 복구됐다고 표시하지 않는다. 실제 복구는 실행 판정이 소유한다.
  • 실행을 근거로 런북을 검증됨으로 승격하는 기존 회고와, 항상 진행하는 파트 2·3은 구분한다. 실패·미실행 런북을 분석 결과만으로 검증됨으로 승격하지 않는다.

기존 ADR에서 바뀌는 계약

아래는 같은 결정의 기존 소유 ADR을 수정할 변경안이다. 새 번호를 만들거나 현재 Accepted 상태를 새 동작의 구현 완료로 해석하지 않는다.

기존 소유 ADR 변경 전 계약 승인된 계약
agent/0007 보고서 분석 완료 뒤 단일 원문 확정, 미확정 실행 금지 3파트 순차 공개와 단계별 원본 보존, 검증된 정상화 런북의 조기 승인
agent/0008 플레이북·런북 완료 세션·확정 원인 뒤 승인, 미확정은 빈 실행 단계 정상화 파트의 저장·검증 완료를 사고별 조기 승인 근거로 사용; 공개 지식 게시와 분리
agent/0011 오케스트레이션 RCA → Report 정상화 → 근본원인 → 운영 개선; 실행을 기다리지 않는 역할별 산출물
agent/0017 실행 승인 이 데모는 원인 확정 후 롤백 승인 서버 검증된 정상 기준·대상·호환성·고정 런북을 근거로 확정 전에도 사용자 승인 허용
agent/0018 회고 해결 후 실행 증거 기반 교정·승격 실행 후 교정·승격 조건은 유지하고 상시 원인·운영 분석과 명확히 분리
agent/0001·0014, infra/0002 관측·증거 사고 범위·정상 기준·원본 증거와 시간 관계 보존 조기 정상화 전에 장애 시점 근거를 고정하고 복구 후 관측과 분리해 후속 담당에 전달
infra/0005 분석·실행 추적 완료 분석의 승인 근거와 실행 기록을 보존 파트별 완료·개정·승인 적격 상태와 조기 승인 예약의 조건부 일치를 보존
infra/0007 데모 원인 확정 → 승인 실행 → 후속 분석 정상화 런북 우선, 실행과 독립된 원인·운영 분석을 시연
agent/0016 평가 현재 분석 완료·원인·절차 게이트 조기 런북의 근거 검증과 뒤 분석의 독립 진행을 별도 검증

사용자 확인은 완료됐다. 관련 선행 결정과 실제 상태·권한 변경을 정리하며 런타임 프롬프트·완료 게이트·대시보드·평가 하네스를 함께 구현·검증한다. 보고서 제목만 바꾸거나 현재 완료·확정 검사를 무조건 우회하는 구현은 이 변경안이 아니다.

승인 후 함께 반영할 런타임 범위

  • Strands: prompts/report.py, prompts/playbook.py, 분석 오케스트레이션과 완료·게시 경로.
  • Headless: 전문 역할 프롬프트, harness/analysis의 역할·도구 범위, 전문 프로세스 호출 순서와 산출물 저장·완료 검증.
  • Dashboard: 진행 중인 파트 조회, 조기 런북의 승인 적격 판단, 개정본 조건부 예약, 분석 진행과 실행 결과의 독립 표시·갱신.
  • 평가: 조기 정상화 근거, 미승인·미실행·실패·취소 상태에서 뒤 파트 진행, 승인 후 분석 갱신에도 명령 불변, 원인·코드·CI 제안의 증거 연결을 검사.

기존 가설 검증·증거 격리·시간 예산은 각 소유 ADR의 규칙을 유지해 회귀 검사한다. 이 목록은 적용 대상이며, 현재 활성 프롬프트나 승인 코드를 이미 수정했다는 뜻은 아니다.
