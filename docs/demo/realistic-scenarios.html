RCA Agent · 2026-09-10 · 운영자·검토자용

증상에서 원인을 구별하는 네 시나리오

현재 상태: 로컬 PostgreSQL 실측 반영, AWS 알람 보정 대기. 핵심 관측은 main/DB 작업자의 실제 두 번째 실행과 소스 해시에 연결했다. 알람 외곽 입력은 합성 예시이고, 정상 기준·사고 구간의 실제 UTC 시각을 사용한다. 모델에 복원 결과를 전달하지 않는다. 실패한 첫 실행과 초기 합성 초안도 보존했다. AWS 배포 성공·실모델 통과·기준선 승인은 없다.

1. 무엇을 구별하는가

RCA는 근본원인분석이다. 연결을 얻지 못했다는 증상만으로는 누수인지, 작아진 풀인지, 락 때문인지 알 수 없다. 연결 풀은 요청이 함께 쓰고 반환하는 연결 묶음이고, 트랜잭션의 락은 다른 작업의 접근을 제한하는 잠금이다.

카탈로그 ID / 분류구별하는 증거복원 확인
pool-config-regression
unsupported		 작아진 유효 풀 설정, 획득 대기, 요청 뒤 연결 반환, DB 전체 연결 상한, 같은 시작 부하 원래 설정으로 복귀한 뒤 같은 부하에서 저장·대기 회복
query-amplification
slow-query		 같은 결과 행을 읽는 SQL 횟수, 개별·전체 시간, 일괄 조회와 행별 조회 코드 차이 원래 이미지에서 같은 응답 내용·조회 횟수·시간 회복
maintenance-transaction-lock
unsupported		 차단자·대기자, 잠금 모드·SQL·트랜잭션 시각, 해당 실행의 작업 소유권 소유 정비 트랜잭션만 롤백한 뒤 저장 재개
exception-session-cleanup
db-leak		 예외 요청 종료 뒤에도 남은 연결, 정리 코드 차이, 이후 정상 요청의 풀 대기 정상 이미지 복귀·결함 태스크 종료 후 같은 예외 입력의 연결 반환

unsupported는 기존 주입 유형에 속하지 않는 원인이라는 뜻이다. 풀 설정과 락을 누수로 바꾸지 않는다. 각 사례는 별도 관측으로 반박할 수 있는 경쟁 원인 두 개도 요구한다. 데이터가 없다는 이유만으로 원인을 기각하지 않는다.

2. 세 종류의 검증을 따로 기록한다

아래는 의존성 없는 정적 SVG 흐름도다. 이어지는 Mermaid 원문으로 같은 관계를 재사용할 수 있다.

Mermaid 원문
flowchart LR
  L["로컬 DB: 정상 → 결함 → 복원"] --> R["정상·사고 관측 선택"]
  R --> M["제공 관측 모델 평가: 두 엔진"]
  M --> G["동일 구조·안전성 채점 → 검토 후 승인"]
  A["AWS 배포 제어: 소유 변경·원상복원"] --> D["증상 알람 → 신규 세션 → 실제 증거 탐색"]

로컬 DB 재현은 실제 쿼리와 연결 수명을 확인한다. 제공 관측 모델 평가는 주어진 증거의 해석·인용을 확인한다. 배포 E2E(처음부터 끝까지의 검증)는 알람 전달·신규 세션·실제 증거 탐색과 원상복원을 확인한다. 한 계층의 통과로 다른 계층을 통과했다고 기록하지 않는다.

3. 알람 시각과 평가 세션 시각

알람에 리전, 네임스페이스, 차원(지표의 리소스 좌표), 통계, 기간, 임계치, 평가 조건이 있으면 두 어댑터가 전달한다. 제공되지 않은 조건은 원본 메타데이터에 추가하지 않는다. 운영 기본값은 유지하며 모델 평가에서는 없는 리전·통계·주기·시각을 not provided로 표시한다. 숫자 0과 제공된 원본 값은 보존한다.

Strands는 반복 평가가 과거 세션과 충돌하지 않도록 새 실행 시각을 사용한다. 원본 알람 시각은 별도 메타데이터로 남고, 제공된 관측 구간도 각 관측에 명시한다. 원본에 없는 구간은 null과 누락 사유를 유지한다. 새 세션의 생성 시각을 사고 관측 시각으로 해석하지 않는다. 락의 분석 마감은 차단 쓰기의 종료 시각이며, 그 뒤의 해제·복원 요청은 제공하지 않는다.

4. 승인 전 남아 있는 일

  1. B의 최종 UTC 측정과 중립 capture ID를 사용하고 원본·복원 결과는 운영자 자료로 보존한다.
  2. 지속 부하로 AWS 조회 알람 임계치를 보정한다. 기본 500ms는 이번 로컬 조회 실측보다 높았다.
  3. 배포 제어가 준비된 사례에만 deployed-e2e를 선언한다.
  4. 새 입력으로 두 엔진의 실제 결과를 모두 수집하고 안전한 복구 절차까지 검토한다.
  5. 별도의 승인 절차로 fixture와 기준선을 갱신한다. 통과·검토 전에는 승인하지 않는다.

원래 네 입력과 정규화 결과는 tests/fixtures/historical/original-four/에 보존했다. 기존 실패 결과와 tests/baseline/은 그대로다. 현재 fixture 부재·digest 불일치에 따른 게이트 실패는 숨기거나 합성 결과로 메우지 않는다.
