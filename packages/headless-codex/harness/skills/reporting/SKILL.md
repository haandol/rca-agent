# RCA 리포트와 플레이북

분석의 산출물은 플레이북을 포함한 리포트 하나다. Report 에이전트는 서술과 구조화
플레이북을 만들지만, 서버가 최종 `## 근본 원인`과 `## 대응 플레이북` 섹션을
검증 산출물과 `playbook.json`에서 다시 렌더링한다.

## 입력

- 원본 알람 상세
- RCA 전문 에이전트의 최종 결과와 증거
- 서버 검증 `effective_state`: 판정의 권위다. 요약과 충돌하면 서버가 선택한 가설 및
  실제 reasoning/evidence_summary를 따른다. 누락된 기각이나 관측 ID를 보충해 만들지 않는다.

입력에 없는 사실은 만들지 않는다. **복구를 실행하지 않았으므로 실행 결과나 정상화
여부를 쓰지 않는다.** 플레이북은 사용자가 승인한 뒤 별도 에이전트가 수행한다.

## report.md

다음 섹션을 포함한다.

- `## 인시던트 요약`
- `## 영향`
- `## 증거 시간 범위`
- `## 근본 원인`과 확정 여부·신뢰도
- `## 5 Whys` (증거가 끊기면 추가 조사 필요로 종료)
- `## 뒷받침 증거`
- `## 가설 분석 경로`
- `## 대응 플레이북`
- `## Action Items`

서버는 이 아홉 섹션의 내용을 유지하며 맨 앞에 `## 빠른 판단`을 추가한다.
요약에는 영향·심각도·서버 판정 원인·확정 여부·신뢰도·다음 조치·런북 상태와
유사 플레이북 비교 상태를 표시한다. SUMMARY/DETAIL은 표현 방식이며 내용을 줄이는
새 스키마가 아니다. 상세 설명·증거·5 Whys·가설 경로·명령을 요약으로 대체하지 않는다.
`## 빠른 판단`과 기계 판독용 `rca-summary:v1` 메타데이터는 서버가 작성하므로 모델이 만들지 않는다.
별도 비교 프로세스가 게시된 실제 플레이북과 현재 증거를 비교한다. Report는 과거 지식을
자동 교체했다고 쓰거나 비교 결과·변경 제안을 미리 만들어 기록하지 않는다.

### `## 대응 플레이북`

이 섹션에는 서버가 교체할 임시 설명을 둔다. 실행 절차의 권위는 `playbook.json`이다.
최종 리포트에서 서버는 다음을 포함한다.

- 이 플레이북이 **초안(DRAFT)**이며 아직 실행으로 검증되지 않았다는 표기
- 각 실행 단계의 `step_id`, 의도, 수행할 작업, 성공 판정 기준
- 되돌릴 수 없는 조치가 필요한 경우 그것이 실행 대상이 아니라 수동 조치 권고임을 명시

서버는 `playbook.json`의 각 단계에서 step ID, 의도, 작업, 성공 판정 기준과 순서를
그대로 렌더링한다. 모델이 작성한 단계 서술은 최종 승인 문서에 남지 않는다.

확정 근본원인이 없으면 실행 단계를 만들지 않고, 무엇을 더 조사해야 하는지를 쓴다.

### `## 증거 시간 범위`

다음 두 라벨과 ISO-8601 시작·종료 시각을 반드시 쓴다.

- `Current alarm window`: 현재 알람의 상태 변경 시각을 기준으로 조사한 구간
- `Historical comparison window`: 정상 baseline 또는 과거 비교를 위해 조회한 구간

각 라벨과 시작·종료 시각은 **같은 한 줄**에 쓴다. 라벨과 시각을 다른 줄이나 표의
다른 칸으로 나누면 저장이 거부된다. 시각은 초 단위까지와 타임존 표기(`Z` 또는
`+09:00`)를 포함한 ISO-8601 이어야 한다. 다음 형식을 그대로 사용한다.

```
- Current alarm window: 2026-07-29T13:00:00Z ~ 2026-07-29T14:00:00Z
- Historical comparison window: 2026-07-29T12:00:00Z ~ 2026-07-29T13:00:00Z
```

### 증거 인용 규칙

알람 컨텍스트가 신호를 `[식별자] 요약` 형태로 제공한 경우, 그 신호를 근거로 사용한
증거 항목에 식별자를 원문 그대로 함께 적는다. 근거로 쓰지 않은 신호의 식별자는
적지 않으며, 제공되지 않은 식별자를 만들지 않는다.

이는 기각된 가설에도 적용된다. 가설을 기각한 것은 어떤 관측이 그것을 반증했기
때문이므로, `## 가설 분석 경로`의 기각 항목에 반증 근거가 된 신호의 식별자를 함께
적는다. 반증 근거 없는 기각은 발견이 아니라 주장이다.

모든 증거 항목에 어느 window에서 관측했는지 표시한다. 이번 실행의 current alarm
window보다 이전에 생성된 수동 장애 주입·수동 테스트 로그는 historical context일
뿐이며 현재 장애의 발생·원인·지속 증거로 서술하지 않는다. 시각이 없거나 window를
판별할 수 없는 로그는 현재 장애 증거에서 제외한다.

## playbook.json

스키마와 `execution_steps` 규칙은 시스템 프롬프트의 플레이북 스키마 절을 따른다.
핵심은 세 가지다.

- `step_id`는 안정적인 식별자이고 `report.md`의 서술과 일치해야 한다.
- `action`은 설명이며, `commands`에 현재 사고의 대상·리전을 고정한 완성된 AWS CLI를 담는다.
  각 단계는 commands, 고정 deployment_wait, 고정 metric_wait 중 하나만 가진다. 과거 명령·대상을
  상속하지 않으며, 승인 후 변경은 새 승인을 요구한다. 근거 부족이면 실행 목록을 비운다.
- `success_criteria`는 관측 가능한 기준이어야 한다. 없으면 실행 에이전트가 해결
  여부를 판정할 수 없다.

`verification_status`는 항상 `DRAFT`다.
서버가 전달한 별도 승인 실행 워커의 명령 정책과 발견된 소유자를 함께 확인한다.
읽기 전용 소유자 확인 → 승인된 조작 → 사후 건강 관측 순서를 유지한다. 직접 SQL,
셸, ECS exec나 새 태스크 등록/실행으로 수동 롤백을 대체하지 않는다.
독립 태스크의 소유권과 롤백 경로가 증명된 경우에만 그 태스크 중지를 제안한다.
근거 없는 스케줄러 중지나 환경 플래그는 만들지 않으며, 실행 불가능한 조작은
수동 에스컬레이션으로 남긴다. 확인되지 않은 소유 태스크를 추측하지 않는다.

Report 전문 에이전트는 `report.md`와 `playbook.json`을 모두 저장한다. 두 저장 응답의
`ok: true`를 확인한 뒤 파일명과 저장 성공만 담은 짧은 완료 응답을 반환한다.
보고서 Markdown 전문을 최종 응답에 반복하지 않는다. 저장 실패는 교정하고,
해결할 수 없으면 실패를 명시한다.
