같은 입력, 실제 DB 결함, 확인 가능한 복원

정상 서비스와 결함 서비스가 같은 PostgreSQL에 같은 종류의 요청을 보냅니다. 연결 설정·조회 코드·정리 코드·정비 트랜잭션만 바꾸어 원인과 결과를 비교합니다. 자세한 명령과 인터페이스는 README에 있습니다.

네 가지 원인과 구별할 증거

원인실제로 달라지는 동작복원 확인
풀 설정앱이 동시에 빌릴 수 있는 연결을 8개에서 1개로 축소. 실제 INSERT가 경쟁.8개 복원 후 같은 8개 요청 성공.
조회 증폭 · r2120행을 한 번에 읽던 SELECT가 ID 목록 + 행별 조회로 121회가 됨.r1로 돌아가 SQL 1회, 같은 응답 hash.
정비 락별도 프로세스가 SHARE 락을 소유해 INSERT의 락 획득을 막음.그 프로세스만 SIGTERM, 롤백 후 저장 재개.
세션 정리 · r3음수 LIMIT 오류 뒤 연결이 반환되지 않아 이후 유효한 저장까지 실패.r1과 종료 정리 후 같은 오류에도 연결 반환.

연결이 남는 이유

세션은 업무 쿼리를 실행하는 객체이고, 풀은 재사용할 DB 연결의 묶음입니다. 연결을 빌린 뒤 오류가 나도 반환해야 다음 요청이 사용할 수 있습니다. r1은 finally에서 닫습니다. r3은 정상 처리 뒤에만 닫도록 소스가 달라져 예외 경로에서 반환하지 않습니다.

저장소는 async with database.session_context()로 호출합니다. 이렇게 해야 저장소 본문의 오류와 취소가 정리 코드를 감싼 범위에 전달됩니다. 기존 async for 안에서 바로 반환하는 방식은 이런 전달과 즉시 정리를 보장하지 않습니다.

취소 실험은 실제 연결에서 backend PID를 조회한 다음 소비자를 취소합니다. 드라이버가 실행 중인 SQL을 취소하면서 연결 자체를 무효화하는 경우와 구별한 실험입니다.

관측과 안전한 실행 범위

요청별 ID로 SQL hash·횟수·시간, 연결 획득과 반환을 연결합니다. 관측 전용 연결은 1개로 제한하며 업무 요청이 대기 중이어도 차단 관계를 읽습니다. SQL 매개변수·원문·비밀번호는 로그에 담지 않습니다.

로컬 runner는 명시한 127.0.0.1 포트의 rca_demo만 허용하고 5432는 거부합니다. 자기 실행의 스키마와 프로세스만 정리합니다. Docker 컨테이너 수명은 호출자가 관리합니다.

빌드 시 r1/r2/r3 소스가 고정되고, 시작 시 manifest의 파일 hash를 확인합니다. 일반 실행 환경변수로 리비전을 바꿀 수 없습니다. 기본 이미지는 r1입니다.

검증 경계: 실제 PostgreSQL + 서비스 메서드 + 독립 빌드 소스. HTTP 전체 경로, AWS 배포·알람, 모델 평가 결과는 별도 검증입니다.
