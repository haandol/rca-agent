Realistic Healthcare demos

Prepared tooling; no AWS deployment or mutation was performed during implementation. The command separates requested changes, observed rollout, and verified service recovery. It never claims causal reproduction or model-evaluation success.

Entry point: python3 scripts/run_realistic_demo.py. Requires Python 3.11+, Unix file locks and AWS CLI v2. Use a single shared, durable --journal-root for every operator targeting the service.

Commands

All commands take the same caller RunId (1–48 letters, digits, underscores or hyphens) and target. Plan freezes controls; subsequent commands read them from the immutable snapshot.

JOURNAL_ROOT=/absolute/shared/realistic-demo-evidence
RUN_ID=demo-20260910-pool-01

demo() {
  python3 scripts/run_realistic_demo.py "$@" \
    --run-id "$RUN_ID" --region us-east-1 \
    --cluster RcaAgentDevHealthcare --service RcaAgentDevHealthcare \
    --journal-root "$JOURNAL_ROOT"
}

# AWS read-only; baseline must already be stable, private and healthy.
demo plan --scenario pool-config \
  --pool-size 1 --max-overflow 0 --pool-timeout 1 \
  --alarm RcaAgentDev-Healthcare-VitalIngestFailures \
  --alarm RcaAgentDev-Healthcare-PatientVitalsQueryLatency \
  --alarm RcaAgentDev-Healthcare-RdsHighConnections

# Future authorized operation; these two commands DO mutate AWS.
demo apply --wait-seconds 600
demo status
# Preserve status evidence during the fault; causal evaluation is separate.
demo restore --wait-seconds 600

For an image scenario, choose a new RunId and replace the plan scenario/controls with --scenario query-revision --image "$QUERY_IMAGE_DIGEST_REF" --revision "$QUERY_SOURCE_ID" or the session equivalents. For maintenance use --scenario maintenance-lock --hold-seconds 7200. Every owned maintenance launch uses the fixed command python -m test_service.maintenance --run-id RUN_ID --hold-seconds SECONDS --schema SCHEMA from the pinned healthy image. RunId, finite positive hold duration up to 7200 seconds, and PostgreSQL schema identifier are validated before launch; --maintenance-schema defaults to public. Use a healthy image whose maintenance module supports the coordinated 7200-second bound (older builds capped at 900 seconds). The --maintenance-command-json option has been removed. Apply refuses an existing journal with a different recorded command; restore still discovers and stops its proven owned tasks, including after a lost RunTask response, without launching another task or rewriting the journal snapshot.

--profile NAME is optional. Plan/apply/status return 0 when the command completes; this does not assert scenario success. Restore returns 0 only for verified recovery, 2 while recovery is pending or failed, and 1 on a command-level exception. Argument errors return 2. Read JSON fields, including recoveryVerified, checks, ownershipError, errors and queryLatency. scenarioSuccess stays false because the tool does not perform causal/model evaluation. A zero-wait apply is only a submitted change plus one observation. A timed-out/failed apply runs the same restore poller with a fresh cleanup budget equal to --wait-seconds. Even if cleanup verifies recovery, apply exits 1 and reports operationSucceeded=false with the independent result under cleanup.

Immutable original image and r1 source evidence

Plan rejects a tag-based original application image before claiming the service or registering a fault revision. Recording a resolved digest next to a mutable task definition is insufficient: restoring that exact definition could otherwise launch different code. The original definition itself must pin the observed digest. Fault images also require digest references.

Plan reads source_manifest startup events from each current task's exact awslogs stream, using its creation time as the lower bound. Every event must report revision=r1, verified=true and a source-file map matching its fingerprint; fingerprints must agree across baseline tasks. Raw events, task identity and image digest are retained in the snapshot. An environment label such as DEPLOYED_REVISION=r1 is not source proof. Missing/expired logs, an unbuilt source tree (verified=false), r2/r3 or conflicting fingerprints stop plan. The operator needs read access to logs:FilterLogEvents for the task's log group in the target region. This is runtime source evidence, not signed build provenance or approval evidence.

Apply refuses an older snapshot without this evidence or with a tag-based original image. Restore refuses to launch a tag-based original from an older journal, while still attempting independently owned maintenance cleanup. It does not silently create a replacement definition or move an image tag. Prepare and measure the immutable r1 baseline separately before starting a new run.

Bounded restore and failure cleanup

restore --wait-seconds 600 attempts the original task-definition restore and own-job cleanup, then polls until the service is stable, original image digests are running, own jobs have stopped, two fresh complete metric periods are healthy and alarms are OK. The same implementation runs after an apply error, including an apply observation timeout.

restorationState=verified requires recoveryVerified=true. A zero wait performs one cleanup/observation attempt. If verification is unfinished, the result stays restorationState=pending and restore exits 2. An exhausted positive budget additionally sets waitExpired=true. Journal files and the service owner are retained; resume with the same RunId and journal. Update-service/reset acknowledgements never count as recovery.

The apply and cleanup waits each get their own budget, so a failed apply can take up to both polling budgets plus in-flight AWS calls. Each AWS CLI invocation has a 90-second timeout; the wait value bounds polling, not a hard wall-clock cancellation of an in-flight operation. A transient cleanup/read error is retained in the journal and can be retried during the remaining budget. No approval signature or approved-remediation causality is inferred; this is operator cleanup, separate from approval-execution E2E.

Separate baseline setup and calibration

Normal deployment configuration now supports the required pin. In the existing packages/infra/.toml [healthcare] section, set imageDigest = "sha256:<64 lowercase hex digits>" to the already published healthy r1 ARM64 image manifest digest. Keep imageTag set to its build identifier: it remains the DEPLOYED_REVISION label even when the image is pinned. The resulting application image is <account>.dkr.ecr.<region>.amazonaws.com/<lowercase namespace+stage>/healthcare@sha256:DIGEST. The optional HEALTHCARE_IMAGE_DIGEST environment variable overrides the TOML digest; empty or malformed values fail validation. With neither setting, legacy repository:imageTag behavior remains, which is not accepted by this demo's baseline guard.

This uses the normal CDK entry point and an existing registry image; no image build, push, tag move or demo-CLI guard change is needed. The command assumes the normal dependency stacks already exist. The digest selects image content, but neither it nor a label alone proves r1: after the separately authorized deployment stabilizes, plan must independently verify each running task's matching ECS image digest and production source_manifest evidence (revision=r1, verified=true, matching source fingerprint). Setting DEPLOYED_REVISION=r1 does not select r1 code or satisfy source verification. This preparation procedure is documentation only; no deployment was performed for this integration change.

  1. Before this demo run, prepare the healthy r1 service with its original application task-definition image pinned to repository@sha256:DIGEST, plus the fixed dataset and chosen traffic/observation profile through the normal deployment process. The pinned digest must exactly match every running application container's ECS imageDigest; for a multi-platform build use the matching platform image manifest digest. A latest, r1 or commit-looking tag is refused even if its current digest is known. This CLI does not prepare or mutate that profile.
  2. Collect healthy measurements and calibrate the query alarm using Average in milliseconds. Finish calibration before plan; do not tune traffic, query limit, observer interval or alarm settings during the fault/restored comparison. Compare fully stabilized service stages and retain transient rolling-deployment overlap as separate evidence.
  3. Run plan with repeated --expect-setting assertions for the prepared profile. A mismatch aborts before any cloud mutation. The run's original task definition is this measured, prepared baseline; reverting earlier calibration/setup is a separate operation.
  4. Apply only the selected cause. The service environment may change only the three pool-cause fields for pool-config, or the image/source identifier for revision scenarios, plus RunId lineage. Every other environment value and absence is preserved. Maintenance uses its own standalone task and leaves the service profile untouched.

Workload and alarm configuration

The new alarm is PatientVitalsQueryDuration / Average / Milliseconds, namespace Healthcare/Sensor, dimension ServiceName=healthcare-sensor-app, one-minute periods, two evaluation periods, greater-than-or-equal comparison, SNS ALARM and OK actions. Missing data stays unknown. Initial threshold 500ms is tuning, not a measured result. Snapshot/status evidence preserves the actual statistic and threshold. Existing ingest alarm and connection threshold 12 remain unchanged; service pool defaults remain 5 + 10 and the network stays private.

A task definition is an ECS launch specification; its ARN identifies the exact immutable revision. RunId identifies the caller's demo, not RCA analysis ownership. Each create-only JSON journal event includes a timestamp, previous hash and its own hash. Atomic publication and file fsync protect against partial writes. The first event retains the full task definition, image, settings including absent fields, network, deployment state, tags, running digests and baseline observations. Credential secret values are not resolved, but literal task environment values may be sensitive: keep the journal protected. Files are created mode 0600 and new directories 0700.

Before service changes, live task-definition/settings and RunId/hash must still match. Unexpected deployment/network/settings or foreign tags cause refusal; the tool never overwrites them. Service restore and owned maintenance cleanup are independent attempts. A lost RunTask response is rediscovered using startedBy and all ownership proofs; restore never launches another task. Registration results are recorded before use; an unacknowledged registration may leave an unused tagged revision, which is retained rather than deleted. Other tasks, database sessions, fault reset APIs, repositories and task definitions are never deleted.

revisionObservation distinguishes the original revision, the owned fault revision, the original seen after apply/restore, and a foreign revision. It retains fresh ECS rollback events and reports whether the original was already selected at the first restore observation. Without an ECS rollback event the return cause stays not-established. Restore does not deploy again when the exact original is already selected; a foreign revision is refused even if its settings look healthy. Observing the original does not by itself verify recovery.

Restore updates only the original task-definition ARN because other service settings were never changed. External setting drift is refused, not silently reset. After original rollout and digests are observed and own maintenance tasks stop, verification waits for two complete fresh one-minute buckets: positive ingest attempts, zero ingest failures and query Average below the observed threshold. All configured alarms must be OK and alarm configuration unchanged. maintenanceRestoration retains pre-restore stopped tasks and the full task exit reason/status, stoppedAt and container exit codes. approvedRestorationCausedRecovery stays false: neither an expired/already-stopped hold nor a stop API request proves an approved restore caused recovery. Missing metrics, partial rollout, differing digest or uncertain task termination remain unverified. This is operational recovery evidence, not proof that the causal scenario or model analysis was correct.

Journal storage failure: New claims, registrations, service updates and task launches require successfully persisted prechange intents. Once a change has a durable intent, snapshot and matching ownership, failure to save its response or an error/cleanup record does not block independent service restoration and owned-task stopping. Lost RunTask responses are rediscovered using the original intent, registered definition, startedBy and both ownership tags. Validated task ARNs also remain in memory for re-observation if discovery records cannot save. The original image and ownership checks still apply.

Every failed append is reported to stderr by event name and exception type; returned cleanup includes journalErrors, recoveryVerified=false and restorationState=pending. Apply exits 1 and restore exits 2. A later successful write in the same command cannot erase the evidence gap. Both cleanup branches are attempted, and a positive wait budget still permits retries, but journal failures prevent verified recovery. Recovery result records must save before owner release. If the acknowledgement after a completed untag cannot save, the controller attempts to reclaim its own tags only after checking that no foreign owner or deployment has appeared; reclaim failure remains visible in the result. Repair storage and resume restore with the same RunId and preserved journal to collect fresh evidence.

Limits: The journal and advisory lock must be shared by all operators. ECS tag/update operations do not provide an atomic compare-and-swap with these ownership checks; coordinate external deployments and never run independent journal roots against the same service concurrently. The local hash chain is tamper-evident against modified records, not WORM storage or protection against privileged deletion/truncation. SIGKILL, host loss, a lost/unreadable original journal or an ambiguous disappeared task require explicit restore with the preserved journal; no recovery guarantee is made without evidence. An append failure during an active command still permits the independent cleanup attempts described above. If RunTask has no acknowledged/discoverable task, the run remains unresolved. AWS eventual consistency or stopped-task retention can require repeated restore or manual evidence review; failures never authorize stopping a foreign task. New runs require a digest-pinned original application definition before any fault. Restoration reuses that exact definition and still checks observed digest equality. Missing registry content cannot be repaired by the tool and remains unverified; no ECR tag rewrite is attempted.
